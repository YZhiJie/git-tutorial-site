# EP.08 企业级分支模型

> 对应正文：[guide/collaboration/09-branching-models.md](../guide/collaboration/09-branching-models.md)

## 剧情回顾

- **第 1 格**：三十人团队沿用 Git Flow，发布越来越慢，hotfix 回灌频繁冲突。
- **第 2 格**：码叔摆出 Git Flow、GitHub Flow、Trunk-Based 三种模型的结构与适用场景。
- **第 3 格**：像素酱用三个问题做选型：发布频率、团队规模、回滚与审计要求。
- **第 4 格**：结案——模型只是骨架，分支保护、小 PR、自动化才是落地关键。

## 知识点拆解

### 第 1 格 · 分支越多，合流越痛

Git Flow 同时存在 main、develop、release、feature、hotfix 多条长期分支。每次发布要在多条线之间来回合并，hotfix 还要同时回灌 main 与 develop，冲突面积随分支寿命增长。

### 第 2 格 · 三种模型的定位

- **Git Flow**：严格版本发布，适合客户端、嵌入式、需要维护多个历史版本的场景；
- **GitHub Flow**：main 常驻可发布，feature 短分支 + PR 评审，适合 Web/SaaS 与中小团队；
- **Trunk-Based**：主干开发、极短分支、特性开关兜底，适合高频发布与成熟自动化团队。

### 第 3 格 · 选型三问

1. 多久发布一次？按版本发布偏 Git Flow，按天发布偏 GitHub Flow / Trunk-Based；
2. 团队多少人？三十人以上应压缩分支寿命、强化 CI，而不是增加分支层级；
3. 回滚与审计要求多强？强审计保留 release/hotfix 轨迹，否则优先简化。

三个问题里有两个指向同一模型，就选它；摇摆时先选更简单的。

### 第 4 格 · 让模型真正落地

```text
main 分支保护：
- 至少 1 人 approve
- CI 必须绿；禁止直接 push
- 线性历史或 squash 合并
```

再配合小 PR、频繁集成、自动化测试，冲突才会从源头减少。

## 坑点清单

1. 只改分支命名，不改评审与自动化流程，模型形同虚设；
2. feature 分支存活数周，合并时冲突成灾；
3. 团队规模扩大后仍照搬小团队流程，评审与集成成为瓶颈。

## 自测 3 题（含答案）

1. Git Flow 的主要成本是什么？——**多条长期分支带来的合流与回灌复杂度，发布节奏越慢成本越高。**
2. Trunk-Based 的前置条件？——**较强的自动化测试、特性开关与快速回滚能力。**
3. 分支模型选好后最关键的一步？——**配套分支保护、小 PR 与 CI 门禁，让规则真正被执行。**
