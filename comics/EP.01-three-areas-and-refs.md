# EP.01 三区模型与分支指针

> 对应正文：[guide/basics/03-three-areas.md](../guide/basics/03-three-areas.md) 与 [guide/basics/05-branch-basics.md](../guide/basics/05-branch-basics.md)

## 剧情回顾

- **第 1 格**：标签君改完三个文件，`git status` 红成一片，分不清哪些改动已经进了暂存区。
- **第 2 格**：码叔画出工作区、暂存区、版本库三层，说明命令只是在搬运快照，HEAD 指向的是分支引用。
- **第 3 格**：像素酱追问「新建分支会复制文件吗」，码叔用分支图回答：分支只是一个 40 位哈希的指针。
- **第 4 格**：结案——先看 status，再小步 `add -p`，一个提交只讲一件事。

## 知识点拆解

### 第 1 格 · 读懂 status 短格式

`git status -s` 每行两个字符：左列表示暂存区，右列表示工作区。

```bash
 M src/app.ts      # 工作区改了，还没 add
M  src/login.ts    # 已暂存，等待 commit
?? docs/notes.md   # 未跟踪文件
A  src/demo.ts     # 新增并已暂存
```

红字不是报错，只是状态提示。看不清就加 `-s`，比长格式更容易扫一眼。

### 第 2 格 · 三个区各存一份

- **工作区**：你正在编辑的文件，`git add` 之前的变化只在这里；
- **暂存区（index）**：下一次提交将要包含的内容，`git add` 把工作区快照写进来；
- **版本库**：`git commit` 把暂存区固化成 tree 与 commit 对象，形成不可变历史；
- **HEAD**：指向 `refs/heads/<branch>`，切换分支时 HEAD 换指向，工作区随之更新。

### 第 3 格 · 分支只是指针

```bash
$ cat .git/refs/heads/main
3f2a1c9a1b2c3d4e5f60718293a4b5c6d7e8f901
```

新建分支不会复制任何提交，只是新写一个指针文件；因此 `git switch -c` 瞬间完成。分支图里 `main` 与 `feature` 分叉，本质是两个指针停在不同提交上。

### 第 4 格 · 小步提交

- `git add -p` 逐块确认，避免把调试代码一起提交；
- 提交信息写「为什么」而不是「改了什么」；
- 在 detached HEAD 上提交不会自动属于任何分支，切走前要 `git switch -c` 接住。

## 坑点清单

1. `git add .` 把构建产物、`.env`、密钥一起暂存；
2. 只看 `git status` 的长格式，忽略了「已暂存 / 未暂存」的区别；
3. 在 detached HEAD 上提交后直接切分支，提交变成「孤儿」。

## 自测 3 题（含答案）

1. `M ` 和 ` M` 有什么区别？——**左列有 M 表示改动已进暂存区；右列有 M 表示工作区改了但没暂存。**
2. 新建分支为什么很快？——**只创建一个指向提交的引用文件，不复制对象与工作区。**
3. HEAD 和分支是什么关系？——**HEAD 通常指向某个分支引用，分支引用再指向提交；切换分支就是改 HEAD 的指向。**
