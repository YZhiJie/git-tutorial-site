# EP.06 线上回滚怎么选

> 对应正文：[guide/collaboration/06-revert-vs-reset.md](../guide/collaboration/06-revert-vs-reset.md)

## 剧情回顾

- **第 1 格**：错误提交已上线，实习生提议 `reset --hard` 再强推，标签君犹豫。
- **第 2 格**：码叔画出两条路：revert 新增反向提交，reset 把分支指针往回跳。
- **第 3 格**：像素酱搞清 `--soft`、`--mixed`、`--hard` 对暂存区和工作区的不同影响。
- **第 4 格**：结案——线上只 revert，本地未推送才 reset；回滚合并提交要写 `-m 1`。

## 知识点拆解

### 第 1 格 · 为什么不能强推

公共分支的历史已经被所有人拉取。`reset --hard` 加 `push --force` 会让远端历史变短，他人本地提交与远端失去共同祖先，下一次 pull 就是灾难。

### 第 2 格 · 加一笔与擦一笔

- **revert**：生成一个反向提交，抵消目标提交的改动，历史继续向前，可安全 pull；
- **reset**：移动当前分支指针，原提交被孤立，只适合尚未推送的本地历史；
- 两者不是「谁更高级」，而是适用场景不同。

### 第 3 格 · 三种 reset 模式

| 模式 | HEAD | 暂存区 | 工作区 |
| ---- | ---- | ---- | ---- |
| `--soft` | 移动 | 保留 | 保留 |
| `--mixed`（默认） | 移动 | 清空 | 保留 |
| `--hard` | 移动 | 清空 | 清空 |

```bash
$ git reset --soft HEAD~1   # 撤销提交，改动仍在暂存区
$ git reset HEAD~1          # 撤销提交与暂存，改动留在工作区
$ git reset --hard HEAD~1   # 提交与改动一起丢弃
```

### 第 4 格 · 线上回滚标准动作

```bash
$ git revert a1b2c3d
$ git revert -m 1 <merge-hash>
```

`-m 1` 表示保留合并提交的第一父提交（通常是主线）。回滚后照常走发布流程，不 force push。

## 坑点清单

1. 线上分支 `reset --hard` 后强推，导致同事本地历史断裂；
2. 回滚合并提交忘记 `-m 1`，Git 直接拒绝执行；
3. `reset --hard` 前没 stash，未提交改动永久丢失。

## 自测 3 题（含答案）

1. 为什么线上回滚要用 revert？——**它新增反向提交而不改写历史，所有协作者都能安全同步。**
2. `--soft` 和 `--mixed` 的关键差别？——**soft 保留暂存区内容；mixed 清空暂存区但保留工作区改动。**
3. 回滚合并提交为什么要 `-m 1`？——**合并提交有两个父，必须告诉 Git 以哪一边为主线来计算反向改动。**
