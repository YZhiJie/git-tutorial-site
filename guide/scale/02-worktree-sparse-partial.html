31 规模化检出：worktree、sparse checkout 与 partial clone ​

仓库变大以后，瓶颈很少是「Git 不会用」，而是「每次切分支都要重装依赖」「git status 要扫二十万个文件」「clone 要下 8 GB 历史」。Git 提供了三层互相独立的机制：

  • worktree：多个工作目录共享一个对象库，解决「同时开多个分支」。
  • sparse checkout：只把部分目录检出到工作区，解决「工作区太大」。
  • partial clone：只下载部分对象，按需补拉，解决「clone 太慢」。

三者可以叠加，但各自解决的问题不同。混为一谈会导致配置互相打架。

学习目标 ​

  • 用 git worktree 并行处理多条分支，理解它和 clone 的差别。
  • 用 cone mode 配置 sparse checkout，并知道 skip-worktree 位在做什么。
  • 用 blobless / treeless clone 降低首次克隆成本，理解 promisor 远程。
  • 判断一个场景该用哪一层，以及三层怎么组合。
  • 避开稀疏检出与构建工具、IDE、CI 的常见冲突。

worktree：一个对象库，多个工作区 ​

普通 git clone 会复制一份完整对象库。git worktree 不复制对象，只新建一个工作目录，并让它指向同一个 .git：

bash
# 在 main 上开一个热修目录
git worktree add ../app-hotfix main

# 基于已有分支开目录（不能是当前已检出的分支）
git worktree add ../app-review feature/login

# 新建分支并检出
git worktree add -b feature/export ../app-export main

# 查看所有工作树
git worktree list
# /repo            a1b2c3d [main]
# /app-hotfix      d4e5f6a [hotfix/urgent]
# /app-review      9a8b7c1 [feature/login]

# 用完删除（会检查是否有未提交改动）
git worktree remove ../app-hotfix

# 目录被手滑删了，清理元数据
git worktree prune

worktree 的典型用法 ​

场景做法
正在开发，线上要热修git worktree add ../hotfix main，修完直接删
同时 review 两个 PR每个 PR 一个 worktree，不用反复 stash
跑对照实验两个版本各一个目录，共享依赖缓存
生成文档 / 跑基准独立目录，避免污染主工作区
可移动磁盘上的仓库git worktree lock 防止路径失效后误删元数据

不能对同一分支开两个 worktree

git worktree add ../x main 在 main 已被当前目录检出时会报错。这是刻意的保护：两个工作区指向同一分支，提交会互相覆盖。需要并行就在新目录建新分支。

worktree 不解决的问题：磁盘占用还是 N 份工作文件，依赖目录（node_modules）也要各装一遍。这正是 sparse checkout 的用武之地。

sparse checkout：只检出需要的目录 ​

大 monorepo 里，你只改 packages/api，但工作区里有 packages/web、packages/mobile、docs、infra 共二十万个文件。sparse checkout 让 Git 只把这些路径写到磁盘，其余仍留在对象库里。

自 Git 2.25 起推荐 cone mode：只写目录，不写文件通配，性能好且行为可预测。

bash
# 开启（--cone 是默认值，建议显式写）
git sparse-checkout init --cone

# 设置要检出的顶层目录；根目录文件始终保留
git sparse-checkout set packages/api packages/shared

# 查看当前规则
git sparse-checkout list
# packages/api
# packages/shared

# 追加一个目录（set 是覆盖，add 是追加）
git sparse-checkout add packages/cli

# 临时关闭，恢复完整检出
git sparse-checkout disable

cone mode 的规则很简单：

  • set 里列的是目录，每个目录下的所有文件都会检出。
  • 仓库根目录下的文件（README.md、package.json、pnpm-workspace.yaml）始终保留。
  • 目录内的子目录默认递归包含。

需要按文件通配时，才用非 cone 模式（--no-cone + .git/info/sparse-checkout 写 pattern）。非 cone 模式要求 Git 逐个文件匹配，大仓库会明显变慢，且规则容易写错，除非确有需要否则别用。

与构建工具配合 ​

sparse checkout 会让工作区「看起来缺文件」。常见问题：

问题原因处理
pnpm install 报 workspace 包缺失被裁掉的包在 workspaces 里sparse-checkout add packages/<依赖>
IDE 索引报红语言服务器看不到被裁路径把 SDK / 索引范围也限制到已检出目录
git status 显示文件被删在非 cone 模式下手改规则git sparse-checkout reapply
Docker 构建上下文缺文件构建需要全量构建阶段用完整 clone，或显式 copy 依赖
修改 sparse 规则后文件没回来规则变了但没重新应用git sparse-checkout reapply

partial clone：按需下载对象 ​

partial clone 改变的是对象获取方式：克隆时不下载全部 blob（或全部 tree），只下载提交图和目录结构；需要某个文件内容时，再向 promisor 远程单独请求。

bash
# blobless：不下载文件内容，需要时再拉（最常用）
git clone --filter=blob:none git@github.com:org/big.git

# treeless：连 tree 也不下载，最省流量，但 log/diff 会频繁回源
git clone --filter=tree:0 git@github.com:org/big.git

# 限制单个 blob 大小
git clone --filter=blob:limit=1m git@github.com:org/big.git

克隆后查看配置，会看到：

bash
git config --get remote.origin.promisor   # true
git config --get remote.origin.partialclonefilter  # blob:none

对象库中有一个 pack-*.promisor 文件，标记「这些对象可能不在本地，需要时向远程要」。

blobless 与 treeless 怎么选 ​

方式不下载适合不适合
blob:none文件内容大多数开发场景、CI 构建需要大量 git log -p 的考古
tree:0tree + blob只关心提交元数据的分析正常开发、构建、IDE
blob:limit=1m超过阈值的大文件仓库里混有大二进制需要这些大文件的场景

日常开发推荐 blob:none：git log、git branch、git status 都能正常工作，只有真正读取文件内容时才回源。

三层怎么叠加 ​

它们解决不同维度，可以组合：

bash
# 只关心 api 包：blobless + 稀疏检出
git clone --filter=blob:none --sparse git@github.com:org/monorepo.git
cd monorepo
git sparse-checkout set packages/api packages/shared

效果：

  • 首次 clone 不下载任何文件内容（partial）。
  • 工作区只写 packages/api、packages/shared（sparse）。
  • 需要读某个未检出目录的文件时，Git 会按需拉 blob（promisor）。

再加 worktree 并行：

bash
git worktree add ../api-hotfix main

三个 worktree 共享同一份（本来就已经很小的）对象库。

维度机制省什么代价
并行分支worktree对象库副本工作文件仍 N 份
工作区大小sparse checkout磁盘文件数、IDE 索引构建工具可能缺依赖
网络与历史partial clone首次下载量按需回源延迟、离线受限

常见坑 ​

坑后果正确做法
对已检出分支再开 worktree命令报错新目录建新分支，或先切走
手动删 worktree 目录元数据残留，list 显示失效git worktree prune
在 worktree 里再 clone又复制一份对象库直接 worktree add
sparse 规则手改后不 reapply文件状态与规则不一致git sparse-checkout reapply
用非 cone 模式写复杂通配大仓库 status 极慢尽量用 cone mode 目录级规则
CI 用 partial clone 又跑全历史 blame大量回源，构建变慢甚至超时CI 用完整 clone，或加 --filter 后避免考古操作
服务器不支持 filterclone 直接报错确认平台与 Git 版本，降级为普通 clone

小结 ​

  • worktree 解决「同时开多个分支」，共享对象库，不共享工作区与 index。
  • sparse checkout 解决「工作区太大」，用 cone mode 按目录裁剪，靠 skip-worktree 位维持一致。
  • partial clone 解决「首次下载太大」，blobless 最常用，按需向 promisor 回源。
  • 三者可以叠加：--filter=blob:none --sparse + worktree，分别对应网络、磁盘、并行三个瓶颈。
  • 选择依据是瓶颈在哪一层，而不是「哪个更高级」。
