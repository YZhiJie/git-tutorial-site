30 CI 中的 Git：浅克隆、fetch-depth 与凭据 ​

CI 里的 Git 和本地不是同一个东西：默认浅克隆、detached HEAD、临时 workspace、只读 token。很多“本地明明能跑”的失败，根源都在检出方式。

学习目标 ​

  • 说清浅克隆会让哪些 Git 命令失效，以及为什么。
  • 根据任务选择 fetch-depth、tag、PR ref 的正确组合。
  • 正确配置凭据、权限与 submodule，避免“能读不能推”或权限过大。
  • 用 partial clone / sparse checkout / 缓存加速大仓库流水线。

默认检出到底做了什么 ​

actions/checkout 默认 fetch-depth: 1：只取目标 ref 的最新一个提交，历史被截断。

受影响的常见操作：

命令浅克隆下的表现
git describe --tags找不到 tag，报 No names found
git merge-base main HEAD找不到共同祖先，返回空或报错
git diff origin/main...HEAD三点 diff 失去基准
git log --follow历史被截断，追溯不完整
git blame只能看到末端提交
git bisect没有足够历史，无法二分

fetch-depth 怎么选 ​

任务建议
只跑 lint / 单元测试fetch-depth: 1 足够
需要 describe、tag、版本号fetch-tags: true，必要时 fetch-depth: 0
需要 merge-base diff显式 fetch 目标分支，或 fetch-depth: 2
发布 / 生成 changelogfetch-depth: 0
超大仓库partial clone + 按需 fetch，而不是全量
yaml
# 最小检出
- uses: actions/checkout@v4
  with:
    fetch-depth: 1
    persist-credentials: false

# 需要完整历史与 tag 的发布流水线
- uses: actions/checkout@v4
  with:
    fetch-depth: 0
    fetch-tags: true

PR 检出：你拿到的可能不是 head ​

GitHub Actions 在 PR 事件上默认检出 refs/pull/<n>/merge，也就是“合并后的结果”，而不是 PR 分支的 head。它处于 detached HEAD，并且是临时生成的合并提交。

yaml
# 需要基于 PR head 做推送或精确比较时
- uses: actions/checkout@v4
  with:
    ref: ${{ github.event.pull_request.head.sha }}

要推回分支时，先建临时分支：

bash
git switch -c ci/${{ github.run_id }}

凭据与权限 ​

  • persist-credentials: false：避免 token 被写进 .git/config，减少后续步骤误用。
  • 最小权限：默认 permissions: contents: read，需要发布时再单独提升。
  • safe.directory：在容器、挂载卷、UID 不一致的环境中，Git 会拒绝操作；用 git config --global --add safe.directory "$GITHUB_WORKSPACE" 显式放行。
  • 不要把长期 token 写进脚本或缓存；优先使用平台注入的短期凭据。

submodule 与加速 ​

yaml
- uses: actions/checkout@v4
  with:
    submodules: recursive
    token: ${{ secrets.SUBMODULE_TOKEN }}

大仓库三件套：

bash
git clone --filter=blob:none --sparse https://example.com/big.git
cd big && git sparse-checkout set packages/app
  • partial clone 延迟下载 blob，适合只需要部分目录的 CI。
  • sparse checkout 减少工作区文件数，但不会减少 Git 对象。
  • 缓存依赖（pnpm store、Maven、Gradle），不要缓存 .git 目录：refs、index、锁文件都可能导致脏状态。

常见坑 ​

坑表现正确做法
默认浅克隆跑 git describe版本号为空或报错fetch-tags: true 或 fetch-depth: 0
以为 PR 检出的是 head推送/比较对象错位显式 ref: head.sha
fetch-depth: 0 拖慢大仓库检出阶段占了大半时间partial clone + 按需 fetch
token 权限过大构建脚本可写仓库permissions 最小化
缓存整个 .git分支/索引状态过期只缓存依赖目录
私有 submodule 缺凭据checkout 卡住或 403传入专用 token

小结 ​

  • CI 的默认检出是浅克隆 + detached HEAD，依赖历史的命令必须显式补历史。
  • fetch-depth、fetch-tags、PR ref 要按任务选择，不要一律 0 或一律 1。
  • 凭据遵循最小权限，safe.directory 只在确有需要时放行。
  • 大仓库优先 partial clone + sparse checkout，缓存依赖而不是 .git。
