33 仓库体检与维护 ​

仓库变慢时，多数人第一反应是「Git 不行了」或「换台电脑」。实际上常见的三个原因是：

  • 松散对象太多，每次遍历都要打开成千上万个小文件。
  • 缺少 commit-graph，git log 要逐个解析提交对象。
  • 引用太多（几千个远端分支/标签），git fetch 与 status 的元数据开销变大。

这些都可以通过定期体检与维护解决。本章讲一套可执行的流程，而不是背一堆命令。

学习目标 ​

  • 用 count-objects、fsck、verify-pack 判断仓库健康度。
  • 理解 gc、repack、commit-graph、multi-pack-index 各自优化什么。
  • 配置后台自动维护，避免「等坏了再修」。
  • 安全地清理大对象与失效引用，不误删需要的历史。
  • 建立一套月度/季度体检清单。

先体检：四个命令看清现状 ​

bash
# 1. 对象数量与体积
git count-objects -vH
# count: 1240
# size: 8.20 MiB
# in-pack: 48213
# packs: 12
# size-pack: 310.42 MiB
# prune-packable: 0
# garbage: 0
# size-garbage: 0

# 2. 仓库完整性
git fsck --full
# 输出 dangling commit 通常无害；missing / corrupt 才是问题

# 3. 体积排行榜（找出最占空间的 pack）
ls -lh .git/objects/pack/*.pack | sort -k5 -h | tail -5

# 4. 引用数量
git for-each-ref --format='%(refname)' | awk -F/ '{print $2}' | sort | uniq -c

count-objects 的几个字段含义：

字段含义异常信号
count松散对象个数几万个说明很久没 gc
in-pack已打包对象数正常仓库主体应在这里
packspack 文件个数几十个说明 pack 碎片化
size-packpack 总大小持续增长但代码没变，可能有历史大文件
garbage无效临时文件大于 0 可 git gc --prune=now 清理

gc：一次把该做的都做了 ​

bash
# 日常维护（--auto 会按阈值判断是否需要）
git gc --auto

# 强制完整整理
git gc

# 连不可达对象一起清掉（危险：会删掉 reflog 之外的悬空提交）
git gc --prune=now --aggressive

git gc 会做几件事：

  1. 把松散对象打包成 pack。
  2. 合并已有 pack。
  3. 清理过期 reflog（默认 90 天）。
  4. 删除不可达对象（默认保留 2 周，给误操作留后路）。
  5. 更新 commit-graph 与 multi-pack-index（若已启用）。

commit-graph：让 log 与 rev-list 快一个数量级 ​

commit-graph 预先记录每个提交的父提交、根树、提交时间，git log 不必逐个解压提交对象：

bash
# 生成 / 更新
git commit-graph write --reachable --changed-paths

# 查看是否存在
ls .git/objects/info/commit-graph

# 让 fetch 后自动更新
git config --global fetch.writeCommitGraph true
git config --global gc.writeCommitGraph true

--changed-paths 会额外记录每个提交改动的路径，使 git log -- path 也变快，代价是文件更大。大仓库值得开，小仓库收益不明显。

multi-pack-index：pack 碎片化的解药 ​

频繁 fetch 会产生很多小 pack。multi-pack-index（MIDX）在所有 pack 之上建一张统一索引：

bash
git multi-pack-index write
git multi-pack-index verify

# 让 gc 顺带维护
git config --global gc.multiPackIndex true

开启后，git cat-file、git rev-list 不必逐个 pack 查找，pack 数量多时提升明显。

后台自动维护 ​

Git 2.31 起提供 git maintenance，可以注册系统级定时任务：

bash
# 查看当前策略
git maintenance run --task=gc --dry-run

# 注册每小时/每天的任务
git maintenance start

# 手动跑一轮
git maintenance run

# 停止
git maintenance stop

默认会调度 gc、commit-graph、prefetch 等任务。prefetch 会在后台预拉取远端对象，让 git fetch 更快，但会占用带宽，按需开启：

bash
git config --global maintenance.prefetch.enabled true

清理大对象与失效引用 ​

仓库体积异常时，先定位来源：

bash
# 找出历史中最大的 10 个对象（需要 rev-list 遍历，大仓库较慢）
git rev-list --objects --all \
  | git cat-file --batch-check='%(objecttype) %(objectname) %(objectsize) %(rest)' \
  | awk '$1=="blob" {print $3, $4}' \
  | sort -nr | head -10

如果确认是某个大文件，用第 29 章的 filter-repo 从历史中移除。不要只 git rm 当前版本，历史里仍占空间。

清理失效引用（远端已删除、本地还留着的分支）：

bash
# 删除远端已不存在的跟踪分支
git fetch --prune

# 预设每次 fetch 都 prune
git config --global fetch.prune true

# 清理已合并的本地分支
git branch --merged main | grep -v main | xargs -r git branch -d

reflog 是最后的后悔药

git gc --prune=now 会立刻删除不可达对象，reflog 里还能找回的提交会一并消失。除非你确认不需要任何悬空历史，否则用默认的 2 周保留期。

一份可执行的体检清单 ​

频率检查项命令处理
每周松散对象是否堆积git count-objects -vHgit gc --auto
每周远端分支是否残留git branch -vvgit fetch --prune
每月完整性git fsck --full修复损坏对象或从备份恢复
每月体积趋势du -sh .git增长异常时查大对象
每季度pack 数量git count-objects -vH 的 packsgit gc 合并
每季度索引是否最新是否存在 commit-graphgit commit-graph write --reachable
按需CI 克隆耗时流水线日志结合 partial clone / 浅克隆

常见坑 ​

坑后果正确做法
只 git rm 大文件仓库体积不降用 filter-repo 改写历史
gc --prune=now 当日常命令误删悬空提交，reflog 失效只在确认后使用
频繁 --aggressive每次耗时很长，收益递减默认 gc 即可，偶尔 aggressive
忽略 packs 数量fetch 越来越慢开 MIDX 或定期 gc
把 commit-graph 当必需文件误删后以为仓库损坏它是缓存，可重建
后台 prefetch 占满带宽办公网络卡顿按需开启或限制时间窗
在 CI 里每次全量 gc流水线变慢CI 用浅克隆 + partial clone，不做 gc

小结 ​

  • 先体检再动手：count-objects、fsck、pack 体积、引用数量。
  • gc 只改变存储形态，安全；--prune=now 才会提前删悬空对象。
  • commit-graph 加速 log / rev-list，multi-pack-index 解决 pack 碎片化。
  • 用 git maintenance start 把维护变成后台任务，而不是出问题才处理。
  • 体积异常先定位大对象，再用 filter-repo 从历史移除；只删当前文件没有用。
