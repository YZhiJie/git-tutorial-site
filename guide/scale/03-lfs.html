32 LFS 与大文件治理 ​

Git 是为文本设计的：它保存每个版本的完整快照，压缩算法擅长处理相似的文本。当仓库里混进设计稿、视频、模型权重、安装包时，问题会同时出现在三个地方：

  1. 对象库膨胀，克隆越来越慢。
  2. 每次改一个像素，仓库多一份完整副本。
  3. 平台对单文件大小和仓库体积有硬限制。

Git LFS（Large File Storage）把大文件内容搬到独立存储，仓库里只留一个几百字节的指针文件。它解决的是「版本控制系统里放二进制」这一结构性矛盾，而不是「用命令压缩一下」。

学习目标 ​

  • 说清 LFS 指针、smudge/clean filter 与 LFS 服务器之间的关系。
  • 正确配置 .gitattributes，让新文件从一开始就进 LFS。
  • 用 git lfs migrate 把历史大文件迁进 LFS，并理解它会改写历史。
  • 在 CI 里按需拉取 LFS 对象，或干脆跳过。
  • 判断什么该进 LFS，什么不该进版本库。

指针文件：仓库里到底存了什么 ​

执行 git lfs track "*.psd" 后，.gitattributes 里会多一行：

text
*.psd filter=lfs diff=lfs merge=lfs -text

之后提交一个 .psd 时，Git 通过 clean filter 把文件内容交给 LFS，仓库里写入的是一个指针文件，长这样：

text
version https://git-lfs.github.com/spec/v1
oid sha256:4d7a214614ab2935c943f9e0ff69d22eadbb8f32b1258daaa5e2ca24d17e2393
size 12345678

三行分别是协议版本、内容的 SHA-256、字节数。检出时，smudge filter 根据 oid 去 LFS 存储取回真实内容，写进工作区。

从零配置 LFS ​

bash
# 1. 安装（每台机器一次）
brew install git-lfs
git lfs install

# 2. 在仓库里声明要跟踪的类型
git lfs track "*.psd"
git lfs track "*.zip"
git lfs track "assets/models/**"

# 3. 提交 .gitattributes —— 这一步不能忘
git add .gitattributes
git commit -m "chore: 配置 LFS 跟踪大文件"

# 4. 查看当前规则
git lfs track
git lfs ls-files

.gitattributes 是规则的唯一来源。只在本机跑 git lfs track 而不提交 .gitattributes，同事克隆后不会生效，大文件仍会直接进 Git 对象库。

顺序很重要

git lfs track 必须在文件第一次提交之前执行。已经进过 Git 历史的文件，再加规则不会自动迁移，需要 git lfs migrate。

把历史大文件迁移进 LFS ​

假设仓库里已经躺着 300 MB 的 *.zip，想迁进 LFS：

bash
# 先备份
git clone --mirror git@github.com:org/app.git app-backup.git

# 预览：哪些文件会被迁移
git lfs migrate info --include="*.zip" --everything

# 执行迁移（会改写历史）
git lfs migrate import --include="*.zip" --everything

# 验证
git lfs ls-files | head
git count-objects -vH

--everything 表示扫描所有 ref（分支、标签）。常用变体：

参数作用
--include="*.psd"只迁移匹配的文件
--exclude="fixtures/**"排除某些路径
--everything覆盖所有分支与标签
--no-rewrite不改历史，只把当前快照转成指针（新仓库适用）

迁移会重写历史，后续必须 git push --force 所有分支和标签，并通知全员重新克隆。协作成本与第 29 章的历史重写完全一样。

日常使用 ​

bash
# 拉取 LFS 对象（clone 后通常自动执行）
git lfs pull

# 只拉某个路径
git lfs pull --include="assets/models/**"

# 查看状态：哪些对象没下载
git lfs status

# 查看 LFS 服务的对象列表
git lfs ls-files

# 锁定文件，避免多人同时改二进制
git lfs lock design/main.psd
git lfs locks
git lfs unlock design/main.psd

文件锁是 LFS 相对普通 Git 的一个实用能力：二进制文件无法合并，与其让两个人改完再冲突，不如先锁住。

CI 中的 LFS ​

GitHub Actions 的 actions/checkout 默认不拉取 LFS 内容：

yaml
- uses: actions/checkout@v4
  with:
    lfs: true          # 需要大文件时才开
    fetch-depth: 1

如果构建不需要这些大文件（例如只跑单元测试），保持 lfs: false 可以显著缩短流水线：

yaml
# 只拉指针，跳过内容
- uses: actions/checkout@v4
  with:
    lfs: false

需要部分文件时，在 checkout 后用：

bash
git lfs pull --include="assets/fonts/**"

什么该进 LFS，什么不该进版本库 ​

类型建议理由
设计源文件（psd、ai、fig）LFS单文件大、二进制、需要版本历史
视频、音频素材LFS 或对象存储体积大，更新频繁时 LFS 配额压力大
模型权重、数据集LFS + 锁，或独立制品库单文件常达 GB 级，CI 拉取成本高
依赖安装包（jar、whl）制品库，不进 Git可复现构建不应依赖仓库内二进制
构建产物（dist、build）不进 Git可由源码重建
小图标、小字体（< 100 KB）普通 GitLFS 有额外请求成本，小文件不划算
需要 diff / merge 的文本普通 GitLFS 文件无法逐行 diff

经验阈值：单个文件稳定超过 1 MB、且改版不频繁，考虑 LFS；超过 100 MB 的平台硬限制，必须 LFS 或外部存储。

常见坑 ​

坑后果正确做法
忘提交 .gitattributes同事克隆后规则不生效跟踪规则后立刻提交该文件
文件已提交后才 track旧版本仍在 Git 历史里用 git lfs migrate import
迁移后普通 push远端拒绝或历史不一致push --force 全部 ref
迁移后没通知团队同事本地历史与远端分叉提前公告，要求重新克隆
CI 开 lfs: true 但构建不需要流水线变慢、消耗带宽按需拉取或关闭
把 dist/ 也 track 进 LFS配额被构建产物吃掉构建产物不进版本库
多人同时改二进制无法合并，只能二选一用 git lfs lock
以为 LFS 能去重所有历史内容变了就是新对象仅相同内容去重，改版仍占空间

小结 ​

  • LFS 把大文件内容搬到独立存储，Git 里只留指针；指针与内容通过 oid 对齐。
  • .gitattributes 是规则的唯一来源，必须提交；track 要在文件首次提交前执行。
  • 已进历史的大文件用 git lfs migrate import 迁移，代价是改写历史 + 全员重新克隆。
  • CI 中按构建是否真的需要内容来决定拉取范围，不要无脑 lfs: true。
  • 大文件治理的核心不是「用 LFS」，而是先判断这个文件该不该进版本库。
