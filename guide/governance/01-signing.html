34 提交与标签签名 ​

签名解决的是“这个提交确实由某个密钥持有者创建，且内容没有被改过”，而不是“代码没有 bug”。它把 Git 的身份从“配置里随便填的邮箱”升级为“可验证的密钥”，是发布与供应链治理的基础设施。

学习目标 ​

  • 说清签名在对象层面改了什么，以及验证时到底校验什么。
  • 掌握 GPG 与 SSH 两条签名路线，能各自跑通提交和标签签名。
  • 能设计团队级签名策略：谁能签、签什么、在哪里强制校验。
  • 知道签名不能替代权限控制、代码审查和密钥轮换。

签名写进了对象本身 ​

Git 的提交对象里有一个可选的 gpgsig 头。执行 git commit -S 时，Git 会先算出提交对象的内容，再用私钥对它签名，把签名结果写进 gpgsig 头。验证时，验签者用公钥重算并校验这段内容。

因此：

  • 签名是对象内容的一部分，不是仓库外的附件。
  • amend、rebase、cherry-pick 都会生成新对象，旧签名不会自动跟过去。
  • 改一个字符，提交哈希和签名都会失效。

路线一：GPG 签名 ​

bash
# 1. 生成密钥（按提示选择算法与有效期）
gpg --full-generate-key
gpg --list-secret-keys --keyid-format=long

# 2. 告诉 Git 用哪把密钥
git config --global user.signingkey <KEY_ID>
git config --global commit.gpgsign true
git config --global tag.gpgSign true

# 3. 签名提交与标签
git commit -S -m "feat: 增加导出"
git tag -s v1.2.0 -m "release 1.2.0"

# 4. 验证
git verify-commit HEAD
git verify-tag v1.2.0
git log --show-signature -3

GPG 的痛点很实际：密钥管理、pinentry、CI 中无交互环境、跨平台差异。团队里最常见的失败不是“签名算法错”，而是“邮箱与密钥 UID 不一致，平台不给 Verified”。

路线二：SSH 签名（更轻） ​

Git 2.34+ 支持用 SSH 密钥签名。它复用你已经在用的 SSH key，不需要额外维护 GPG 密钥环：

bash
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true

# allowed_signers 用于本地验证
cat >> ~/.config/git/allowed_signers <<'EOF'
zhangsan@example.com ssh-ed25519 AAAAC3Nza...
EOF
git config --global gpg.ssh.allowedSignersFile ~/.config/git/allowed_signers

git verify-commit HEAD

allowed_signers 的每一行是“主体 + 公钥”，主体通常写邮箱，必须与提交里的作者邮箱匹配，否则验证会失败。

平台验证与团队策略 ​

  • GitHub / GitLab 会把签名与账号上传的公钥匹配，匹配成功才显示 Verified。
  • 发布标签建议强制签名：标签是制品入口，比普通提交更值得保护。
  • 保护分支可以要求 signed commits；但管理员绕过、机器人账号、CI 提交都要单独规划。
  • 密钥轮换：新密钥上线后，旧密钥保留一段时间用于验证历史签名，再吊销。
  • CI 不应保存长期私钥。优先使用平台 OIDC / 短期令牌；必须用 GPG 时，把密钥放进 secret 并限制 job 权限。

常见坑 ​

坑表现正确做法
邮箱与密钥 UID 不一致本地 verify-commit 通过，平台不显示 Verified统一 user.email 与密钥主体
CI 里 GPG pinentry 卡住构建一直等待输入密码使用无交互密钥或改用 SSH 签名
amend 后签名丢失旧提交签名失效、新提交未签开启 commit.gpgsign，amend 后重新签
SSH 签名没配 allowed_signersverify-commit 报 “no principal matched”写入正确邮箱与公钥
把私钥提交进仓库密钥泄露，历史里永久存在立即吊销并轮换，按历史重写流程清理
密钥过期后不换新提交无法签名，旧签名验证失败设置提醒与轮换流程

小结 ​

  • 签名写入提交/标签对象本身，验证的是“内容未被改 + 密钥持有者确认”。
  • GPG 生态成熟但运维重；SSH 签名复用现有密钥，更适合日常开发。
  • 签名只有叠加平台验证、保护分支和发布策略，才从个人习惯变成团队约束。
  • 签名不替代权限、审查与测试；私钥泄露要按安全事件处理。
