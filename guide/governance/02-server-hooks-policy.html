35 服务端 hooks 与分支治理 ​

客户端 hooks 有个根本缺陷：它可以被绕过。git commit --no-verify、换一台机器、网页上传、换客户端，都能跳过。真正需要「谁都别想违反」的规则，必须放在服务端。

服务端 hooks 运行在接收推送的裸仓库里，推送在更新引用之前先过一遍脚本。本章讲三个服务端钩子的执行顺序、各自能拦什么，以及它们与平台分支保护、CI 检查如何组合。

学习目标 ​

  • 分清 pre-receive、update、post-receive 的执行时机与能力边界。
  • 用 pre-receive 实现禁止强推、要求签名、拦截大文件、校验提交信息。
  • 理解托管平台上服务端 hooks 的可用性限制。
  • 把 hooks 与分支保护、CODEOWNERS、必需检查组合成完整治理方案。
  • 判断哪些规则该写脚本，哪些该交给平台。

三个钩子的位置 ​

text
git push
   │
   ├─ 客户端 pre-push（可被 --no-verify 跳过）
   ▼
服务端裸仓库
   │
   ├─ pre-receive    整批推送一次；可整体拒绝
   ├─ update         每个 ref 一次；可单独拒绝某个分支
   └─ post-receive   全部接受后；做通知/部署，失败不影响结果
钩子触发次数输入能否拒绝典型用途
pre-receive每次 push 一次全部 old new ref 行是，整批全局策略：签名、大小、路径
update每个 ref 一次单个 ref 的 old/new是，单个 ref分支级规则：谁能推 main
post-receive接受后一次已接受的 ref 列表否通知、部署、镜像同步

pre-receive 与 update 从标准输入读取：

text
<old-sha> <new-sha> <ref-name>

删除分支时 new-sha 是全零；新建时 old-sha 是全零。用这个特征就能区分新增、更新、删除。

pre-receive：整批策略 ​

pre-receive 最适合做「一次推送里所有 ref 都必须满足」的规则。下面是一个可用的最小实现：

bash
#!/usr/bin/env bash
# hooks/pre-receive
set -euo pipefail

ZERO=0000000000000000000000000000000000000000
PROTECTED="refs/heads/main refs/heads/release"
MAX_BLOB=$((20 * 1024 * 1024))   # 单文件 20 MB

fail() { echo "ERROR: $*" >&2; exit 1; }

while read -r old new ref; do
  # 1. 保护分支禁止删除
  if [ "$new" = "$ZERO" ]; then
    case " $PROTECTED " in
      *" $ref "*) fail "禁止删除保护分支: $ref" ;;
    esac
    continue
  fi

  # 2. 保护分支禁止强推（非快进）
  case " $PROTECTED " in
    *" $ref "*)
      if [ "$old" != "$ZERO" ] && ! git merge-base --is-ancestor "$old" "$new"; then
        fail "禁止对 $ref 强推；请走 PR 合并"
      fi
      ;;
  esac

  # 3. 新增提交必须签名
  if [ "$old" = "$ZERO" ]; then
    range="$new --not --all"
  else
    range="$old..$new"
  fi
  for c in $(git rev-list "$range"); do
    git verify-commit "$c" >/dev/null 2>&1 || fail "提交 $c 未签名或签名无效"
  done

  # 4. 单文件大小限制
  for c in $(git rev-list "$range"); do
    while read -r _sha size path; do
      [ "$size" -le "$MAX_BLOB" ] || fail "文件过大: $path ($size bytes) 于 $c"
    done < <(git ls-tree -r -l "$c")
  done
done

exit 0

要点：

  • set -euo pipefail 防止脚本静默失败后放行。
  • 错误信息写到 stderr，客户端能看到。
  • 用 merge-base --is-ancestor 判断是否快进，而不是比较提交时间。
  • 遍历提交用 rev-list，但大仓库上要限制范围，否则每次 push 都扫全历史。

钩子要快

pre-receive 里对每个提交跑 rev-list、ls-tree、verify-commit，在 monorepo 上可能几十秒。规则越多，越要控制扫描范围（只查 old..new），必要时把重活交给 CI。

update：分支级规则 ​

update 每个 ref 调用一次，参数是 ref 名与 old/new：

bash
#!/usr/bin/env bash
# hooks/update
ref="$1"; old="$2"; new="$3"

# 只允许特定人推 release 分支
if [ "$ref" = "refs/heads/release" ]; then
  user="${GL_USERNAME:-${REMOTE_USER:-unknown}}"
  case "$user" in
    release-bot|zhangsan) ;;
    *) echo "ERROR: $user 无权推送 release" >&2; exit 1 ;;
  esac
fi

# 分支命名规范
case "$ref" in
  refs/heads/*)
    branch="${ref#refs/heads/}"
    echo "$branch" | grep -Eq '^(feature|fix|chore|release)/[a-z0-9._-]+$' \
      || { echo "ERROR: 分支名不合规: $branch" >&2; exit 1; }
    ;;
esac

update 的优点是拒绝粒度细：一批推送里可以只拒一个分支，其余照常接受。

post-receive：只做副作用 ​

bash
#!/usr/bin/env bash
# hooks/post-receive
while read -r old new ref; do
  echo "更新 $ref: $old -> $new"
done

# 触发部署或通知（用 nohup 避免阻塞 push）
nohup /srv/deploy/notify.sh >/var/log/git-notify.log 2>&1 &
exit 0

post-receive 的返回值不影响推送结果。它适合通知、镜像同步、触发构建，不适合做校验——校验必须放在前两个钩子里。

裸仓库里怎么装 ​

bash
# 服务端仓库通常是 bare
git init --bare /srv/git/app.git

# 放入钩子并加执行权限
cp pre-receive /srv/git/app.git/hooks/pre-receive
chmod +x /srv/git/app.git/hooks/pre-receive

# 确认 core.hooksPath 没有被改到别处
git --git-dir=/srv/git/app.git config --get core.hooksPath

若用 core.hooksPath 统一管理：

bash
git --git-dir=/srv/git/app.git config core.hooksPath /srv/git/hooks

托管平台的限制 ​

GitHub、GitLab、Gitee 等托管服务不让你直接改服务端 hooks。对应能力是：

需求GitHubGitLab
禁止强推 / 删除保护分支Branch protection / RulesetsProtected branches
要求签名Rulesets 的「Require signed commits」Push rules
提交信息格式无原生支持，靠 CIPush rules 的正则
单文件大小无原生支持，靠 CI 或 LFSPush rules 的文件大小限制
必需检查Required status checksMerge request approvals + pipelines
代码所有者CODEOWNERSCODEOWNERS

自建 GitLab 可以启用 server hooks（/var/opt/gitlab/git-data/repositories/.../custom_hooks/），能力接近原生 pre-receive。GitHub Enterprise Server 也有 pre-receive hooks；GitHub.com 没有。

分支治理的最小组合 ​

一个可落地的方案：

  1. 保护 main：禁止直接推送、禁止强推、禁止删除。
  2. 必须 PR：至少 1 个审批，CODEOWNERS 覆盖核心目录。
  3. 必需检查：单测、lint、类型检查、构建。
  4. 签名策略：主线要求签名，平台开启「Require signed commits」。
  5. 提交信息规范：CI 用 commitlint 校验（平台无原生能力时）。
  6. 大文件：pre-commit 提示 + CI 拦截 + LFS 规则。
  7. 分支命名：CI 或平台 push rule 校验。

这套组合里，只有第 6 条的「提交前提示」用客户端钩子，其余都在服务端或平台层。

常见坑 ​

坑后果正确做法
钩子没加执行权限完全不生效，且无报错chmod +x hooks/*
脚本没有 set -e中间命令失败仍放行set -euo pipefail
在 post-receive 里做校验拒绝无效，引用已更新校验放 pre-receive / update
每次 push 扫全历史大仓库推送极慢只扫 old..new
把 core.hooksPath 指错钩子静默不执行显式 config --get 确认
依赖 --no-verify 能防住客户端钩子本就不可靠强制规则放服务端/平台
钩子里调用需要交互的命令服务端无 TTY，卡死全部非交互，加超时
忘了托管平台不支持自定义钩子方案落不了地用 rulesets / push rules / CI 替代

小结 ​

  • pre-receive 整批校验、update 逐 ref 校验、post-receive 只做副作用。
  • 服务端钩子拦的是「引用更新」，对象已先传输；被拒对象稍后被清理。
  • 自建仓库可以直接装钩子；托管平台要用分支保护、rulesets、push rules、CI 替代。
  • 规则分层：客户端提醒、服务端/平台强制、CI 验证；只有客户端层的规则等于没有。
  • 最小治理组合 = 保护分支 + 必须 PR + 必需检查 + 签名 + 提交规范 + 大文件拦截。
