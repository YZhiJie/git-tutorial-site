26 引用体系与 revision 语法 ​

引用（ref）是 Git 里唯一“可变”的东西：它只是一个指向对象哈希的指针。分支、标签、远程跟踪分支、HEAD，全部是引用。理解引用的命名空间与 revision 语法，才能看懂 HEAD~2^2@{u} 到底在说什么。

学习目标 ​

  • 说清 loose ref、packed-refs、HEAD 的存储方式。
  • 区分 symbolic ref、detached HEAD 与普通分支引用。
  • 独立解析 ~、^、@{n}、@{u}、..、... 等表达式。
  • 知道短哈希、上游引用和 reflog 引用各自的边界。

引用就是一个哈希指针 ​

bash
cat .git/refs/heads/main            # 一个 40 位哈希
git rev-parse main                  # 同样的事情，通过 Git 解析
git symbolic-ref HEAD               # refs/heads/main
git show-ref                        # 列出所有 ref

引用分布在不同的命名空间里：

命名空间内容例子
refs/heads/*本地分支refs/heads/main
refs/tags/*标签refs/tags/v1.0
refs/remotes/*远程跟踪分支refs/remotes/origin/main
refs/notes/*注释refs/notes/commits
refs/stashstash 栈顶refs/stash
refs/replace/*对象替换refs/replace/<hash>

HEAD：符号引用与 detached HEAD ​

正常状态下：

text
HEAD -> refs/heads/main -> a1b2c3d

HEAD 存的是 ref: refs/heads/main，这叫 symbolic ref。切分支就是改这一行。

执行 git switch --detach a1b2c3d 后，HEAD 直接存哈希，不再经过分支。此时提交会创建新对象，但没有分支指向它；一旦切换走，只能靠 reflog 找回。

bash
git switch --detach HEAD~3
git switch -c rescue-branch       # 在 detached HEAD 上建分支，把提交接住

revision 语法：把“图上的位置”写成表达式 ​

表达式解析结果说明
HEAD / @M当前提交
HEAD^1Emerge 的第一个父提交（主line）
HEAD^2Gmerge 的第二个父提交（被合入分支）
HEAD~1E等价于 ^1
HEAD~2D先到 E，再沿第一父提交到 D
mainE本地分支引用
origin/mainE（或更远）远程跟踪引用，取决于最近一次 fetch
feature@{1}Gfeature 上一次移动前的位置（reflog）
@{u}origin/feature当前分支的上游
@{push}推送目标与 @{u} 不一定相同
@{-1}上一个分支类似 cd -
HEAD^{tree}tree 对象从 commit 解引用到树
HEAD:README.mdblob 对象读取该提交里的文件
:/fix bug提交按提交信息正则查找
main..featureF、G、Mfeature 可达、main 不可达
main...featureD、E、F、G、M两侧对称差

查看与修改引用 ​

bash
git show-ref --heads                 # 只看本地分支
git for-each-ref --format='%(refname:short) %(objectname:short)' refs/heads
git rev-parse --abbrev-ref HEAD      # 当前分支名（detached 时是 HEAD）
git rev-parse HEAD^{tree}            # 解引用到 tree
git update-ref refs/heads/tmp <hash> # 安全地移动引用
git symbolic-ref HEAD refs/heads/main

packed-refs 与短哈希 ​

引用多起来后，Git 会把它们压缩进 .git/packed-refs：

bash
git pack-refs --all
cat .git/packed-refs

松散引用和 packed 引用可以同时存在；同名时以松散引用为准。不要手工编辑 .git/packed-refs，用 update-ref。

短哈希（如 a1b2c3d）只是前缀匹配。在大仓库里可能不唯一：

bash
git rev-parse --disambiguate=a1b2c3d

脚本里应使用完整哈希，或至少处理歧义报错。

常见坑 ​

坑表现正确做法
把 @{1} 当固定提交新操作后指向漂移记下绝对哈希，或先建备份分支
在 detached HEAD 上直接提交切走后提交“消失”先 git switch -c 接住
@{u} 报错分支没有 upstream先 git branch -u origin/xxx
~ 与 ^ 混用解析到意外提交记住 ~ 走第一父，^n 选父
短哈希写进脚本偶发歧义/找不到用完整哈希
手改 packed-refs引用损坏或不同步用 update-ref / pack-refs

小结 ​

  • 引用是哈希指针；HEAD 通常再指向分支引用，detached 时直接指向提交。
  • ~n 沿第一父提交回溯，^n 选择第 n 个父提交，只有 merge 才有 ^2。
  • @{n} 读 reflog，@{u} 读上游配置，二者都不是提交图上的固定位置。
  • .. 是可达差集，... 是对称差；理解图结构比背符号更重要。
