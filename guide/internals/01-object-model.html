25 对象模型：Git 到底存了什么 ​

很多 Git 的“怪行为”，追到根上都是同一件事：Git 不是按文件保存差异，而是把内容存成不可变对象，再让引用指向这些对象。理解这套模型，reflog 为什么能救命、rebase 为什么会让哈希全变、重命名为什么不算新文件，都能直接推导出来。

学习目标 ​

  • 说清 blob、tree、commit、tag 四种对象的字段与职责。
  • 用 hash-object、mktree、commit-tree 手工造出一个提交。
  • 解释为什么同一份文件内容在多个提交里只存一份。
  • 区分 loose object、packfile 与 reflog 可达性。

一个仓库只有两样核心东西 ​

Git 仓库可以粗暴地切成两半：

部分位置特性
对象库.git/objects不可变，按内容哈希寻址
引用.git/refs、.git/HEAD可变，本质是可移动的哈希指针

其余的 index、config、hooks 都是围绕这两半工作的辅助设施。

四种对象 ​

类型存什么关键点
blob文件的原始字节不存文件名、不存权限、不存路径
tree一层目录清单每项包含 mode、类型、哈希、文件名
commit一个 tree、零到多个 parent、作者/提交者、时间、说明指向的是一整棵快照，不是 diff
tag指向另一个对象，附带标签名、打标签者、说明轻量标签只是 ref，附注标签才产生 tag 对象

用 git cat-file 可以直接看对象的原始内容：

bash
git cat-file -t HEAD          # commit
git cat-file -s HEAD          # 对象大小（字节）
git cat-file -p HEAD          # 提交对象的结构
git cat-file -p HEAD^{tree}   # 根目录树
git cat-file -p HEAD:src/app.ts

一个提交对象长这样：

text
tree 4b825dc642cb6eb9a060e54bf8d69288fbee4904
parent 9f8e7d6...
author 张三 <zhangsan@example.com> 1760000000 +0800
committer 张三 <zhangsan@example.com> 1760000000 +0800

feat: 增加订单导出

tree 的每一行则是：

text
100644 blob 4f2a1c9...    README.md
100755 blob 8c1d3e4...    scripts/build.sh
040000 tree 71e9b2a...    src

040000 是目录，100644 是普通文件，100755 是可执行文件。权限和文件名属于 tree，不属于 blob。

快照，不是差异 ​

这是 Git 与 SVN 一类系统最大的认知差异：commit 指向的 tree 是一棵完整快照。git show、git diff 里的差异，是命令临时比较两棵树算出来的，不是仓库里存了一份 patch。

由此可以推出几个常见结论：

  • 重命名不会产生新 blob：文件名在 tree 里变，内容哈希不变。
  • rebase 会改哈希：父提交变了，commit 对象的内容就变了，哈希必然重算。
  • 空目录不会被跟踪：Git 只存 blob 和 tree，而空目录没有可提交的条目。
  • 同一个文件在多个分支上只存一份：只要内容相同，blob 哈希就相同。

哈希是怎么算出来的 ​

对象哈希不是随机 ID，而是对「类型 + 大小 + 内容」做哈希：

text
hash = SHA-1("blob 10\0hello git\n")

写入后按前两位分目录存放：

text
.git/objects/8d/0e4123...

手工造一个提交 ​

理解了字段，就可以不用 git add / git commit，直接从底层拼一个提交出来：

bash
mkdir object-demo && cd object-demo && git init -q

# 1. 写入 blob，得到哈希
blob=$(printf 'hello git\n' | git hash-object -w --stdin)

# 2. 用 blob 组一个 tree
tree=$(printf '100644 blob %s\tgreeting.txt\n' "$blob" | git mktree)

# 3. 用 tree 组一个 commit
commit=$(printf 'first commit\n' | git commit-tree "$tree")

# 4. 让 main 和 HEAD 指向它
git update-ref refs/heads/main "$commit"
git symbolic-ref HEAD refs/heads/main
git reset --hard main

git log --oneline --stat
git cat-file -p HEAD

这套流程就是 git commit 的内部骨架：写 blob → 组 tree → 写 commit → 移动引用。git add 负责前两步并更新 index，git commit 负责后两步。

对象可达性与“丢失” ​

对象是否会被垃圾回收，只看它还能不能从某个根（ref、HEAD、reflog、stash 等）走得到：

  • 分支删除、reset --hard、rebase 之后，旧提交只是不可达，通常还在磁盘上。
  • git fsck --lost-found 可以列出 dangling commit。
  • git gc --prune=now 才会真正删除不可达对象。

这就是 reflog 能救回误操作的底层原因：它保留了一条指向旧提交的引用轨迹。反过来，从未 add 的工作区内容根本没有对象，reflog 也救不了。

SHA-256 与哈希碰撞 ​

Git 默认仍使用 SHA-1，但支持 SHA-256 仓库：

bash
git init --object-format=sha256 sha256-demo

SHA-256 仓库与 SHA-1 仓库目前不能直接互相 fetch/push，生态兼容性有限。日常更值得关注的是：哈希碰撞不是“改一个文件”，而是构造出内容不同、哈希相同的对象，实际攻击成本极高，但也不应把哈希当作安全边界。真正的权限控制要靠签名与分支保护，见 提交与标签签名。

常见坑 ​

坑表现正确理解
以为 commit 存的是 diff想从对象里直接取 patchcommit 存快照，diff 是命令现算的
以为重命名会产生新 blob历史里看不到“重命名对象”变的是 tree 条目，blob 哈希不变
直接改 .git/objects 文件仓库损坏、哈希校验失败用 hash-object / mktree 等命令写入
以为删分支就删了提交实际上还能 fsck 找到删除只是去掉引用，对象仍在
救援时执行 gc --prune=now目标对象被彻底清掉救援期间不要 prune
把短哈希当唯一 ID大仓库里短哈希可能不唯一冲突时加长，脚本里用完整哈希

小结 ​

  • Git 的核心是「不可变对象库 + 可变引用」，commit 指向完整快照而不是 diff。
  • blob 存内容，tree 存文件名与权限，commit 存快照、父提交与元信息，tag 存附注标签。
  • 相同内容哈希相同，因此跨提交、跨分支自动去重；rebase/amend 改父提交就会改所有后代哈希。
  • 对象是否会被回收取决于可达性，reflog 正是可达性的一条重要根。
  • 掌握底层命令后，add / commit / reset 都只是对「写对象 + 移引用」的封装。
