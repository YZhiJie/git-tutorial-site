27 索引与三棵树 ​

git add、git commit、git reset、git checkout 看起来是四个命令，本质上都在移动三棵树：HEAD、索引（index）和工作区。把这三棵树想清楚，冲突、撤销、暂存这些事就不会再靠背命令。

学习目标 ​

  • 说清 HEAD、index、工作区的职责与它们保存的内容。
  • 能判断 git diff、git diff --cached、git diff HEAD 各自比较哪两棵树。
  • 理解冲突时 index 里的 stage 1/2/3，以及 git add 如何折叠冲突。
  • 区分 assume-unchanged 与 skip-worktree，用对场景。

三棵树是什么 ​

树位置存什么可变性
HEAD.git/HEAD → 当前提交上一次提交的完整快照随 commit/reset 移动
index.git/index下一次提交的候选快照 + stat 缓存随 add/rm/reset 变化
工作区仓库目录（不含 .git）你正在编辑的真实文件随编辑器变化

index 里到底有什么 ​

.git/index 不是简单文件列表，每个条目至少包含：

  • 路径（path）；
  • 文件 mode（100644 / 100755 / 120000 符号链接等）；
  • blob 哈希；
  • stage（0 表示正常，1/2/3 表示冲突三方）；
  • stat 缓存（mtime、size、inode 等），用来快速判断文件是否变化。
bash
git ls-files --stage
# 100644 8d0e4123... 0   README.md
# 100644 4f2a1c9...  0   src/app.ts

git ls-files --debug README.md   # 看 stat 缓存

git status 之所以快，一部分靠 stat 缓存：文件元信息没变就跳过内容比较。反过来，touch 一个文件即使内容没变，也可能让 Git 重新读它。

冲突时 index 变成三阶段 ​

正常条目只有 stage 0。发生内容冲突时，同一个路径会同时存在：

stage来源含义
1base共同祖先里的版本
2ours当前分支（HEAD）的版本
3theirs被合入分支的版本

可复现实验：

bash
git switch -c conflict-demo
printf 'port: 8080\n' > config.yml
git add config.yml && git commit -m "base"

git switch -c ours
printf 'port: 9090\n' > config.yml
git commit -am "ours"

git switch -c theirs main
printf 'port: 8443\n' > config.yml
git commit -am "theirs"

git switch ours
git merge theirs            # 冲突
git ls-files -u             # stage 1/2/3
git checkout --ours config.yml   # 取 ours 版本
git add config.yml               # 折叠为 stage 0

assume-unchanged 与 skip-worktree ​

两者都让 Git “少管”某个文件，但语义完全不同：

选项语义适用场景风险
assume-unchanged我保证不改它，别再检查提升大仓库 status 速度你真改了，Git 可能不提示
skip-worktree这个文件在工作区被有意跳过sparse checkout、本地配置覆盖pull 时可能保留本地版本
bash
git update-index --assume-unchanged config/local.yml
git update-index --no-assume-unchanged config/local.yml

git update-index --skip-worktree config/local.yml
git update-index --no-skip-worktree config/local.yml

不要把 assume-unchanged 当成 .gitignore 使用；它不会阻止文件被提交，也不会阻止别人修改。

intent-to-add 与拆分索引 ​

bash
git add -N src/new-file.ts     # 只登记“意图”，不暂存内容
git diff                       # 能看到新文件的完整 diff

-N 适合在提交前先看新文件差异，或配合交互式暂存。超大仓库还可以了解 split index（git update-index --split-index）与 sparse index，它们主要优化 index 的读写性能，不改变三棵树的语义。

常见坑 ​

坑表现正确做法
以为 git add -A 只加当前目录把无关文件也暂存用明确路径，先 git status
用 assume-unchanged 忽略配置文件仍被提交、协作方互相覆盖用 .gitignore 或模板
index.lock 残留所有命令报 “index.lock exists”确认无进程后删除锁文件
restore --staged 与 reset 混用以为撤销了工作区--staged 只动 index
CRLF 导致“没改却脏”status 一直显示修改统一 .gitattributes 与 core.autocrlf
冲突后直接 commit提交里带着冲突标记先解决、git add、再 commit

小结 ​

  • HEAD、index、工作区是三棵可移动的树；命令只是搬运它们的数据。
  • index 保存候选快照与 stat 缓存，冲突时同一路径出现 stage 1/2/3。
  • git add 把冲突三阶段折叠成 stage 0；这是“解决冲突”的机械定义。
  • assume-unchanged 是性能承诺，skip-worktree 是稀疏检出语义，不能互换。
  • 理解三棵树后，reset/restore/checkout 的差异不再需要死记。
