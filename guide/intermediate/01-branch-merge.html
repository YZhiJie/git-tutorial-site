06 分支合并与快进 ​

学习目标 ​

  • 能判断一次合并会走快进（fast-forward）还是三方合并（three-way merge）。
  • 能用 ASCII 图画出两种合并后的提交图差异。
  • 能使用 git merge、git merge --no-ff 并按团队策略选择合并方式。
  • 能解释合并提交为什么有两个父提交，并用 git cat-file -p 验证。
  • 能在合并完成后安全删除分支，并用 git log --graph 检查结果。

合并的两种形态 ​

git merge <branch> 把指定分支的变更并入当前分支。设当前在 main，要合并 feature/login，结果取决于两条分支是否已经分叉：

条件合并方式是否产生合并提交
main 是 feature 的祖先（feature 只是领先）快进（fast-forward）否，只移动指针
两条分支各自有新提交三方合并（three-way merge）是，两个父提交

判断是否分叉：

bash
git log --oneline --graph --decorate --all
# * 4c5d6e7 (feature/login) feat: 登录页面
# * 3b4c5d6 feat: 登录接口
# * 2a9c7f1 (HEAD -> main) chore: 初始化项目

此时 main 停在 2a9c7f1，没有新提交，合并会快进。

快进合并 ​

bash
git switch main
git merge feature/login
# Updating 2a9c7f1..4c5d6e7
# Fast-forward
#  src/login.ts | 42 ++++++++++++++++++++++++++++++++++++++++++++
#  1 file changed, 42 insertions(+)

合并前后：

text
合并前：
* 4c5d6e7 feat: 登录页面      ← feature/login
* 3b4c5d6 feat: 登录接口
* 2a9c7f1 chore: 初始化项目    ← HEAD -> main

合并后：
* 4c5d6e7 feat: 登录页面      ← HEAD -> main, feature/login
* 3b4c5d6 feat: 登录接口
* 2a9c7f1 chore: 初始化项目

快进的本质是把 main 指针直接移到 feature 的位置，不创建新对象。历史保持一条直线，看起来像所有提交都直接发生在 main 上。

快进的优点是不产生额外提交；缺点是丢失了「这些提交属于同一个功能分支」的信息，事后无法从图上看出功能边界。

三方合并 ​

两条分支从共同祖先分叉后各自前进：

text
* 8b1e0d4 fix: 修复超时          ← HEAD -> main
| * 4c5d6e7 feat: 登录页面       ← feature/login
| * 3b4c5d6 feat: 登录接口
|/
* 2a9c7f1 chore: 初始化项目      ← 共同祖先（merge base）
bash
git switch main
git merge feature/login
# Merge made by the 'ort' strategy.
#  src/login.ts | 42 ++++++++++++++++++++++++++++++++++++++++++++
#  1 file created

结果：

text
*   9a8b7c6 (HEAD -> main) Merge branch 'feature/login'
|\
| * 4c5d6e7 (feature/login) feat: 登录页面
| * 3b4c5d6 feat: 登录接口
* | 8b1e0d4 fix: 修复超时
|/
* 2a9c7f1 chore: 初始化项目

Git 使用三方合并算法：取共同祖先 2a9c7f1 作为基准（base），分别比较 main 的 8b1e0d4 和 feature 的 4c5d6e7。只有一方修改的区域直接采纳，双方都修改同一区域时产生冲突。

合并提交 9a8b7c6 同时记录两个父提交，把两条历史线连接起来。

验证合并提交 ​

bash
git log --oneline --graph --decorate -5
# *   9a8b7c6 (HEAD -> main) Merge branch 'feature/login'
# |\
# | * 4c5d6e7 (feature/login) feat: 登录页面
# | * 3b4c5d6 feat: 登录接口
# * | 8b1e0d4 fix: 修复超时
# |/
# * 2a9c7f1 chore: 初始化项目

git cat-file -p HEAD
# tree 5d6e7f8...
# parent 8b1e0d4a1b2c3d4e5f60718293a4b5c6d7e8f901
# parent 4c5d6e7b2c3d4e5f60718293a4b5c6d7e8f9012a
# author Zhang San <zhangsan@example.com> 1760000000 +0800
# committer Zhang San <zhangsan@example.com> 1760000000 +0800
#
# Merge branch 'feature/login'

普通提交只有一个 parent 行，合并提交有两个。git show HEAD 默认展示合并提交相对第一父提交的差异，也就是 feature 分支带来的全部改动。

git merge --no-ff ​

即使可以快进，也强制生成合并提交：

bash
git merge --no-ff feature/login -m "merge: 合并登录功能"
text
快进（ff）：
* 4c5d6e7 (HEAD -> main, feature/login) feat: 登录页面
* 3b4c5d6 feat: 登录接口
* 2a9c7f1 chore: 初始化项目

禁止快进（no-ff）：
*   9a8b7c6 (HEAD -> main) merge: 合并登录功能
|\
| * 4c5d6e7 (feature/login) feat: 登录页面
| * 3b4c5d6 feat: 登录接口
|/
* 2a9c7f1 chore: 初始化项目

选择依据：

场景建议原因
个人分支、提交已整理成线性允许快进历史干净，无多余提交
功能分支需要保留边界--no-ff图上能看出整个功能是一个合并单元
发布分支合入主干--no-ff便于按功能整体回滚
平台开启「Create a merge commit」走 no-ff与 PR 记录对应

--no-ff 的代价是多一个提交；收益是合并单元明确，git revert -m 1 <merge-commit> 可以一次撤销整个功能。

合并后的清理 ​

bash
git branch -d feature/login
# Deleted branch feature/login (was 4c5d6e7).

git branch -a
# * main
#   remotes/origin/main
#   remotes/origin/feature/login

本地分支删除后，远程跟踪分支仍可能存在。远程分支的删除与多人协作流程见 11 远程协作全流程。

合并冲突 ​

两边修改同一区域时合并会暂停，git status -s 显示 UU。解决冲突文件后 git add 并用 git commit 完成合并；放弃本次合并用 git merge --abort。

常见坑 ​

合并方向搞反

在 feature/login 上执行 git merge main，会把主干变更并入功能分支；真正想做的通常是切到 main 再合并功能分支。方向反了不会立刻报错，但会产生大量无意义的合并提交。合并前先 git branch --show-current 确认位置。

快进合并后无法用单个 revert 撤销整个功能

快进不会留下合并提交，功能中的每个提交都直接落在 main 上。要整体撤销只能逐个 revert，或 reset 到合并前（会改写历史）。需要「一个功能一个可回滚单元」时使用 --no-ff。参见 08 revert。

合并前保证工作区干净

有未提交改动时，Git 可能拒绝合并，或在可自动合并的情况下把改动带入结果。先 git status -s，必要时 git stash 暂存现场（见 09 stash）。

小结 ​

  • 目标分支未分叉时快进，只移动指针；分叉时三方合并，产生两个父提交的合并提交。
  • 三方合并以共同祖先为基准，比较两个分支的最新提交。
  • --no-ff 强制保留合并提交，适合需要明确功能边界的团队策略。
  • 合并提交是「一个功能一个单元」的抓手，也是整体回滚的入口。
  • 合并后先看图确认结构，再删除已合入的分支。
