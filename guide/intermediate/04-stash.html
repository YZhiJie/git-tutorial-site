09 stash：临时保存工作现场 ​

学习目标 ​

  • 能用 git stash push -m 保存当前修改，并让工作区回到干净状态。
  • 能区分 -u 与默认行为，正确处理未跟踪文件。
  • 能使用 list、show、apply、pop、drop、clear 管理 stash 栈。
  • 能解释 pop 与 apply 的差异，以及 --index 对暂存状态的恢复。
  • 能在 stash 应用冲突或分支已分叉时，用 git stash branch 安全恢复。

stash 保存了什么 ​

git stash 把当前已跟踪文件的修改（包括已暂存和未暂存）打包成一个提交对象，存到 refs/stash，然后把工作区与暂存区重置到 HEAD。效果是「现场被收走，目录变干净」。

text
执行前：
工作区：src/app.ts 有修改
暂存区：src/config.ts 已 add
HEAD：3f2a1c9

执行 git stash push 后：
工作区：干净
暂存区：空
stash@{0}：保存了上述两份改动，基于 3f2a1c9

默认不包含未跟踪文件，因此 stash 后 git status 仍可能显示 ??。需要一并保存时加 -u。

保存现场 ​

bash
git status -s
#  M src/app.ts
# A  src/config.ts
# ?? notes/todo.md

git stash push -m "调试登录超时"
# Saved working directory and index state On main: 调试登录超时

git status -s
# ?? notes/todo.md      ← 未跟踪文件仍在

包含未跟踪文件：

bash
git stash push -u -m "包含未跟踪的调试脚本"
# Saved working directory and index state On main: 包含未跟踪的调试脚本

git status -s
# （干净）
参数包含内容
git stash push已跟踪文件的修改与暂存内容
-u / --include-untracked额外包含未跟踪文件
-a / --all额外包含被忽略文件（可能把 node_modules 一起打包）
-m <msg>给这条 stash 加说明，便于日后辨认
--keep-index保存现场，但保留暂存区内容不重置

不带参数的 git stash 等价于 git stash push，但无法附加说明。多条 stash 堆叠时，说明信息是唯一可靠的识别依据。

查看 stash 栈 ​

bash
git stash list
# stash@{0}: On main: 包含未跟踪的调试脚本
# stash@{1}: On main: 调试登录超时
# stash@{2}: WIP on main: 3f2a1c9 feat: 登录接口

编号越小越新。默认信息 WIP on <branch>: <hash> <subject> 记录了 stash 基于哪个提交创建。

查看具体内容：

bash
git stash show stash@{1}
#  src/app.ts    | 12 +++++++-----
#  src/config.ts |  3 ++-
#  2 files changed, 10 insertions(+), 5 deletions(-)

git stash show -p stash@{1}
# 输出完整差异

恢复：apply 与 pop ​

bash
# 应用最近的 stash，保留 stash 记录
git stash apply

# 应用指定 stash
git stash apply stash@{1}

# 应用并恢复当时的暂存状态
git stash apply --index stash@{1}

pop 等于 apply 成功后再 drop：

bash
git stash pop
# Dropped refs/stash@{0} (3f2a1c9...)

区别：

命令应用改动删除 stash适用场景
apply是否不确定是否要保留，或要在多个分支试用
pop是成功时是确认只恢复一次，保持栈干净
apply --index是否需要恢复「哪些已暂存」的状态

默认恢复后所有改动都是未暂存状态。原来 git add 过的内容不会自动回到暂存区，需要 --index。

删除 stash ​

bash
git stash drop stash@{1}
# Dropped stash@{1} (8b1e0d4...)

git stash clear
# 清空所有 stash

stash clear 不可逆

git stash clear 删除整个 stash 栈，没有确认提示。清理前先 git stash list 确认，重要的现场应先应用到分支或导出为补丁：

bash
git stash show -p stash@{0} > /tmp/stash-0.patch

分支已分叉：git stash branch ​

stash 基于创建时的提交。如果当前分支已经前进，或切换到了差异很大的分支，直接 pop 可能产生冲突。git stash branch 会回到 stash 创建时的提交，新建分支并应用：

bash
git stash branch fix/login-timeout stash@{0}
# Switched to a new branch 'fix/login-timeout'
# Dropped refs/stash@{0} (3f2a1c9...)

成功后该条 stash 会被删除。这个命令把「恢复」和「隔离」合并成一步，适合处理搁置较久的现场。

恢复冲突 ​

bash
git stash pop
# Auto-merging src/app.ts
# CONFLICT (content): Merge conflict in src/app.ts
# The stash entry is kept in case you need it again.

与合并冲突一样，编辑文件删除冲突标记，然后：

bash
git add src/app.ts
git status -s
# M  src/app.ts

git stash drop

冲突时 stash 不会被自动删除，这是保护机制：确认恢复结果正确后再手动 drop。若放弃恢复，确认没有其他未提交工作后执行 git reset --hard HEAD，stash 记录仍然保留。

适用边界 ​

适合使用：

  • 正在开发时来了线上问题，需要立即切到 hotfix 分支。
  • 拉取远程更新时工作区不干净，暂时收起再 pull。

不适合使用：

  • 当作长期任务清单。stash 不会推送，换机器就没了，也容易被遗忘。
  • 团队共享代码。需要传递未完成工作时应推送 WIP 分支。
  • 替代提交。重要节点应形成真实提交，让历史和 CI 都能看到。

需要长期保存的未完成工作，应提交到功能分支并推送：

bash
git switch -c wip/login-timeout
git add -A && git commit -m "wip: 登录超时调试中间状态"
git push -u origin wip/login-timeout

常见坑 ​

默认 stash 不含未跟踪文件

git stash 后仍看到 ?? 文件，不是命令失效，而是设计如此。需要干净工作区时加 -u，但要先确认这些文件里没有本地配置或密钥。

pop 之后暂存状态丢失

git add 过的内容在 pop 后变成未暂存，容易误以为改动丢了。用 git stash apply --index 恢复索引状态。

小结 ​

  • stash 保存已跟踪文件的修改与暂存内容，默认不包含未跟踪文件，需要 -u。
  • apply 保留记录，pop 成功后删除记录，--index 恢复暂存状态。
  • 分支已分叉时用 git stash branch，回到 stash 的基点新建分支再应用。
  • 恢复冲突时 stash 会保留，解决冲突并确认后再 drop。
  • stash 是本地临时手段，不是备份、共享或长期任务管理工具。
