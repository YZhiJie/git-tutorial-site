07 撤销的艺术：restore 与 reset 三模式 ​

学习目标 ​

  • 能区分「撤销工作区修改」「撤销暂存」「撤销提交」三个层级，并选对命令。
  • 能用 git restore 与 git restore --staged 精确回退文件。
  • 能对照 git reset --soft、--mixed、--hard 对 HEAD、暂存区、工作区的影响。
  • 能用 git reflog 找回被 reset 掉的提交。
  • 能根据「是否已推送、是否保留改动」给出撤销决策。

先问三个问题 ​

撤销命令之所以容易用错，是因为「撤销」可能指三件不同的事。动手前先确认：

  1. 要撤销到哪一层：工作区、暂存区，还是提交？
  2. 改动还要不要保留？
  3. 提交是否已经推送到共享分支？

已经推送的提交不应通过 reset 改写历史，应使用 git revert 追加反向提交（见 08 revert）。

text
工作区（未暂存） ── restore ──────────────> 丢弃，回到暂存区版本
暂存区          ── restore --staged ──────> 取消暂存，工作区不动
提交            ── reset <mode> ──────────> 移动分支指针，按模式处理暂存区与工作区

git restore：文件级撤销 ​

丢弃工作区修改 ​

bash
git diff README.md          # 先确认要丢的是什么
git restore README.md
# 工作区文件回到暂存区中的版本

git status -s
# （如果暂存区与 HEAD 一致，则文件恢复干净）

如果文件已经暂存，restore 回到的是暂存区版本，而不是最后一次提交。想让工作区和暂存区都回到 HEAD：

bash
git restore --staged --worktree README.md

取消暂存 ​

bash
git add src/app.ts
git restore --staged src/app.ts
git status -s
#  M src/app.ts     ← 改动还在工作区，只是不再暂存

--staged 只改索引，不碰磁盘文件。这是「git add 加多了」最安全的回退方式。

从历史版本取文件 ​

bash
# 取回上一次提交中的版本到工作区
git restore --source=HEAD~1 README.md

# 同时更新暂存区
git restore --source=HEAD~1 --staged --worktree README.md

git diff --staged
# 可以看到 README.md 相对 HEAD 的变化

restore 丢弃的未提交改动无法找回

git restore 直接覆盖工作区，被覆盖的内容没有进入对象库，也不在 reflog 中。执行前先 git diff 或 git stash push。--staged 是安全的，因为它只操作索引。

git reset：提交级撤销 ​

git reset <target> 把当前分支指针移到 <target>，再根据模式决定是否重置暂存区和工作区。目标可以是 HEAD~1、某个提交哈希或分支名。

三模式对照 ​

模式HEAD / 分支指针暂存区工作区典型场景
--soft移到目标不变不变撤销提交，改动仍已暂存，准备重新提交
--mixed（默认）移到目标重置到目标不变撤销提交与暂存，改动留在工作区重新挑选
--hard移到目标重置到目标重置到目标彻底丢弃提交与所有未提交改动

--soft：只退提交 ​

bash
git log --oneline -3
# 3f2a1c9 feat: 登录接口
# 8b1e0d4 fix: 修复超时
# 2a9c7f1 chore: 初始化项目

git reset --soft HEAD~1

git log --oneline -2
# 8b1e0d4 fix: 修复超时
# 2a9c7f1 chore: 初始化项目

git status -s
# M  src/login.ts    ← 上一个提交的改动仍在暂存区

适合「提交粒度不对，想拆成两个提交」：soft 回退后，用 git restore --staged 取消全部暂存，再 git add -p 重新组合。

--mixed：退提交并取消暂存 ​

bash
git reset HEAD~1
# Unstaged changes after reset:
# M  src/login.ts

git status -s
#  M src/login.ts    ← 改动在工作区，未暂存

这是默认模式，也是最常用的「我刚才提交早了，想重新组织」的做法。改动一行没丢，只是回到未暂存状态。

--hard：全部丢弃 ​

bash
git reset --hard HEAD~1
# HEAD is now at 8b1e0d4 fix: 修复超时
git status -s
# （无输出）

--hard 同时重置暂存区和工作区。对已跟踪文件而言，未提交的修改会消失；未跟踪文件不会被删除，需要 git clean -fd 才会清理（先用 -n 预览）。

--hard 之前先确认三件事

第一，目标提交是否正确（git log --oneline）；第二，工作区改动是否已 stash 或提交；第三，分支是否已推送。--hard 丢掉的未提交改动无法通过 reflog 找回。已推送分支上执行 --hard 再强推，会影响所有协作者。

旧命令 git checkout -- ​

bash
git checkout -- README.md
# 等价于 git restore README.md，丢弃工作区修改

区别在于 git checkout HEAD -- README.md 会同时把 HEAD 的版本写入索引和工作区，效果接近 git restore --source=HEAD --staged --worktree README.md。因为语义混合，新代码应优先使用 restore。

reflog：reset 的兜底 ​

reset 只是移动指针，原提交对象不会立即删除。git reflog 记录了 HEAD 的每次移动：

bash
git reflog
# 3f2a1c9 HEAD@{0}: reset: moving to HEAD~1
# 3f2a1c9 HEAD@{1}: commit: feat: 登录接口
# 8b1e0d4 HEAD@{2}: commit: fix: 修复超时
# 2a9c7f1 HEAD@{3}: commit (initial): chore: 初始化项目

误执行 git reset --hard HEAD~1 后恢复：

bash
git reset --hard HEAD@{1}
# HEAD is now at 3f2a1c9 feat: 登录接口

如果提交已经不在任何分支上，也可以基于它重建分支：

bash
git branch rescue/login 3f2a1c9

reflog 不是永久保险

reflog 默认保留 90 天的可达记录、30 天的不可达记录，且只存在于本地仓库。清理过期的 reflog 或重新克隆后，丢失的提交无法找回。重要工作仍应推送到远程。

撤销决策树 ​

text
要撤销什么？
├─ 工作区里未暂存的修改
│   └─ git restore <file>            （丢弃，无法恢复）
├─ 已经 add 的内容
│   └─ git restore --staged <file>   （改动保留在工作区）
└─ 已经 commit 的内容
    ├─ 已推送到共享分支
    │   └─ git revert <commit>       （追加反向提交，不改历史）
    └─ 尚未推送
        ├─ 保留改动并保持暂存  → git reset --soft HEAD~1
        ├─ 保留改动但取消暂存  → git reset --mixed HEAD~1
        └─ 全部丢弃            → git reset --hard HEAD~1（确认后）

常见坑 ​

在共享分支上 reset 后强推

git reset --hard 加 git push --force 会让其他人的本地历史与远程分叉，他们拉取时可能把旧提交重新带回来。主干分支应禁止强推，回滚线上代码用 revert。

小结 ​

  • 撤销分三层：工作区用 restore，暂存区用 restore --staged，提交用 reset。
  • --soft 只退指针，--mixed 再退暂存区，--hard 连工作区一起重置。
  • reset --hard 丢弃的未提交改动不可恢复，执行前必须确认或先 stash。
  • 已推送的提交不要 reset 改写，改用 revert 追加反向提交。
  • reflog 能找回被 reset 的提交，但只在本机、且有保留期限。
