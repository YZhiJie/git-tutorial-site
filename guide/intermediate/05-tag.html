10 tag：版本发布标记 ​

学习目标 ​

  • 能区分轻量标签（lightweight tag）与附注标签（annotated tag）的存储差异。
  • 能创建、查看、推送、删除本地与远程标签。
  • 能按语义化版本（Semantic Versioning，SemVer）为发布命名。
  • 能使用 git describe 生成可追溯的构建版本号。
  • 能说明为什么已发布的标签不应移动或覆盖。

标签是什么 ​

标签（tag）是指向某个提交的固定引用，存放在 .git/refs/tags。与分支不同，标签不会随着新提交自动前移，它标记的是「这个提交就是 v1.0.0」。

Git 支持两种标签：

类型创建方式存储内容适用场景
轻量标签git tag v1.0.0直接指向提交的引用本地临时标记、个人书签
附注标签git tag -a v1.0.0 -m "..."独立的 tag 对象，含打标签人、日期、说明正式发布、需要审计的版本
text
轻量标签：
refs/tags/v1.0.0-rc1 ──────────────> commit 8b1e0d4

附注标签：
refs/tags/v1.0.0 ──> tag 对象 ──> commit 3f2a1c9
                     （tagger、日期、说明、可选签名）

正式发布应使用附注标签，因为它包含谁在什么时候、基于什么原因发布的信息，git show 能直接看到。

创建与查看 ​

bash
# 轻量标签
git tag v1.0.0-rc1

# 附注标签（推荐用于发布）
git tag -a v1.0.0 -m "release: 1.0.0 正式版"

# 在指定提交上打标签
git tag -a v0.9.0 8b1e0d4 -m "release: 0.9.0 灰度版本"

列出与查看：

bash
git tag                      # 列出全部标签
# v1.0.0
# v1.0.0-rc1

git tag -l "v1.*"
# v1.0.0
# v1.0.0-rc1

git show v1.0.0
# tag v1.0.0
# Tagger: Zhang San <zhangsan@example.com>
# Date:   Tue Oct 20 15:02:11 2026 +0800
#
# release: 1.0.0 正式版
#
# commit 3f2a1c9a1b2c3d4e5f60718293a4b5c6d7e8f901

轻量标签执行 git show 时只显示提交信息，没有 tag 对象头部，这是区分两者的直接方法。

签名标签 ​

需要证明标签由持有私钥的人创建时，使用 GPG 签名：

bash
git tag -s v1.0.1 -m "release: 1.0.1 安全修复"
git tag -v v1.0.1
# gpg: Good signature from "Zhang San <zhangsan@example.com>"

验证失败或显示 BAD signature 时不要发布。团队也可以配置 gpg.format ssh 与 user.signingkey，用 SSH 密钥签名。签名只证明标签来源，不证明代码本身安全。

推送标签 ​

git push 默认不推送标签。打了标签但没推送，远程仓库和 CI 都看不到。

bash
# 只推一个
git push origin v1.0.0
# To github.com:your-org/your-repo.git
#  * [new tag]         v1.0.0 -> v1.0.0

# 推送全部标签（包括轻量标签）
git push origin --tags

# 只推送与已推送提交关联的附注标签
git push origin --follow-tags
命令范围建议
git push origin <tag>单个标签精确发布，最常用
git push origin --tags所有本地标签补推历史标签时使用，注意不要带上临时标签
git push origin --follow-tags可达的附注标签日常推送分支时顺带发布版本

--follow-tags 不会推送轻量标签，这是它比 --tags 更安全的原因：临时书签不会误上远程。

删除标签 ​

本地与远程是两套命名空间，需要分别删除：

bash
# 删除本地
git tag -d v1.0.0-rc1
# Deleted tag 'v1.0.0-rc1' (was 8b1e0d4)

# 删除远程
git push origin --delete v1.0.0-rc1
# To github.com:your-org/your-repo.git
#  - [deleted]         v1.0.0-rc1

只删本地，远程标签仍然存在，其他人拉取时会重新出现；只删远程，本地仍保留。两步都完成后才算真正移除。

不要移动已发布的标签

删除并在另一个提交上重建同名标签，会让已经拉取过的人、镜像缓存和构建系统看到不同内容。同一版本号指向两个提交，排查问题时无法确定线上跑的是哪份代码。发布后发现错误，应发布新的补丁版本（如 v1.0.1），而不是覆盖 v1.0.0。

语义化版本 ​

SemVer 的格式为 MAJOR.MINOR.PATCH，惯例加 v 前缀作为标签名：

text
v2.3.1
 │ │ └─ PATCH：向后兼容的缺陷修复
 │ └─── MINOR：向后兼容的新功能
 └───── MAJOR：不兼容的接口变更
变更版本动作示例
修复 bug，行为兼容PATCH +1v1.4.2 → v1.4.3
新增功能，兼容旧用法MINOR +1，PATCH 归零v1.4.3 → v1.5.0
删除或修改公开接口MAJOR +1，其余归零v1.5.0 → v2.0.0
预发布加连字符标识v2.0.0-rc.1、v2.0.0-beta.2

标签名与包版本保持一致。若 package.json 写 1.4.3，Git 标签应是 v1.4.3，避免构建产物无法对应。

bash
# 发布前确认工作区干净、提交正确
git status -s
git log --oneline -1
# 3f2a1c9 feat: 登录接口

git tag -a v1.4.3 -m "release: 1.4.3"
git push origin v1.4.3

git describe：从提交反查版本 ​

bash
git describe --tags
# v1.4.3-12-g3f2a1c9

输出含义：

片段含义
v1.4.3最近的可达标签
-12-距离该标签 12 个提交
g3f2a1c9g + 提交短哈希

常用变体：

bash
git describe --tags --always   # 没有标签时输出短哈希，适合构建脚本兜底
git describe --tags --dirty    # v1.4.3-12-g3f2a1c9-dirty，表示工作区有未提交修改
git describe --tags --match "v[0-9]*"   # 只匹配版本号形式的标签

CI 常用它生成构建号，把产物精确关联到「哪个版本之后第几个提交」，比单纯用分支名更可追溯。

常见坑 ​

标签没有推送就等于没发布

git tag 只写本地。流水线按 tag 触发时，远程没有该标签就不会构建。发布清单中应包含 git push origin <tag>，并用远程仓库页面或 git ls-remote --tags origin 确认。

同名标签与分支会造成歧义

同时存在 v1.0.0 分支和标签时，git rev-parse v1.0.0 会给出警告并优先按标签解析。需要明确时写全引用：refs/tags/v1.0.0 或 refs/heads/v1.0.0。版本标签不要与长期分支同名。

检出标签会进入游离 HEAD

git switch --detach v1.0.0 可以查看发布版本，但不要在此状态直接开发。需要基于该版本修复时，新建分支：git switch -c hotfix/v1.0.1 v1.0.0。

小结 ​

  • 轻量标签只是提交引用，附注标签是独立对象，正式发布应使用附注标签。
  • 标签默认不随 git push 推送，需显式推送单个标签或使用 --follow-tags。
  • 删除标签要同时处理本地与远程两个命名空间。
  • SemVer 用 MAJOR.MINOR.PATCH 表达兼容性，标签名应与包版本一致。
  • git describe 把提交映射为「最近标签 + 距离 + 哈希」，适合构建追溯。
