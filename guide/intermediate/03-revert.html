08 revert：安全地反向提交 ​

学习目标 ​

  • 能解释 git revert 生成反向提交的原理，以及它与 reset 的本质区别。
  • 能用 git revert <commit> 撤销单个提交，并处理撤销过程中的冲突。
  • 能按正确顺序连续撤销多个提交，或用 --no-commit 合并为一次回滚。
  • 能用 git revert -m 1 <merge-commit> 回滚合并提交，并说明再次合并时的注意事项。
  • 能判断线上回滚应使用 revert 而不是 reset。

revert 做了什么 ​

git revert <commit> 不是删除提交，而是计算目标提交的相反变更，并把它作为一个新提交追加到当前分支。

text
撤销前：
* 3f2a1c9 (HEAD -> main) feat: 登录接口
* 8b1e0d4 fix: 修复超时
* 2a9c7f1 chore: 初始化项目

执行 git revert 8b1e0d4 后：
* 9c4d2e1 (HEAD -> main) Revert "fix: 修复超时"
* 3f2a1c9 feat: 登录接口
* 8b1e0d4 fix: 修复超时      ← 仍然在历史中
* 2a9c7f1 chore: 初始化项目

新提交 9c4d2e1 的内容等于「把 8b1e0d4 引入的改动反向应用」。原提交保留，历史只增不改，因此可以直接 git push，不会影响其他人的本地仓库。

这与 reset 的差别是根本性的：

维度resetrevert
历史移动指针，删除提交追加新提交，保留原提交
哈希分支指向的提交改变所有既有提交不变
已推送分支需要强推，破坏协作普通推送即可
可追溯性被撤销的提交从分支历史消失撤销原因和对象都在历史中
适用场景本地未推送的整理共享分支、线上代码回滚

基本用法 ​

bash
git log --oneline -5
# 3f2a1c9 feat: 登录接口
# 8b1e0d4 fix: 修复超时
# 2a9c7f1 chore: 初始化项目

git revert 8b1e0d4
# [main 9c4d2e1] Revert "fix: 修复超时"
#  1 file changed, 3 deletions(-)

不打开编辑器，直接使用默认信息：

bash
git revert --no-edit 8b1e0d4
# 提交信息为：Revert "fix: 修复超时"

只在工作区与暂存区应用反向变更，不立即提交：

bash
git revert --no-commit 8b1e0d4
git status -s
# M  src/config.ts
git commit -m "revert: 回滚超时配置"

--no-commit 适合把多个撤销合并成一次提交，或在提交前补充其他修复。

连续撤销多个提交 ​

要把 B、C 两个提交都撤销，必须从新到旧处理。原因是每个反向补丁都基于当前工作区状态计算，顺序错了容易产生不必要的冲突。

text
历史：A - B - C - D (HEAD)
目标：撤销 B 和 C，保留 D
顺序：先 revert C，再 revert B
bash
git revert --no-commit 4c5d6e7 3b4c5d6
# 4c5d6e7 对应 C，3b4c5d6 对应 B

git status -s
# M  src/login.ts

git commit -m "revert: 撤销登录功能相关的两次提交"

也可以使用区间，Git 会按从新到旧的顺序依次应用：

bash
git revert --no-commit 3b4c5d6..4c5d6e7
git commit -m "revert: 撤销登录接口与页面"

区间 A..B 不包含 A、包含 B，因此上面的写法覆盖 B 之后的提交直到 C。执行前用 git log --oneline 3b4c5d6..4c5d6e7 确认范围。

一次撤销大量提交容易冲突

连续 revert 中间状态可能互相依赖。先小范围验证，遇到冲突立即解决再继续；不要在一堆冲突未处理时继续叠加新的 revert。

冲突处理 ​

如果目标提交改过的行后来又被修改，反向补丁无法直接应用：

bash
git revert 8b1e0d4
# Auto-merging src/config.ts
# CONFLICT (content): Merge conflict in src/config.ts
# error: could not revert 8b1e0d4... fix: 修复超时

处理流程与合并冲突一致：编辑文件删除冲突标记，git add 标记解决，再 git revert --continue 完成提交。放弃用 git revert --abort。

bash
git add src/config.ts
git revert --continue
# [main 9c4d2e1] Revert "fix: 修复超时"

回滚合并提交 ​

合并提交有两个父提交，revert 必须知道「以哪一条为主线」。-m 1 表示保留第一父提交（通常是当前分支）一侧的上下文，撤销另一侧带来的全部改动。

text
*   9a8b7c6 (HEAD -> main) Merge branch 'feature/login'
|\
| * 4c5d6e7 (feature/login) feat: 登录页面
| * 3b4c5d6 feat: 登录接口
* | 8b1e0d4 fix: 修复超时
|/
* 2a9c7f1 chore: 初始化项目

父提交顺序：

bash
git cat-file -p 9a8b7c6
# parent 8b1e0d4...   ← 父 1：main 合并前的位置
# parent 4c5d6e7...   ← 父 2：feature 的末端

执行：

bash
git revert -m 1 9a8b7c6
# [main 1d2e3f4] Revert "Merge branch 'feature/login'"

省略 -m 会直接报错：

bash
git revert 9a8b7c6
# error: commit 9a8b7c6 is a merge but no -m option was given.

再次合并同一个分支的坑 ​

回滚合并提交后，feature/login 的提交仍然存在于历史中。Git 认为这些提交「已经合并过」，再次 git merge feature/login 不会重新引入它们，结果可能是空合并。

bash
git merge feature/login
# Already up to date.

要恢复该功能，有两种正确方式：

  • 撤销这次 revert：git revert 1d2e3f4，把反向变更再反向一次。
  • 在 feature/login 上继续提交新改动，再合并；新提交会被正常带入，但被回滚的旧提交不会自动恢复。
text
错误做法：reset 掉 revert 提交后重新 merge
正确做法：revert the revert，或基于新提交重新合并

线上回滚不要用 reset

主干已经发布时，git reset --hard 加 git push --force 会把其他人的提交一起抹掉，并让克隆过仓库的人再次推送时把旧提交带回来。线上回滚一律使用 git revert，保留完整历史。

常见坑 ​

revert 不会抹除敏感信息

凭证已经提交并推送后，revert 只是在新提交里删除它，旧提交仍然包含明文。必须立即轮换密钥，并用历史改写工具清理；revert 只解决「当前版本中的引用」，不解决泄露。

回滚合并提交后直接再合并无效

如上一节所述，Git 会认为功能已合并。不要反复 reset 合并提交试图「骗过」Git，使用 revert 撤销那次回滚，或让功能分支产生新提交。

小结 ​

  • revert 通过追加一个反向补丁提交来撤销变更，原提交保留在历史中。
  • 已推送分支上的回滚应使用 revert，只有本地未推送的整理才适合 reset。
  • 连续撤销多个提交按从新到旧的顺序执行，可用 --no-commit 合并为一次回滚。
  • 回滚合并提交必须用 -m 1 指定主线父提交，之后再次合并同一分支不会自动恢复旧改动。
  • revert 不消除敏感信息，凭证泄露要先轮换再清理历史。
