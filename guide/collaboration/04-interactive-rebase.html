14 交互式 rebase：整理提交历史 ​

学习目标 ​

学完本章，你将能够：

  • 用 git rebase -i 打开提交清单，并读懂每一列
  • 熟练使用 pick / reword / edit / squash / fixup / drop / exec
  • 把一堆「wip」「fix typo」提交整理成可评审的原子提交
  • 用 --autosquash 配合 fixup! 提交自动归并
  • 判断哪些历史整理是安全的，哪些会坑到同事

交互式 rebase 在做什么 ​

bash
# 整理最近 5 个提交
git rebase -i HEAD~5

# 或者：整理从 main 分叉以来的所有提交
git rebase -i main

编辑器会打开一份「待办清单」：

text
pick 3f2a1c9 feat: 登录接口基础结构
pick 8b1e0d4 wip
pick 2a9c7f1 fix typo
pick 5d3e8a2 feat: 登录失败提示
pick 9c1b7f0 修改 review 意见

从上到下就是新的提交顺序。每行三列：动作、提交哈希、提交信息。你修改动作或调整行的顺序，Git 就按新清单重放提交。

保存退出后，Git 从最上面开始逐个执行；遇到 squash 等动作会继续弹出编辑器让你合并提交信息。

七个动作的准确含义 ​

动作简写作用什么时候用
pickp保留该提交默认
rewordr保留改动，修改提交信息写错了 message
edite停下来让你修改提交内容要补文件、拆分提交
squashs合并到上一个提交，保留两条信息多个提交合成一个，想保留描述
fixupf合并到上一个提交，丢弃本条信息修 typo、补漏文件
dropd删除该提交提交完全不需要
execx执行一条 shell 命令每个提交后跑测试/格式化

提交顺序可以调整

把后面的 pick 行剪切到前面，就能改变提交顺序。但如果两个提交改同一段代码，调整顺序可能引发冲突——这很正常，按第 13 章的方式解决即可。

场景一：把 wip 提交合并成一个 ​

整理前：

text
* 9c1b7f0 (HEAD -> feature/login) 修改 review 意见
* 5d3e8a2 feat: 登录失败提示
* 2a9c7f1 fix typo
* 8b1e0d4 wip
* 3f2a1c9 feat: 登录接口基础结构
bash
git rebase -i HEAD~5
text
pick 3f2a1c9 feat: 登录接口基础结构
fixup 8b1e0d4 wip
fixup 2a9c7f1 fix typo
pick 5d3e8a2 feat: 登录失败提示
fixup 9c1b7f0 修改 review 意见

结果：

text
* 7d4c2b1 (HEAD -> feature/login) feat: 登录接口基础结构
* 4e8a9c3 feat: 登录失败提示

两条干净的原子提交。fixup 会丢弃被合并提交的信息，适合无意义的中间提交；如果想保留描述细节，用 squash。

场景二：修改历史提交的信息 ​

text
reword 3f2a1c9 feat: 登录接口

保存退出后，Git 会为这个提交单独打开编辑器，改完信息继续执行。注意：reword 之后的所有提交哈希都会改变，因为它们的祖先变了。

场景三：拆分一个过大的提交 ​

text
edit 3f2a1c9 feat: 登录接口

Git 会停在这个提交上：

bash
# 当前 HEAD 指向该提交，工作区是干净的
git reset HEAD^                 # 把改动退回工作区，提交本身撤销
git add src/api/login.ts
git commit -m "feat: 登录接口请求层"
git add src/components/LoginForm.vue
git commit -m "feat: 登录表单组件"
git rebase --continue

拆分是 review 友好度提升最明显的操作：一个提交只做一件事。

场景四：删除一个提交 ​

两种方式：

text
drop 2a9c7f1 fix typo

或者直接删掉那一行（效果相同）。如果删除后后面的提交依赖它，会冲突，需要手工解决。

场景五：autosquash 自动归并 ​

日常开发中不必攒到最后再整理。当你发现某个提交需要修补时：

bash
# 针对 3f2a1c9 做一个修补提交
git commit --fixup 3f2a1c9

# 之后自动整理，无需手工编辑清单
git rebase -i --autosquash main

清单会自动变成：

text
pick 3f2a1c9 feat: 登录接口
fixup 9e2b7c4 fixup! feat: 登录接口
pick 5d3e8a2 feat: 登录失败提示

配合配置可以省掉 --autosquash：

bash
git config --global rebase.autoSquash true

场景六：每个提交后跑一次测试 ​

text
pick 3f2a1c9 feat: 登录接口
exec pnpm test -- --run
pick 5d3e8a2 feat: 登录失败提示
exec pnpm test -- --run

exec 会在该提交重放完成后执行命令。任一命令失败，rebase 会停下，让你修复。这是保证「每个提交都能独立通过 CI」的有效手段，适合准备开源或需要 bisect 的仓库。

操作中的冲突与收尾 ​

bash
# 解决冲突后
git add <file>
git rebase --continue

# 当前提交的改动已被上游包含，直接跳过
git rebase --skip

# 整个整理放弃，回到开始前
git rebase --abort

# 查看还剩哪些提交没处理
git status

整理历史的前提

交互式 rebase 会改写提交哈希。只对尚未被他人依赖的分支使用。已经 push 的个人分支需要 --force-with-lease 重新推送；共享分支一律不动。

常见坑 ​

  1. 清单顺序理解反了：清单从上到下是新历史顺序，不是时间倒序的展示。
  2. squash 和 fixup 混用导致信息丢失：需要保留描述用 squash，纯修补用 fixup。
  3. edit 后忘了 --continue：仓库会一直停在 rebase 中间状态，后续命令行为异常。
  4. 整理完直接普通 push：历史已改写，必须 --force-with-lease。
  5. 在 main 上整理已合并的提交：改写公共历史，影响所有协作者。
  6. 一次整理太多提交：冲突叠加后很难定位。建议按功能分批整理。

小结 ​

  • git rebase -i 的本质是编辑一份提交重放清单，顺序、动作都可改。
  • pick 保留、reword 改信息、edit 改内容、squash/fixup 合并、drop 删除、exec 跑命令。
  • --fixup + --autosquash 是日常最省力的整理组合。
  • 整理后哈希全变，只能对个人分支操作，并用 --force-with-lease 推送。
  • 好的提交历史不是「好看」，而是每个提交都能独立构建、独立回滚、独立 bisect。
