13 merge vs rebase：黄金法则 ​

学习目标 ​

学完本章，你将能够：

  • 用分支图解释 merge 与 rebase 对历史结构的根本差别
  • 说明 rebase 为什么会改写提交哈希，以及由此带来的协作风险
  • 熟练处理 rebase 过程中的冲突：--continue / --skip / --abort
  • 依据「分支是否已共享」做出 merge 还是 rebase 的决策
  • 安全地强推个人分支：--force-with-lease 而不是 --force

同一个目标，两种历史 ​

假设 main 和 feature 从同一点分叉，双方各有新提交：

text
        D---E feature
       /
  A---B---C main

现在要把 feature 的改动集成到 main。两种方式的结果完全不同。

merge：保留真实分叉 ​

bash
git switch main
git merge feature
text
        D---E feature
       /     \
  A---B---C---M main

M 是一个合并提交，有两个父提交（C 和 E）。历史是真实的：它记录了「这两条线在某个时刻汇合」。代价是图会越来越复杂，git log --graph 在长期项目里会变成一团麻。

rebase：把提交「搬」到新基底上 ​

bash
git switch feature
git rebase main
text
  A---B---C main
           \
            D'---E' feature

D' 和 E' 不是原来的 D、E，而是内容相同、父提交不同的新提交。哈希必然改变，因为提交哈希由「内容 + 父提交 + 作者 + 时间」共同决定，父提交变了，哈希就变了。

历史变成一条直线，读起来像「feature 是在最新 main 之后开发的」。但它不是真实发生过的时间线。

一句话记住区别

merge 记录「发生了什么」，rebase 讲述「本来应该怎样」。

黄金法则：不要 rebase 公共分支 ​

已经被其他人拉取过的分支，不要 rebase。

原因不是风格偏好，而是数学结果：

  1. rebase 生成了新的提交 D'、E'，旧的 D、E 仍在同事本地。
  2. 同事下次 pull 时，Git 会看到两条历史：一条有 D,E，一条有 D',E'，内容重复但哈希不同。
  3. Git 只能做一次合并，结果是同一改动出现两次，或者产生大量冲突。
  4. 同事必须手动 reset --hard origin/main 才能修复，未推送的工作可能一起丢失。
text
同事本地：  A---B---C---D---E
远端（你强推后）：A---B---C---D'---E'

这两条线再也无法自动对齐。

判断标准很简单：

分支是否可 rebase
只有你在用、还没合并的 feature 分支可以
已经 push 且同事基于它开发不可以
main / develop / release 等共享分支绝对不可以
已合并进主干的提交不需要，也不应该

决策表：什么时候用哪个 ​

场景推荐理由
个人 feature 分支落后 mainrebase保持线性历史，PR diff 干净

多人共同开发的长周期分支merge改写历史会破坏所有人的本地仓库
把 feature 合入 mainmerge --no-ff 或平台 Squash Merge保留「这是一个完整功能」的边界
紧急修复要进多个分支cherry-pick（见第 15 章）不需要整支合并

rebase 遇到冲突怎么办 ​

rebase 不是一次性操作，而是逐个提交重放。每个提交都可能冲突：

bash
git rebase main
# CONFLICT (content): Merge conflict in src/api/client.ts
# error: could not apply 8b1e0d4... feat: 新增重试逻辑

流程与 merge 类似，但收尾命令不同：

bash
# 1. 解决当前提交的冲突
#    编辑文件，删除冲突标记
git add src/api/client.ts

# 2. 继续重放下一个提交
git rebase --continue

# 3. 如果这个提交的改动已经不需要了（例如已被上游实现），跳过它
git rebase --skip

# 4. 放弃整个 rebase，回到开始前的状态
git rebase --abort

rebase 冲突中的 ours / theirs 是反的

rebase 时 ours 是目标分支（main），theirs 是你正在重放的提交。别凭 merge 的直觉用 --ours。

另一个实用技巧：开启 rerere 后，同一冲突第二次出现时 Git 会自动套用你上次的解法（第 17 章）。

用 pull --rebase 保持功能分支线性 ​

bash
# 等价于 git fetch + git rebase origin/main
git pull --rebase

# 忘记加参数时，可以中止并用正确方式重来
git rebase --abort

# 设为个人默认（适合功能分支为主的团队）
git config --global pull.rebase true

如果团队的主干要求线性历史（很多仓库开启了 "Require linear history"），pull --rebase 是日常必选项，否则你的合并提交会被分支保护规则拒绝。

强推的正确姿势 ​

rebase 之后本地历史与远端分叉，普通 push 会被拒绝：

text
! [rejected] feature/login -> feature/login (non-fast-forward)

此时只能强推，但要用带保护的条件强推：

bash
git push --force-with-lease origin feature/login

--force-with-lease 的语义是：只有当远端分支仍停留在我上次 fetch 时的位置，才允许覆盖。如果同事在此期间推了新提交，远端位置变了，推送会被拒绝。

bash
# 先 fetch，确认远端确实没有别人的新提交
git fetch origin
git log --oneline HEAD..origin/feature/login   # 应该为空

# 再强推
git push --force-with-lease origin feature/login

永远不要对共享分支强推

git push --force origin main 会无条件覆盖远端。即使你「确定」没人改过，也可能覆盖 CI 机器人的提交、别人的 hotfix，或者上一条被你遗忘的推送。团队里应把这条命令列入禁用清单。

什么时候 rebase 反而更危险 ​

  • 分支上有合并提交：rebase 默认会丢弃合并提交，只保留一侧的改动，可能静默丢失代码。需要加 --rebase-merges 才能保留拓扑。
  • 分支上有签名提交：rebase 后签名失效。
  • 分支被CI 缓存或部署记录引用了具体哈希：改写后这些引用会指向不存在的对象。
  • 你不确定是否有人基于该分支开发：默认按「有人」处理，先沟通。

常见坑 ​

  1. rebase 后直接 push --force：应使用 --force-with-lease，给自己留一道保险。
  2. 在 main 上执行 git pull --rebase 后强推：公共分支被改写，全组遭殃。
  3. rebase 冲突时用 --skip 跳过所有冲突：可能把整个提交的改动都丢掉，必须逐个确认。
  4. 以为 rebase 后提交哈希不变：哈希一定变，任何依赖哈希的脚本、链接、部署记录都会失效。
  5. rebase 前没提交/没 stash：Git 会拒绝执行，或者把未提交改动带入冲突现场。

小结 ​

  • merge 保留分叉和合并提交，rebase 生成线性历史但会改写哈希。
  • 黄金法则：已被他人拉取的公共分支禁止 rebase。
  • rebase 冲突用 --continue / --skip / --abort 收尾，ours/theirs 方向与 merge 相反。
  • rebase 后强推只能用 --force-with-lease，并对共享分支完全禁用强推。
  • 选择依据不是「哪种历史更漂亮」，而是「这条分支有没有被别人依赖」。
