11 远程协作全流程 ​

学习目标 ​

学完本章，你将能够：

  • 说清 origin、远程分支、远程跟踪分支三者的区别
  • 用 fetch / pull / push 完成日常同步，并解释 pull 到底做了什么
  • 正确设置上游分支（upstream），让 git status 和 git push 不再需要重复参数
  • 判断什么时候该用 pull --rebase，什么时候必须用普通 merge
  • 排查「本地明明提交了，远端却没有」这类同步问题

远程仓库不是一个特殊的东西 ​

远程仓库（remote）本质上只是一个存了 URL 的名字。origin 是 git clone 自动起的默认名字，不是关键字，你也可以叫 upstream、fork、company。

bash
# 查看当前配置了哪些远程
git remote -v
# origin  git@github.com:team/project.git (fetch)
# origin  git@github.com:team/project.git (push)

# 添加第二个远程（例如公司镜像仓）
git remote add mirror https://git.example.com/team/project.git

真正的关键概念是远程跟踪分支（remote-tracking branch）：origin/main 是你本地保存的「上次和远端通信时，远端 main 的样子」。它是一份只读快照，你永远不会直接提交到 origin/main，只能通过 fetch 更新它。

本地仓库
├── refs/heads/main          ← 你的本地分支，可提交
├── refs/remotes/origin/main ← 远程跟踪分支，fetch 时更新
└── refs/remotes/origin/feat ← 同上，其他分支的快照

因此 git status 里的这句话：

text
Your branch is ahead of 'origin/main' by 2 commits.

含义是「你的 main 比上次通信时记录的 origin/main 多 2 个提交」，并不代表远端服务器此刻的真实状态。别人可能已经推了新提交，只是你还没 fetch。

clone、fetch、pull、push 各自做了什么 ​

命令作用是否改动工作区是否产生合并提交
git clone复制整个仓库 + 配置 origin + 检出默认分支是（创建文件）否
git fetch下载远端新对象，更新 origin/* 快照否否
git pullfetch + 合并（默认 merge，可配置为 rebase）是视情况
git push把本地提交上传到远端，并更新远端分支否否

记住一句话：pull = fetch + 集成。集成方式由配置决定，这也是事故高发区。

bash
# 只下载，不碰工作区。强烈建议在 pull 前先看一眼远端发生了什么
git fetch origin

# 看看远端比本地多了什么
git log --oneline HEAD..origin/main

# 看看本地比远端多了什么
git log --oneline origin/main..HEAD

第一次推送与上游分支 ​

本地新建的分支在远端并不存在，直接 git push 会报错：

text
fatal: The current branch feature/login has no upstream branch.

两种正确做法：

bash
# 方式一：推送并建立跟踪关系（推荐，只需一次）
git push -u origin feature/login

# 方式二：先设置上游，再推送
git branch --set-upstream-to=origin/feature/login
git push

建立上游后，git status 会显示领先/落后多少个提交，git push、git pull 也可以不带参数。

bash
# 查看所有分支的上游与领先/落后情况
git branch -vv
# * main          5eb9df3 [origin/main: ahead 2] feat: 新增搜索
#   feature/login 8b1e0d4 [origin/feature/login] fix: 登录态刷新

日常同步的正确顺序 ​

企业里最常见的坏习惯是：写代码 → 直接 git pull → 面对一堆冲突 → 慌。推荐顺序：

bash
# 1. 先把工作现场存起来或提交，保证工作区干净
git status
git stash push -u -m "wip: 登录页调整"

# 2. 只下载，不合并
git fetch origin

# 3. 看清差异再决定集成方式
git log --oneline --graph HEAD..origin/main

# 4. 集成（二选一，理由见第 13 章）
git merge origin/main        # 公共分支
git rebase origin/main       # 自己的功能分支

# 5. 恢复现场
git stash pop

git pull 只是第 2、4 步的合并写法。把两步拆开，你才有机会在合并前做判断。

pull 的两种集成方式 ​

bash
# 默认：fetch + merge，会产生合并提交（若双方都有新提交）
git pull

# 可选：fetch + rebase，把自己的本地提交重放到远端最新提交之后
git pull --rebase

# 全局配置（推荐给习惯线性历史的人）
git config --global pull.rebase true

# 更稳妥的配置：fast-forward 能快进就快进，否则 rebase
git config --global pull.ff only
git config --global pull.rebase true

pull.ff only 不是万能的

设置 pull.ff only 后，如果本地有独立提交，git pull 会直接失败并提示你显式选择 --rebase 或 --no-rebase。这是故意的：它逼你在改写历史与产生合并提交之间做一次明确决策，而不是由默认值替你决定。

推送被拒绝的三种真实原因 ​

text
! [rejected]        main -> main (fetch first)
! [rejected]        main -> main (non-fast-forward)
  1. 远端有你没有的提交（最常见）：先 fetch，再 merge/rebase，然后重新推送。
  2. 你改写了历史（rebase/amend 之后）：普通 push 会被拒绝，此时才考虑 --force-with-lease，并且只对自己的分支用。
  3. 分支保护规则：远端要求走 PR、要求线性历史或要求签名，push 会被服务端直接拒绝，需要改流程而不是加 --force。
bash
# 改写历史后的安全强推：远端若已变化则拒绝，避免覆盖同事的提交
git push --force-with-lease origin feature/login

# 绝对不要用的写法（会无条件覆盖远端）
# git push --force origin main

删除远程分支 ​

bash
# 删除远端分支（本地引用会在下次 fetch 时清理）
git push origin --delete feature/login

# 清理本地已不存在的远程跟踪分支
git fetch --prune
# 或者一次性配置
git config --global fetch.prune true

常见坑 ​

高频踩坑点

  1. 把 origin/main 当成远端实时状态：它只是上次 fetch 的快照。排查「远端有没有新提交」必须先 fetch。
  2. 在有未提交改动时 pull：Git 会拒绝合并或把改动搅乱。先提交或 stash。
  3. 对公共分支用 push --force：会抹掉同事已经推送的提交，且对方本地历史不会自动修复，善后成本极高。
  4. git pull 自动产生合并提交后直接推送：功能分支上会留下大量无意义的 merge commit，评审时噪声很大。功能分支优先 pull --rebase。
  5. 删了远程分支但本地还留着：git branch -vv 会显示 [origin/xxx: gone]，用 git branch -d 清理。

小结 ​

  • origin 只是远程仓库的别名，origin/main 是只读快照，不是实时状态。
  • pull = fetch + 集成，拆开执行才能在做决定前看清差异。
  • 新分支第一次推送用 git push -u 建立上游，之后可省略参数。
  • 公共分支用 merge，个人功能分支用 rebase，这是下一章要展开的核心决策。
  • 改写历史后只能用 --force-with-lease，永远不要对 main 无条件强推。
