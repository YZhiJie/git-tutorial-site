16 revert vs reset：线上代码如何回滚 ​

学习目标 ​

学完本章，你将能够：

  • 用一句话说清 revert 与 reset 的本质区别
  • 对单个提交、多个提交、合并提交执行正确的 revert
  • 解释「回滚一个合并提交后，为什么后续再合并会丢代码」
  • 判断线上事故该用 revert、reset 还是重新发版
  • 在必须重置时，选择影响面最小的 reset 模式

一句话区别 ​

revertreset
对历史追加一个反向提交移动分支指针，丢弃后面的提交
哈希原有提交不变被丢弃的提交从分支上消失
是否改写历史否是
已推送的分支能否用能，普通 push 即可不能，必须强推且会影响他人
适用对象已发布、已共享的提交本地、尚未推送的提交
text
revert：A---B---C---R    （R 抵消了 C 的改动，历史完整保留）
reset ：A---B            （C 直接从分支上消失）

核心规则

已经 push 到共享分支的提交，只能用 revert 回滚。reset 后再强推会改写公共历史，所有协作者都要手动修复本地仓库，且可能丢失他们未推送的工作。

revert 的基本行为 ​

bash
# 回滚最近一次提交
git revert HEAD

# 回滚指定提交（会打开编辑器让你确认提交信息）
git revert 8b1e0d4

# 不打开编辑器，直接用默认信息
git revert --no-edit 8b1e0d4

# 只应用反向改动，先不提交（适合批量回滚后合成一次提交）
git revert -n 8b1e0d4

revert 不是「删除提交」，而是计算该提交引入的差异，然后反向应用。如果后续提交又改了同一段代码，revert 可能冲突，需要手工解决：

bash
git revert 8b1e0d4
# CONFLICT (content): Merge conflict in src/api/client.ts

# 解决后
git add src/api/client.ts
git revert --continue

# 放弃
git revert --abort

回滚多个提交 ​

顺序很关键：从新到旧。

bash
# 假设要回滚 C、D、E 三个提交，E 最新
git revert --no-edit E D C

# 或者用区间（注意区间语义不包含起点，需用 C^）
git revert --no-edit C^..E

如果从旧到新回滚，后面的反向改动可能依赖已被抵消的代码，冲突会明显增多。

回滚合并提交：必须指定主线 ​

合并提交有两个父提交，Git 不知道你要保留哪条线：

bash
git revert -m 1 <merge-commit-hash>
  • -m 1 表示保留第一父提交（通常是合并时所在的分支，如 main）
  • -m 2 表示保留第二父提交（被合入的分支）

先确认父提交顺序：

bash
git show --no-patch --pretty=raw <merge-commit-hash>
# parent 3f2a1c9...   ← 第一父提交（main 侧）
# parent 8b1e0d4...   ← 第二父提交（feature 侧）

回滚合并提交的经典陷阱

用 git revert -m 1 回滚合并后，Git 会记录「这条分支的改动已经被拒绝」。之后即使你修复了问题、想把该分支再次合并，Git 也会认为改动已存在而不再引入，导致代码静默丢失。

正确做法二选一：

  1. 回滚后，先 revert 那个 revert（git revert <revert-commit>），恢复改动，再重新修复；
  2. 或者不 revert 合并提交，而是 revert 合并进来的那几个具体提交。

reset 的三种模式（仅限本地） ​

bash
git reset --soft HEAD~1    # 撤销提交，改动保留在暂存区
git reset --mixed HEAD~1   # 撤销提交，改动保留在工作区（默认）
git reset --hard HEAD~1    # 撤销提交，改动一并丢弃
模式HEAD暂存区工作区典型用途
--soft移动保留保留提交信息写错、想重新组织提交
--mixed移动清空保留想重新选择哪些文件进提交
--hard移动清空清空彻底放弃本地改动
bash
# 常见组合：撤销提交后重新拆成多个提交
git reset --soft HEAD~1
git restore --staged .
git add -p
git commit -m "refactor: 拆分用户模块"

--hard 之前先看一眼

bash
git status
git stash push -u -m "reset 前的备份"

即使忘了，git reflog 通常还能找回（第 20 章），但未提交的工作区改动不在 reflog 里，丢了就是丢了。

线上事故的决策流程 ​

text
错误提交是否已经发布/被他人拉取？
├── 是 → git revert（保留历史，普通 push）
│        ├── 单个提交 → git revert <hash>
│        ├── 连续多个 → 从新到旧依次 revert
│        └── 合并提交 → git revert -m 1 <hash>（注意再合并陷阱）
└── 否 → 本地尚未推送
         ├── 想保留改动 → reset --soft / --mixed
         └── 想彻底丢弃 → reset --hard（先 stash 或确认 reflog 可救）

还有一种情况常被忽略：发布包已经构建，但代码没问题，是配置错了。此时回滚代码往往不是最优解，应该回滚配置或重新发版。先定位问题层级，再选用工具。

revert 之后的发布节奏 ​

revert 只是让代码回到正确状态，不会自动触发一次发布。企业里要确认：

  1. revert 提交是否已合并进发布分支；
  2. CI 是否已基于新提交重新构建产物；
  3. 回滚后的版本号是否递增（避免 CDN / 客户端缓存旧产物）；
  4. 监控指标是否恢复，再关闭事故单。
bash
# 确认 revert 已进入发布分支
git log --oneline -5 origin/release/1.2

# 确认线上运行的提交
git rev-parse HEAD

常见坑 ​

  1. 对已推送分支 reset --hard 后强推：团队灾难，必须改用 revert。
  2. 回滚合并提交后直接再次合并：代码静默丢失，需要先 revert 那个 revert。
  3. 多个提交从旧到新 revert：冲突剧增，正确顺序是新到旧。
  4. revert 后以为线上自动恢复：还需要重新构建、发布、验证。
  5. reset --hard 前没看 git status：未跟踪文件和未提交改动不会被 reflog 记录。
  6. 把 revert 当成「删除历史」：它只是追加反向提交，历史里仍然能看到错误提交，这是特性不是缺陷。

小结 ​

  • revert 追加反向提交，安全用于已共享历史；reset 移动指针，只适合本地未推送提交。
  • 回滚多个提交从新到旧；回滚合并提交用 -m 1，并警惕后续再合并丢代码。
  • reset 三模式的区别在于暂存区和工作区是否保留，--hard 风险最高。
  • 线上事故优先 revert + 重新发布，而不是改写历史。
  • 回滚完成后要验证发布链路和监控，代码回滚不等于事故结束。
