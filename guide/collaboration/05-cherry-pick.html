15 cherry-pick：精准搬运提交 ​

学习目标 ​

学完本章，你将能够：

  • 说清 cherry-pick 与 merge、rebase 的本质区别
  • 挑单个提交、多个提交、连续区间提交到当前分支
  • 用 -x 记录来源、-n 控制是否提交、-e 修改信息
  • 正确处理 cherry-pick 冲突、空提交和重复提交
  • 判断什么时候不该用 cherry-pick，而应该合并或回滚

它到底做了什么 ​

git cherry-pick <commit> 的含义是：把那个提交引入的差异，重新应用到当前 HEAD 上，并生成一个新提交。

text
       C---D feature
      /
 A---B---E main（HEAD）
bash
git switch main
git cherry-pick D
text
       C---D feature
      /
 A---B---E---D' main（HEAD）

注意三点：

  1. 只搬运 D 这一个提交的改动，C 不会跟过来。
  2. 生成的是新提交 D'，哈希与 D 不同。
  3. 如果 D 的改动依赖 C，就会冲突甚至编译失败——这是 cherry-pick 最常见的翻车原因。

与 merge / rebase 的定位差异

  • merge：把整条分支的历史并入当前分支。
  • rebase：把当前分支的提交搬到另一条分支上。
  • cherry-pick：从别处摘一个或几个提交过来，不建立任何分支关系。

基本用法 ​

bash
# 单个提交
git cherry-pick 8b1e0d4

# 多个不连续提交（按命令行顺序依次应用）
git cherry-pick 8b1e0d4 2a9c7f1

# 连续区间：A..B 表示「A 之后、B 之前（含 B）」，不包含 A
git cherry-pick 3f2a1c9..9c1b7f0

# 想包含起始提交 A，用 A^..B
git cherry-pick 3f2a1c9^..9c1b7f0

区间方向容易记错，记住：Git 的 A..B 语义统一是「可达 B 但不可达 A」。

三个高频参数 ​

-x：记录来源 ​

bash
git cherry-pick -x 8b1e0d4

提交信息末尾会自动追加：

text
(cherry picked from commit 8b1e0d4a7c1f3e2b9d6a5c4e8f7b1d2a3c4e5f60)

这在 hotfix 回灌时非常重要：三个月后有人看到两个分支上相同的改动，能立刻知道哪个是源头。企业规范里通常强制 hotfix 使用 -x。

-n：只应用改动，不提交 ​

bash
# 把多个提交的改动合并成一次提交
git cherry-pick -n 8b1e0d4 2a9c7f1
git status
git commit -m "fix: 合并两个 hotfix 到 release"

-n 会把改动放进暂存区，适合「需要重新组织提交边界」的场景。

-e：应用前修改提交信息 ​

bash
git cherry-pick -e 8b1e0d4

比如从 main 摘提交到 release/1.2 时，把信息里的版本号改掉。

冲突处理 ​

cherry-pick 和 rebase 一样是逐个应用，冲突时：

bash
git cherry-pick 8b1e0d4
# CONFLICT (content): Merge conflict in src/config.ts
# error: could not apply 8b1e0d4... feat: 新增开关

# 1. 解决冲突
git add src/config.ts

# 2. 继续
git cherry-pick --continue

# 3. 跳过这个提交
git cherry-pick --skip

# 4. 放弃整个操作，回到开始前
git cherry-pick --abort

冲突时 ours / theirs 的方向

cherry-pick 中 ours 是当前分支，theirs 是被摘取提交的内容，与 merge 一致。但因为是「应用差异」而不是「合并两条历史」，复杂冲突建议直接手工编辑，不要依赖 --theirs 整份覆盖。

空提交与重复提交 ​

如果目标分支已经包含同样的改动，cherry-pick 会得到：

text
The previous cherry-pick is now empty, possibly due to conflict resolution.

处理方式：

bash
# 确认改动确实已存在，跳过
git cherry-pick --skip

# 或者确实想保留一个空提交（极少见）
git cherry-pick --allow-empty

更隐蔽的问题是重复改动：同一修复被 cherry-pick 到多个分支后，这些分支再合并回主干时，Git 可能认为是两处独立修改，从而产生冲突或重复代码。这也是为什么需要 -x 留痕，以及在合并前用 git log --grep 排查。

bash
# 检查某修复是否已在当前分支
git log --oneline --grep="修复登录超时"

典型适用场景 ​

场景是否适合 cherry-pick
把 main 上的紧急修复同步到 release 分支适合，配合 -x
误提交到 develop，想搬到正确的 feature 分支适合，搬完再在原分支回退
从废弃分支里抢救一两个有价值的提交适合
把整个功能分支合入主干不适合，用 merge / PR
两条长期并行分支互相同步不适合，用 merge，否则重复提交会失控
已经合并过的提交再摘一次不适合，先确认是否已存在

企业里的一条硬规则 ​

cherry-pick 只用于「单向、少量、有明确来源」的同步；不要用它替代分支合并。

原因：

  • cherry-pick 不建立任何关系，Git 不知道两个提交是同一改动。
  • 摘得越多，后续合并冲突越难推理。
  • 长期双向 cherry-pick 会让两条分支的历史彻底失去可比性。

如果发现自己每周都在 cherry-pick 同一批提交，说明分支模型有问题，应该回到第 19 章重新选型。

常见坑 ​

  1. 摘取依赖其他提交的改动：编译能过但运行报错，或直接冲突。摘之前先 git show <commit> 看它依赖什么。
  2. 忘记 -x：几个月后无法追溯来源，code review 时被质疑重复代码。
  3. 在 cherry-pick 冲突中用 --skip 跳过：会静默丢弃整个提交的改动。
  4. 把合并提交直接 cherry-pick：需要 -m 1 指定主线父提交，且结果往往不符合预期，优先考虑 revert 或重新实现。
  5. 摘完不删原提交：同一改动留在两条分支上，后续合并产生重复。

小结 ​

  • cherry-pick 把指定提交的差异重新应用到当前分支，生成新哈希，不建立分支关系。
  • 支持单提交、多提交、A..B 区间；-x 留痕、-n 不提交、-e 改信息。
  • 冲突处理与 rebase 类似：--continue / --skip / --abort。
  • 适合 hotfix 回灌、误提交转移、抢救个别提交；不适合替代常规分支合并。
  • 企业规范：hotfix 回灌必须带 -x，且保持单向、少量。
