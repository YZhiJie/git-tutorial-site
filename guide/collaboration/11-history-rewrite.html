29 历史重写与脱敏：filter-repo 的正确用法 ​

有些东西不该留在仓库里：误提交的密钥、几十 MB 的构建产物、从别的项目带过来的目录。git rm 只能删掉「现在」，历史里还在，任何人 git log -p 都能翻出来。要把它们从所有历史里拿掉，就得改写历史。

改写历史不是「删一个文件」这么轻。它会让被改提交之后的所有提交换哈希，所有分支、标签、PR、fork、CI 缓存都会跟着失效。本章讲清楚该用什么工具、怎么把风险控制住。

学习目标 ​

  • 理解「改写一个提交 = 重写它所有后代」的连锁反应。
  • 知道 filter-branch、BFG、git filter-repo 各自的边界，默认选后者。
  • 能用 filter-repo 完成删目录、删大文件、替换敏感字符串、迁移子目录。
  • 能设计一次可回滚、可通知、可验证的历史脱敏流程。
  • 明白密钥泄露时「改写历史」只是补救的一半，另一半是吊销并轮换。

为什么删一个文件会改写整条历史 ​

提交对象的哈希由 tree、parent、author、message 等内容算出。你从某个历史提交里删掉一个文件，这个提交的 tree 就变了，哈希随之变化；它的子提交 parent 指向新哈希，于是子提交也要重算；一路传到最后，被改提交之后的每个提交哈希都变。

只有被改提交之前的祖先保持不变，因此新旧历史有一段公共前缀。

工具选型：别再手写 filter-branch ​

工具现状能力建议
git filter-branch官方已不推荐，慢且易错通用但脚本复杂只在老环境无其他选择时用
BFG Repo-Cleaner第三方 Java 工具删大文件、替换文本，速度快简单场景可用，但功能有限
git filter-repoGit 官方推荐路径、内容、子目录、标签全支持默认首选

filter-repo 是独立脚本（Python），不在 Git 发行包里：

bash
# macOS
brew install git-filter-repo
# 或用 pip
python3 -m pip install git-filter-repo

git filter-repo --version

先做镜像备份

filter-repo 默认会删掉 origin 远程，防止你手滑直接推送。执行前务必：

bash
git clone --mirror git@github.com:org/repo.git repo-backup.git

备份仓是裸仓，包含所有 ref、tag 和 reflog 之外的对象，是唯一可靠的后悔药。

四种常见改写任务 ​

任务一：把一个目录从历史中彻底删除 ​

bash
git clone --mirror git@github.com:org/app.git app-rewrite.git
cd app-rewrite.git

# 删除 legacy/ 目录的全部历史
git filter-repo --path legacy/ --invert-paths

# 也支持 glob 与正则
git filter-repo --path-glob '*.min.js' --invert-paths
git filter-repo --path-regex '^docs/old/.*' --invert-paths

--invert-paths 表示「保留除匹配项以外的所有路径」。不加它则是「只保留匹配项」。

任务二：删除超过阈值的大文件 ​

bash
git filter-repo --strip-blobs-bigger-than 10M

它按 blob 大小过滤，比按文件名更稳：同一个 200 MB 的二进制可能被复制成多个路径，逐个删路径容易漏。

任务三：替换历史中的敏感字符串 ​

准备一个替换规则文件：

text
# replacements.txt
literal:AKIAIOSFODNN7EXAMPLE==>***REMOVED***
literal:ghp_xxxxxxxxxxxxxxxxxxxx==>***REMOVED***
regex:postgres://[^ ]+==>postgres://***REMOVED***
bash
git filter-repo --replace-text replacements.txt

literal: 前缀表示普通字符串，regex: 表示正则。替换会作用于所有 blob 内容，包括已经删除的文件。

任务四：把子目录拆成独立仓库 ​

bash
# 在 monorepo 镜像里，只保留 packages/core，并把它提到根目录
git filter-repo --path packages/core/ --path-rename packages/core/:

--path-rename 的冒号左边是旧路径，右边是新路径。右边留空表示提到仓库根。

反过来，把独立仓库并入 monorepo：

bash
git filter-repo --to-subdirectory-filter packages/core

验证：不要相信「应该删干净了」 ​

bash
# 1. 全历史搜敏感串（对象库层面）
git grep 'AKIAIOSFODNN7EXAMPLE' $(git rev-list --all) -- || echo "clean"

# 2. 检查最老的几个提交里是否还有目标路径
git log --all --oneline -- legacy/ | head

# 3. 检查对象库完整性
git fsck --full

# 4. 查看仓库体积变化
git count-objects -vH

# 5. 列出所有 ref，确认分支和标签数量与预期一致
git for-each-ref --format='%(refname)' | sort

git grep <rev-list> 的方式会对每个提交跑一次，仓库大时较慢；可以用 git rev-list --all | git cat-file --batch 管道，或者直接信任 filter-repo 的 --replace-text 并抽查关键提交。

密钥泄露：改写历史只是补救的一半 ​

如果泄露的是生产密钥，顺序必须是：

  1. 立刻吊销/轮换密钥，不要等历史清理完。攻击者可能已经拿到。
  2. 评估影响范围：审计日志、账单、异常调用。
  3. 清理历史，避免后来者继续复制。
  4. 加防护：secret scanning、pre-commit 钩子、CI 拦截。

只改写历史不轮换，等于把泄露的钥匙从门口挪到地毯下面。

团队协作成本 ​

影响面具体表现应对
本地分支旧分支基于旧历史，推送会被拒全员重新 clone，或 reset --hard 到新远端
开放 PR目标分支历史变了，diff 混乱窗口内合并或关闭，改写后重开
fork旧 fork 仍含敏感对象通知删除重建，平台侧清理缓存
CI 缓存基于旧 commit sha 的缓存全部失效接受一次冷启动
标签旧标签仍指向旧历史用 --mirror 一并更新，或重打
子模块引用父项目 gitlink 指向旧哈希同步更新父项目

改写窗口要短

选业务低峰，提前公告，冻结合并，一次推完。拖成「今天改一点明天改一点」会让所有人反复重建本地仓库。

常见坑 ​

坑后果正确做法
直接在原工作仓跑 filter-repo无法对比、无法回滚先 clone --mirror 到副本
忘了删 origin 就直接推可能推错远端filter-repo 默认删远端，推送时显式写 URL
只删当前分支的文件历史仍在用 filter-repo 扫全 ref
filter-branch 后没清 refs/original旧对象残留，体积不降filter-repo 会自动清理；手写脚本要手动删
强推后没通知同事推送失败、重复解冲突提前公告并给重建步骤
只改写不加防护下次又泄露secret scanning + 钩子 + 培训
密钥泄露只清历史不轮换密钥仍可用先轮换，再清理

小结 ​

  • 改写历史 = 重写改写点之后的所有提交，哈希全变，协作面全部受影响。
  • 默认用 git filter-repo：路径、glob、正则、大文件、文本替换、子目录迁移都覆盖。
  • 流程固定：镜像备份 → 副本改写 → 本地验证 → 通知冻结 → --mirror 强推。
  • 密钥泄露的第一动作是吊销轮换，不是删历史。
  • 改写完成后补上防护，否则同样的事会再来一次。
