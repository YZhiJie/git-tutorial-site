28 rebase 深水区：--onto、--rebase-merges 与 --update-refs ​

基础 rebase 解决“把分支挪到最新主干”。真实团队里更常见的是：只搬一段提交、保留 merge 拓扑、重写时同步多条栈式分支。这三个问题分别对应 --onto、--rebase-merges、--update-refs。

学习目标 ​

  • 准确使用 --onto <newbase> <upstream> <branch>，不再把参数顺序记反。
  • 判断什么时候需要保留 merge 拓扑，什么时候应该压平。
  • 用 --update-refs 安全重写栈式分支。
  • 用 range-diff 验证重写前后补丁是否等价。

--onto：只搬“两个基点之间”的提交 ​

先把三个参数拆开：

bash
git rebase --onto <newbase> <upstream> <branch>
  • <upstream>：旧基线的末端，不包含在搬运范围内；
  • <branch>：要移动的分支；
  • <newbase>：这些提交的新落点。

真正被重放的是 <upstream>..<branch> 这段提交。

bash
# 把 feature 从旧 main 挪到新 main
git rebase --onto main old-base feature

# 等价于：把 old-base..feature 的提交重放到 main
git range-diff old-base..feature main..feature   # 重写前后对比

常见误用是把顺序写成 git rebase --onto feature main old-base。记住一句话：先定“搬完落在哪”，再定“从哪之后开始搬”，最后才是“搬谁”。

--rebase-merges：保留 merge 拓扑 ​

默认 rebase 会把 merge 压平成一条线。对于需要保留“功能分支内部合并”的团队，这会让历史失去结构。

bash
git rebase --rebase-merges --onto main old-base feature

交互式 rebase 的清单会从一串 pick 变成 label、reset、merge 的组合：

text
label onto
reset onto
pick F1
pick F2
label feature-1
reset onto
pick G1
merge -C M feature-1

不要手工改这些结构，除非你清楚每一步在重建哪个节点。

--update-refs：栈式分支一起搬 ​

栈式 PR（feature/a → feature/b → feature/c）在 rebase 后，中间分支的引用也需要更新：

bash
git rebase --update-refs main

autosquash、fork-point 与 backend ​

bash
git commit --fixup=<hash>          # 生成 fixup! 提交
git rebase -i --autosquash main    # 自动排到目标提交后面并标为 fixup
git config --global rebase.autoSquash true

--fork-point 会在 upstream 的 reflog 里找“分叉点”，适合 upstream 被 force-push 过的场景；但 CI 里通常是全新 clone，没有 reflog，行为会退化。不要把它当成默认必选项。

bash
git rebase --fork-point main
git rebase --merge                 # 强制 merge backend
git rebase --apply                 # 旧 apply backend，通常不需要

merge backend 更擅长处理重命名、冲突和 merge 拓扑；apply backend 基于补丁，行为更“机械”。现代 Git 默认已经是 merge backend。

收尾与验证 ​

bash
git add <file> && git rebase --continue
git rebase --skip                  # 当前提交已被上游包含
git rebase --abort                 # 回到开始前

git range-diff old-base..old-tip new-base..new-tip

range-diff 会把旧序列与新序列配对，告诉你“哪些补丁原样保留、哪些改动了”。重写后不要只看 git diff，要看 range-diff。

安全网 ​

  • rebase 前建备份分支：git branch backup/pre-rebase。
  • ORIG_HEAD 记录 rebase 开始前的位置，但只有一份，会被下一次危险操作覆盖。
  • 真正可靠的是 reflog；救援时先记绝对哈希。
  • 推送用 --force-with-lease，不要用裸 --force。

常见坑 ​

坑表现正确做法
--onto 参数顺序记反搬到错误基线，历史大乱新基 → 旧基 → 分支
以为 --rebase-merges 是默认merge 拓扑被压平需要保留时显式加参数
栈式分支只推最上层中间 PR base 指向旧提交--update-refs + 逐个推送
CI 上用 --fork-point找不到 reflog，分叉点错误CI 用显式 upstream 或 fetch-depth: 0
rebase 中途切分支状态混乱、后续命令行为异常先 --abort，再切
重写后直接 push --force覆盖同事提交--force-with-lease，先 fetch

小结 ​

  • --onto 的本质是“把 upstream..branch 重放到 newbase”，参数顺序是理解的关键。
  • 默认 rebase 压平 merge；需要保留拓扑时用 --rebase-merges。
  • 栈式分支重写必须配合 --update-refs，否则中间引用会断。
  • 重写后用 range-diff 验证补丁等价性，用 reflog/备份分支兜底。
