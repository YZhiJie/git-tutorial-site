17 rerere：让 Git 记住你的解法 ​

学习目标 ​

学完本章，你将能够：

  • 说清 rerere 的名字来源与它解决的问题
  • 开启 rerere.enabled 与 rerere.autoupdate，观察 Git 自动复用冲突解法
  • 在长期分支、反复 rebase 的场景中用 rerere 节省重复劳动
  • 判断哪些冲突 rerere 帮不上忙
  • 了解团队共享 rr-cache 的收益与风险

名字就是它的全部含义 ​

rerere = reuse recorded resolution（复用已记录的冲突解法）。

默认情况下，同一个冲突你解决一次，下次遇到还得再解决一次。典型场景：

  • 长期功能分支每周 rebase 一次 main，每次都在同一处冲突；
  • 同一个 hotfix 要 cherry-pick 到 5 个 release 分支；
  • 团队成员反复遇到同一段代码的合并冲突。

rerere 会在你解决冲突时，记录「冲突前长什么样 → 你解决后长什么样」，下次遇到完全相同的冲突块时自动套用。

bash
# 开启（只需一次）
git config --global rerere.enabled true

# 可选：自动把解好的文件加入暂存区
git config --global rerere.autoupdate true

一次完整演示 ​

bash
git config --global rerere.enabled true

# 第一次遇到冲突，正常解决
git merge feature
# CONFLICT (content): Merge conflict in src/config.ts
# 编辑文件，删掉冲突标记
git add src/config.ts
git commit --no-edit
# Recorded resolution for 'src/config.ts'.

注意最后一行 Recorded resolution，说明解法已存入 .git/rr-cache/。

回退到合并前，再执行一次同样的合并：

bash
git reset --hard HEAD^
git merge feature
# CONFLICT (content): Merge conflict in src/config.ts
# Resolved 'src/config.ts' using previous resolution.

打开文件，冲突标记已经消失，内容与上次解法完全一致。你只需要：

bash
git add src/config.ts
git commit --no-edit

如果开启 rerere.autoupdate，连 git add 都省了，直接 git commit。

rebase 场景收益最大

git rebase main 每次都会重放提交，长期分支上同一冲突可能反复出现。开启 rerere 后，第二次开始基本无感。配合第 14 章的交互式 rebase，可以大幅降低维护成本。

查看与清理记录 ​

bash
# 列出已记录的冲突路径
git rerere status

# 查看某个冲突的解法差异
git rerere diff

# 忘记记录时的补救：手动标记为已解决
git rerere

# 清空所有记录（谨慎，通常不需要）
rm -rf .git/rr-cache

rr-cache 里存的是冲突块的哈希和对应文件版本，不包含完整仓库内容，体积通常很小。

团队共享 rr-cache 的取舍 ​

rr-cache 位于 .git/ 下，默认不随仓库分发。团队可以把它提交到仓库（或通过 CI 缓存同步），让所有人共享解法。

收益：

  • 新人遇到历史遗留的反复冲突时，能直接复用老同事的解法；
  • 大重构期间，多人 rebase 同一分支的冲突处理成本下降。

风险：

  • 解法可能过时：代码语义变了，旧解法机械套用会引入错误；
  • 冲突块哈希相同不代表上下文相同，自动套用后仍必须 review；
  • 把 .git 内部结构纳入版本管理，需要团队对流程有共识。

自动复用不等于自动正确

rerere 只匹配冲突块的文本形态，不理解业务语义。开启 autoupdate 后，错误解法会被自动暂存，提交前必须 git diff --staged 检查。

rerere 帮不上忙的情况 ​

  • 语义冲突：文本不冲突，合并后行为错误——rerere 无从记录。
  • 冲突块有细微差异：多一个空格、上下文行不同，哈希就变了，无法命中。
  • 冲突范围变化：上次冲突 3 行，这次 5 行，视为不同冲突。
  • 跨语言的合并策略冲突：二进制文件、生成代码的冲突需要人工或工具处理。

与其它工具的配合 ​

bash
# 推荐组合：rerere + merge.conflictStyle=diff3
git config --global merge.conflictStyle diff3
git config --global rerere.enabled true
git config --global rerere.autoupdate true

diff3 让首次解决时能看到 base，做出更准确的判断；rerere 负责后续复用。两者不冲突。

如果团队使用 git mergetool，rerere 依然生效——它记录的是最终写入工作区的内容，与解决方式无关。

常见坑 ​

  1. 以为开了 rerere 就万事大吉：它只在完全相同的冲突块上生效。
  2. autoupdate 后不检查直接提交：可能把过时解法提交上线。
  3. 在多个仓库间手动拷贝 rr-cache：路径与冲突哈希可能不匹配，收益有限。
  4. 清理 .git 时误删 rr-cache：解法记录丢失，但不会影响仓库完整性。
  5. 把 rerere 当成冲突预防：它只是复用解法，减少冲突要靠小提交、勤同步、清晰的分支边界。

小结 ​

  • rerere 记录并复用「相同冲突块」的解法，名字即 reuse recorded resolution。
  • 开启只需 rerere.enabled true，配合 autoupdate 可自动暂存。
  • 长期分支反复 rebase、同一修复多次 cherry-pick 时收益最大。
  • 自动复用必须人工 review，语义正确性不能交给工具。
  • 真正的冲突治理仍是：小步提交、频繁同步、明确的分支职责。
