12 冲突的本质：三方合并 ​

学习目标 ​

学完本章，你将能够：

  • 用「基准（base）— 我方（ours）— 对方（theirs）」三方模型解释冲突从哪来
  • 读懂 <<<<<<< / ======= / >>>>>>> 冲突标记，并判断保留哪一侧
  • 独立完成一次完整的冲突解决：定位 → 编辑 → 暂存 → 提交
  • 使用 merge --abort、--ours / --theirs、mergetool 处理复杂冲突
  • 说清「为什么 Git 不自动选一个」而不是盲目接受某一方

冲突不是 Git 的 bug，是信息不足 ​

Git 合并两个分支时，并不是简单比较「A 文件和 B 文件哪里不一样」，而是找到两条分支的共同祖先，做一次三方比较：

text
             base（共同祖先）
            /                \
    ours（当前分支）      theirs（被合并分支）
            \                /
              → 合并结果
  • 只有 ours 改了某一行 → 采用 ours
  • 只有 theirs 改了某一行 → 采用 theirs
  • 两边都改了同一区域，且改法不同 → Git 无法判断谁的意图正确 → 冲突（conflict）

关键点：冲突的判定单位是「重叠的修改区间」，不是整行文件。两个人改同一文件的不同段落，通常不会冲突；改同一段落的相邻行，就可能冲突。

bash
# 制造一个最小冲突
mkdir demo && cd demo && git init -b main
printf "line 1\nline 2\nline 3\n" > app.txt
git add app.txt && git commit -m "chore: init"

git switch -c feature
printf "line 1\nline 2-feature\nline 3\n" > app.txt
git commit -am "feat: feature 修改第二行"

git switch main
printf "line 1\nline 2-main\nline 3\n" > app.txt
git commit -am "fix: main 修改第二行"

git merge feature
# Auto-merging app.txt
# CONFLICT (content): Merge conflict in app.txt
# Automatic merge failed; fix conflicts and then commit the result.

冲突标记怎么读 ​

打开 app.txt，会看到：

text
line 1
<<<<<<< HEAD
line 2-main
=======
line 2-feature
>>>>>>> feature
line 3
标记含义
<<<<<<< HEAD冲突开始，下面是当前分支（ours）的内容
=======分隔线，上下两种版本
>>>>>>> feature冲突结束，上面是被合并分支（theirs）的内容

解决冲突的本质就是：把这三个标记删掉，写出一段你认为正确的最终内容。可以是保留一侧、合并两侧、或者写出全新的第三版。

text
line 1
line 2-main-and-feature   ← 融合双方意图，而不是二选一
line 3

一次完整的解决流程 ​

bash
# 1. 看哪些文件冲突了
git status
# both modified:   app.txt

# 2. 逐个编辑，删掉冲突标记，写出最终内容
#    （编辑器里搜索 <<<<<<< 可以快速定位全部冲突点）

# 3. 标记为已解决（暂存即代表「这个文件的冲突我处理完了」）
git add app.txt

# 4. 确认所有冲突都已解决
git status
# All conflicts fixed but you are still merging.

# 5. 完成合并，生成合并提交
git commit              # 会打开编辑器，可修改默认的 Merge 信息
# 或者
git commit --no-edit    # 直接使用默认信息

不要在冲突未解决时 commit -a

git commit -a 会跳过暂存区确认，容易把还带着 <<<<<<< 标记的文件提交进去。冲突期间用 git status 确认没有 unmerged 文件再提交。

中途想放弃这次合并：

bash
git merge --abort     # 回到合并前状态，工作区改动一并回退

多文件冲突与冲突类型 ​

git status 会用不同状态区分冲突原因：

状态含义典型场景
both modified双方都改了内容最常见的文本冲突
both added双方都新增了同名文件两人同时创建同名模块
deleted by us我方删除、对方修改重构删文件 vs 别人继续改
deleted by them对方删除、我方修改同上，方向相反

对 deleted by us/them，你要做的是产品决策：文件到底该不该存在。保留就 git add，删除就 git rm。

bash
# 保留对方版本的文件
git add path/to/file

# 确认要删除
git rm path/to/file

只想要某一方的整份文件 ​

当整个文件都该采用某一侧时，不必手工编辑：

bash
# 采用当前分支（ours）的版本
git checkout --ours path/to/file
git add path/to/file

# 采用被合并分支（theirs）的版本
git checkout --theirs path/to/file
git add path/to/file

# Git 2.23+ 的新写法
git restore --ours path/to/file
git restore --theirs path/to/file

--ours / --theirs 在 rebase 中会反转

执行 git rebase 时，Git 是把你自己的提交逐个重放到目标分支上。此时：

  • ours 指的是目标分支（也就是你 rebase 到的那个分支）
  • theirs 指的是你正在重放的提交

这与 merge 时的直觉相反。冲突时先 git status 看清当前处于 merge 还是 rebase，再决定用哪一侧。

可视化工具：mergetool ​

手工编辑适合小冲突，大文件建议用三方合并工具：

bash
# 配置 VS Code 作为合并工具
git config --global merge.tool vscode
git config --global mergetool.vscode.cmd 'code --wait --merge $REMOTE $LOCAL $BASE $MERGED'

# 启动
git mergetool

常见的三方工具还有 vimdiff、kdiff3、Beyond Compare、IntelliJ 内置合并器。它们都会同时展示 base / ours / theirs 三个版本，比在冲突标记里猜意图可靠得多。

更细的冲突上下文：diff3 ​

默认冲突标记只显示两侧，不显示祖先版本。开启 diff3 风格后能看到 base：

bash
git config --global merge.conflictStyle diff3
text
<<<<<<< HEAD
line 2-main
||||||| 3f2a1c9
line 2
=======
line 2-feature
>>>>>>> feature

多出来的 ||||||| 段就是共同祖先。当你不知道双方为什么这么改时，这一行往往能帮你还原意图。

冲突解决后如何验证 ​

解决冲突不是「标记删干净」就结束了，必须验证行为：

bash
# 看最终差异是否符合预期
git diff --staged

# 跑测试 / 构建（冲突常导致语法正确但语义错误）
pnpm test
pnpm build

语义冲突比文本冲突更危险

两个人分别改了同一个函数的调用方和实现，文本上可能完全不冲突，合并后却能编译通过、运行报错。文本冲突 Git 能提示，语义冲突只能靠测试。合并后必须跑一遍相关测试。

常见坑 ​

  1. 看到冲突就 --abort：冲突往往只是需要一次判断，逃避会让分支永远合不进去。
  2. 只保留一侧而不读另一侧：容易把同事的功能静默删掉，评审时也很难发现。
  3. 删掉标记但没 git add：Git 仍认为文件未解决，commit 会失败。
  4. 在 rebase 中用 merge 的 ours/theirs 直觉：方向是反的，务必先确认当前操作类型。
  5. 解决完不跑测试：文本冲突解决了，语义冲突还在。

小结 ​

  • 冲突来自三方合并中「同一区域被双方以不同方式修改」，Git 缺少判断意图的信息。
  • 冲突标记的 HEAD 一侧是当前分支，另一侧是被合并分支；rebase 时方向相反。
  • 解决流程固定为：编辑 → git add → git commit，中途可 git merge --abort。
  • 整份文件取舍用 --ours / --theirs，复杂冲突用 mergetool 看三方视图。
  • 冲突解决后必须跑测试，文本合并不等于语义正确。
