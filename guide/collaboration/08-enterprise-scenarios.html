18 企业级实战：六个真实冲突场景 ​

学习目标 ​

学完本章，你将能够：

  • 在六类高频协作事故中，快速判断该用 merge、rebase、cherry-pick 还是 revert
  • 按「先备份、再操作、后验证」的顺序处理，避免二次事故
  • 写出可以直接贴进团队 runbook 的操作步骤
  • 识别每个方案的风险边界，知道什么时候必须停下来沟通

阅读方式 ​

每个场景按同一结构展开：

  1. 背景：真实团队里怎么发生的
  2. 错误示范：最常见的错误处理，以及它为什么危险
  3. 正确操作：带逐行注释的命令序列
  4. 分支图：操作前后的历史形态
  5. 复盘：这个场景真正的教训

统一前置动作

下面所有场景都默认先做两件事：

bash
git status                 # 确认工作区状态
git fetch origin           # 拿到远端最新快照

不看 status 就操作，是二次事故的第一大来源。

场景一：两个人改了同一个文件 ​

背景 ​

小王和小李同时改 src/utils/date.ts。小王先推送，小李本地已有一个提交，直接 git pull 后产生合并提交，PR 里出现一条无意义的 Merge branch 'main'。

错误示范 ​

bash
# 错误一：直接 pull，产生合并提交，历史变乱
git pull

# 错误二：推送被拒后无脑强推，覆盖小王的提交
git push --force origin feature/date-format

错误二的后果最严重：小王的提交从远端消失，但他的本地仓库仍认为自己推送成功，下一次推送会把冲突带回来，且难以定位。

正确操作 ​

bash
# 1. 确认当前在自己的功能分支
git branch --show-current
# feature/date-format

# 2. 提交本地改动，保证工作区干净
git add src/utils/date.ts
git commit -m "feat: 支持自定义日期格式"

# 3. 只下载，不合并
git fetch origin

# 4. 把自己的提交重放到最新 main 之上
git rebase origin/main
# CONFLICT (content): Merge conflict in src/utils/date.ts

# 5. 打开文件，删掉冲突标记，保留双方意图
#    <<<<<<< HEAD         → main 上小王的实现
#    =======              → 自己刚才的提交
#    >>>>>>> 8b1e0d4      → 当前重放的提交

# 6. 标记已解决，继续重放
git add src/utils/date.ts
git rebase --continue

# 7. 跑测试，确认语义正确
pnpm test -- date

# 8. 安全强推（远端若有新提交会被拒绝）
git push --force-with-lease origin feature/date-format

分支图 ​

text
操作前：
  A---B---C---D main（小王已推送）
       \
        E---F feature/date-format（小李本地，基于 B）

rebase 后：
  A---B---C---D main
               \
                E'---F' feature/date-format

推送后远端：
  A---B---C---D---E'---F'  （线性，无合并提交）

复盘 ​

  • 功能分支用 rebase，主干用 merge，这条规则能消掉 80% 的历史噪声。
  • 冲突解决后必须跑测试：date.ts 的文本冲突可能合并出语法正确但语义错误的代码。
  • --force-with-lease 是强推的最低安全线，团队应把 --force 加入命令黑名单。

场景二：功能分支落后主干，merge 还是 rebase ​

背景 ​

feature/checkout 开发了两周，main 已前进 30 个提交。现在要决定怎么同步。团队里有人主张「直接 merge main 进来省事」，有人主张 rebase。

先问三个问题 ​

问题答案影响
这条分支只有你在用吗？否 → 只能 merge
分支已经 push 且有人基于它开发吗？是 → 只能 merge
团队要求 PR 保持线性历史吗？是 → rebase（且分支必须私有）

错误示范 ​

bash
# 在共享分支上 rebase，同事本地历史全部失效
git switch feature/checkout
git rebase origin/main
git push --force origin feature/checkout

同事第二天 git pull 会看到重复提交，必须 git reset --hard origin/feature/checkout，未推送的工作全丢。

正确操作（个人分支：rebase） ​

bash
# 1. 先备份，出问题可一键回到 rebase 前
git branch backup/checkout-$(date +%Y%m%d)

# 2. 同步远端
git fetch origin

# 3. 重放提交
git switch feature/checkout
git rebase origin/main

# 4. 逐个解决冲突
git status
git add <file>
git rebase --continue
# 若某个提交已被 main 实现，可 git rebase --skip

# 5. 验证
pnpm test && pnpm build

# 6. 安全强推
git push --force-with-lease origin feature/checkout

# 7. 确认同事没有基于旧哈希开发后，删除备份
git branch -D backup/checkout-20261022

正确操作（共享分支：merge） ​

bash
git switch feature/checkout
git merge origin/main
# 解决冲突后
git add <file>
git commit --no-edit
git push

分支图 ​

text
个人分支 rebase：
  main:    A---B---C---D---E---F
                     \
  feature:            X---Y---Z  → 重放为 X'---Y'---Z'（接在 F 后）

共享分支 merge：
  main:    A---B---C---D---E---F
                     \           \
  feature:            X---Y---Z---M  （M 是合并提交）

复盘 ​

  • 判断依据不是「哪种历史好看」，而是「有没有别人依赖这条分支」。
  • rebase 前打备份分支成本几乎为零，却能省掉一次事故。
  • 共享分支 merge 产生的合并提交不是脏，而是必要的协作记录。

场景三：提交到了错误的分支 ​

背景 ​

小张本该在 feature/payment 上开发，却直接在 develop 上提交了两次，并且已经 push 了一次。

错误示范 ​

bash
# 直接 reset --hard 再强推 develop
git reset --hard HEAD~2
git push --force origin develop

develop 是公共集成分支，强推会让所有同事的本地分支与远端分叉，且可能覆盖别人的提交。

正确操作（提交尚未推送） ​

bash
# 1. 记住两个提交的哈希
git log --oneline -3
# 9c1b7f0 feat: 支付回调校验
# 8b1e0d4 feat: 支付下单接口
# 3f2a1c9 chore: 初始化

# 2. 切到正确分支，把提交摘过去
git switch feature/payment
git cherry-pick 8b1e0d4 9c1b7f0

# 3. 回到 develop，丢弃这两个提交（未推送，安全）
git switch develop
git reset --hard origin/develop

# 4. 推送正确分支
git push -u origin feature/payment

正确操作（提交已推送） ​

bash
# 1. 同样先摘到正确分支
git switch feature/payment
git cherry-pick 8b1e0d4 9c1b7f0
git push -u origin feature/payment

# 2. develop 上不能 reset，用 revert 撤销
git switch develop
git revert --no-edit 9c1b7f0 8b1e0d4
git push

分支图 ​

text
误提交后：
  develop:  A---B---C---D   （C、D 是误提交）

修正后（未推送使用 reset）：
  develop:  A---B
  feature:  A---B---C'---D'

修正后（已推送使用 revert）：
  develop:  A---B---C---D---R2---R1   （R 抵消误提交，历史保留）
  feature:  A---B---C'---D'

复盘 ​

  • 未推送 → reset；已推送 → revert。这条分界线适用于所有公共分支。
  • cherry-pick 生成的 C'、D' 哈希不同，属于正常现象，不要试图让两边哈希一致。
  • 预防手段：在 develop、main 上开启分支保护，禁止直接 push。

场景四：hotfix 回灌多个 release 分支 ​

背景 ​

main 上修复了一个线上登录超时问题（提交 H），需要同步到仍在维护的 release/1.4 和 release/1.3。有人直接 git merge main 进 release 分支，把一堆未发布的新功能带了进去。

错误示范 ​

bash
git switch release/1.4
git merge main        # 把 main 上所有未发布功能都带进 release

release 分支的职责是「只包含已发布功能 + 必要修复」，整支合并会破坏发布边界，测试范围瞬间失控。

正确操作 ​

bash
# 1. 确认 hotfix 提交哈希
git log --oneline -3 main
# H 9c1b7f0 fix: 登录超时重试

# 2. 摘到第一个维护分支，-x 记录来源
git switch release/1.4
git cherry-pick -x 9c1b7f0
git push

# 3. 摘到第二个维护分支
git switch release/1.3
git cherry-pick -x 9c1b7f0
git push

# 4. 回到 main，确认没有遗漏（hotfix 本来就在 main，无需回灌）
git switch main

提交信息会自动带上来源：

text
fix: 登录超时重试

(cherry picked from commit 9c1b7f09a1b2c3d4e5f60718293a4b5c6d7e8f90)

分支图 ​

text
main:         A---B---C---H
                       \
release/1.4:   D---E----H'    （只摘 H）
release/1.3:   F--------H''   （只摘 H）

复盘 ​

  • 维护分支只接受 cherry-pick 的修复，绝不整支合并主干。
  • -x 是硬规范：三个月后能追溯来源，避免被误判为重复代码。
  • 如果 release 分支后续还要合回 main，注意第 16 章提到的「重复改动」问题，合并前先 git log --grep 排查。
  • 同一修复摘到 3 个以上分支时，考虑用脚本或发布平台批量执行，减少漏摘。

场景五：整理历史后安全强推 ​

背景 ​

feature/search 上有 7 个提交，其中 4 个是 wip、fix typo、修改 review 意见。PR 评审要求整理成 3 个原子提交。分支已经 push 过，但只有作者本人在用。

错误示范 ​

bash
git rebase -i HEAD~7
git push --force origin feature/search

两个问题：没有备份，整理出错难以回退；--force 无条件覆盖，若期间有人推了提交会直接丢失。

正确操作 ​

bash
# 1. 备份当前状态
git branch backup/search-before-rebase

# 2. 确认远端没有别人的新提交
git fetch origin
git log --oneline HEAD..origin/feature/search
# 输出为空才继续

# 3. 交互式整理
git rebase -i HEAD~7

清单改成：

text
pick   3f2a1c9 feat: 搜索接口封装
fixup  8b1e0d4 wip
fixup  2a9c7f1 fix typo
pick   5d3e8a2 feat: 搜索高亮
fixup  9c1b7f0 修改 review 意见
pick   7e4d1a8 test: 补充搜索用例
fixup  a1b2c3d 补充边界用例
bash
# 4. 处理可能的冲突
git status
git add <file>
git rebase --continue

# 5. 验证整理结果
git log --oneline -3
# 7e4d1a8 test: 补充搜索用例
# 5d3e8a2 feat: 搜索高亮
# 3f2a1c9 feat: 搜索接口封装

pnpm test && pnpm build

# 6. 安全强推
git push --force-with-lease origin feature/search

# 7. 确认无误后删除备份
git branch -D backup/search-before-rebase

出错时如何回退 ​

bash
# 整理到一半发现不对
git rebase --abort

# 已经整理完并强推，才发现问题
git switch feature/search
git reset --hard backup/search-before-rebase
git push --force-with-lease origin feature/search

分支图 ​

text
整理前：
  A---B---C---D---E---F---G---H feature/search

整理后：
  A---B---C'---D'---E' feature/search
  （7 个提交压缩为 3 个，哈希全部改变）

复盘 ​

  • 整理历史前必须满足两个条件：分支私有 + 已备份。
  • 强推前先 fetch 并确认 HEAD..origin/branch 为空，这是 --force-with-lease 之外的第二道保险。
  • 整理后跑完整测试，不要只跑改动相关的用例。

场景六：已发布的错误提交如何回滚 ​

背景 ​

feature/new-pricing 已合并进 main 并发布到生产，随后发现价格计算在生产环境少乘了一个税率系数，影响所有订单。合并提交为 M，功能分支上有 3 个提交。

错误示范 ​

bash
# 直接 reset 掉合并提交并强推 main
git switch main
git reset --hard M^
git push --force origin main

生产发布记录、同事本地仓库、CI 缓存全部指向旧历史；强推后所有人的 main 都需要手动修复。这是最典型的「用本地思维处理公共历史」。

正确操作 ​

bash
# 1. 确认合并提交的父提交顺序
git show --no-patch --pretty=raw M
# parent <hash1>   ← main 侧（第一父提交）
# parent <hash2>   ← feature 侧

# 2. 回滚整个合并，保留 main 主线
git switch main
git revert -m 1 --no-edit M

# 3. 跑测试，确认回滚后行为恢复
pnpm test

# 4. 推送（普通 push，不改写历史）
git push origin main

# 5. 触发重新构建与发布，确认线上恢复
git log --oneline -3

修复后如何重新上线 ​

bash
# 方式一：在功能分支修复后，先 revert 掉那个 revert，再合并
git switch feature/new-pricing
# 修复税率系数并提交
git switch main
git revert --no-edit <revert-commit>   # 恢复被回滚的改动
git merge feature/new-pricing
git push

# 方式二：不 revert 合并提交，改为 revert 功能分支上的具体提交，
#         修复后重新合并，历史更清晰但操作步骤更多

忘记 revert 那个 revert 会怎样

git revert -m 1 M 会让 Git 记住「feature 分支的改动已被拒绝」。修复后直接 git merge feature/new-pricing，Git 会认为这些改动已经处理过，不会重新引入代码，发布后问题依旧。必须先把 revert 反向撤销。

分支图 ​

text
事故后：
  main:  A---B---M---R      （R 抵消 M 的改动，历史完整）

修复上线（方式一）：
  main:  A---B---M---R---R'---N
                            ↑   ↑
                    revert revert  修复后的 feature 合并

复盘 ​

  • 已发布历史只能追加，不能抹除；revert 是唯一安全选项。
  • 合并提交回滚必须指定 -m 1，并牢记「再合并陷阱」。
  • 回滚代码不等于事故结束：要重新构建、发布、验证监控，再关闭事故单。
  • 事后复盘应追问：为什么缺少税率系数的测试？为什么发布前没有灰度？工具能救火，流程才能防火。

决策速查 ​

你的处境首选方案关键命令
个人分支落后主干rebasegit rebase origin/main
共享分支落后主干mergegit merge origin/main
提交到错误分支，未推送cherry-pick + resetgit cherry-pick <hash> + git reset --hard origin/<branch>
提交到错误分支，已推送cherry-pick + revertgit cherry-pick <hash> + git revert <hash>
修复要同步到多个维护分支cherry-pick -xgit cherry-pick -x <hash>
整理个人分支历史交互式 rebasegit rebase -i + git push --force-with-lease

想放弃一次合并merge --abortgit merge --abort
同一冲突反复出现rereregit config --global rerere.enabled true

小结 ​

  • 六个场景覆盖了企业协作中 90% 的冲突决策：同文件冲突、分支落后、误提交、hotfix 回灌、历史整理、线上回滚。
  • 所有操作前先 status + fetch，改写历史前先备份，这是最低成本的保险。
  • 公共历史只追加不抹除；个人历史可以整理，但必须用 --force-with-lease。
  • 每个方案都有明确边界，越过边界就需要停下来和团队沟通，而不是硬上。
  • 工具解决「怎么修」，流程解决「为什么发生」——两者缺一不可。
