19 分支模型选型：Git Flow / GitHub Flow / Trunk-Based ​

学习目标 ​

学完本章，你将能够：

  • 说出三种主流分支模型的结构、发布节奏与适用团队
  • 用团队规模、发布频率、合规要求三个维度做选型
  • 为选定的模型配置对应的分支保护规则与 CI 门禁
  • 识别「模型没问题，但落地变形」的典型症状
  • 从一种模型平滑迁移到另一种，而不打断交付

没有最好的模型，只有匹配的约束 ​

分支模型解决的是三个问题：

  1. 代码从哪里进入主干？
  2. 发布版本如何冻结与修复？
  3. 多人并行时，冲突在哪里消化？

约束不同，答案就不同。下面三种模型分别优化不同的目标。

Git Flow：为重发布节奏设计 ​

text
main      ──●──────────────●──────────●──      （只存已发布版本）
             \            / \        /
release       ●──●──●──●    ...      ...       （发布冻结、只修 bug）
               \  /
develop   ──●───●───●───●───●───●───●──        （集成分支）
             \     /
feature       ●───●                            （功能分支）

核心分支：

  • main：永远对应生产环境，每次合并打 tag；
  • develop：日常集成分支；
  • feature/*：从 develop 切出，完成后合回；
  • release/*：发布冻结，只接受 bugfix；
  • hotfix/*：从 main 切出，修完同时合回 main 与 develop。

适用：

  • 有明确版本号、需要同时维护多个已发布版本的产品（客户端、SDK、私有化部署）；
  • 发布窗口固定，测试周期长；
  • 团队规模中等以上，需要冻结期隔离新功能。

代价：

  • 分支多、合并路径长，develop 长期偏离 main；
  • hotfix 要回灌两处，容易漏；
  • 持续交付团队会觉得很重。

GitHub Flow：为持续部署设计 ​

text
main     ──●────●────●────●────●──      （永远可发布）
            \  /      \  /
feature      ●●        ●●              （短生命周期分支 + PR）

规则只有几条：

  1. main 永远可部署；
  2. 任何改动都从 main 切分支；
  3. 通过 Pull Request 合并，必须通过 CI 与 review；
  4. 合并即部署（或手动触发部署）。

适用：

  • SaaS、Web 应用，发布成本低；
  • 小到中型团队，review 流程顺畅；
  • 不需要维护多个历史版本。

代价：

  • 缺少发布冻结机制，合规或大版本产品需要额外补流程；
  • 功能未完成时不能合入，否则线上暴露半成品——需要 feature flag 配合。

Trunk-Based Development：为高频集成设计 ​

text
main  ──●─●─●─●─●─●─●─●──     （所有人每天多次合入）
         \ /   \ /
分支       ●     ●            （存活不超过 1-2 天，甚至直接提交）

核心纪律：

  • 分支存活时间极短（通常 < 1 天），或直接在主干开发；
  • 未完成功能用 feature flag 隐藏，而不是长期挂分支；
  • 主干必须始终绿：提交前本地跑测试，合并队列（merge queue）保证不破坏；
  • 发布从主干切出，或直接持续部署。

适用：

  • 工程能力强、CI 快（十分钟内）、测试覆盖高的团队；
  • 需要极高发布频率（每天多次）；
  • 微服务架构，单仓变更范围可控。

代价：

  • 对测试与可观测性要求最高；
  • feature flag 管理不善会变成技术债；
  • 没有强 CI 文化的团队直接照搬会频繁弄坏主干。

横向对比 ​

维度Git FlowGitHub FlowTrunk-Based
长期分支多（develop/release）仅 main仅 main
分支寿命数天到数周数小时到数天数小时
发布节奏按版本窗口随时每天多次
多版本维护原生支持弱弱（靠 release 分支）
冲突压力集中在合并期分散极低
CI 要求中中高极高
新人上手成本高低中
典型场景客户端、SDK、私有化SaaS、Web大型高频团队

怎么选：三个问题 ​

  1. 你需要同时维护几个已发布版本？

    • 多个 → Git Flow（或 GitHub Flow + release 分支）
    • 一个 → GitHub Flow / Trunk-Based

  2. 发布一次的成本有多高？

    • 需要数天测试、审批、灰度 → Git Flow 的冻结期有意义
    • 合并即可上线 → GitHub Flow
    • 一天多次 → Trunk-Based

  3. CI 能在 10 分钟内给出可信结果吗？

    • 不能 → 先把 CI 建好，再谈 Trunk-Based
    • 能，且测试覆盖高 → 可以尝试 Trunk-Based
text
发布频率低、版本多  →  Git Flow
发布频率中、单版本  →  GitHub Flow
发布频率高、CI 强   →  Trunk-Based

分支保护：模型落地的硬约束 ​

无论选哪种模型，服务端规则比文档更有效。以 GitHub 为例，main 建议开启：

  • Require a pull request before merging（禁止直推）
  • Require approvals（至少 1-2 人）
  • Require status checks（lint、test、build 必须绿）
  • Require conversation resolution（review 意见必须处理）
  • Require linear history（如采用 rebase 合并策略）
  • Restrict who can push（仅 release bot 可推）
  • CODEOWNERS 自动指定评审人
text
Settings → Branches → Add branch protection rule

规则要和模型一致

Trunk-Based 却允许长期分支、GitHub Flow 却要求线性历史但团队习惯 merge、Git Flow 却没有保护 release/*——这些组合都会产生「制度与实操两张皮」。规则宁愿少而严，不要多而松。

从 Git Flow 迁到 GitHub Flow 的最小路径 ​

  1. 停止从 develop 切新功能，改为从 main 切；
  2. 把 develop 剩余改动合并进 main，然后冻结 develop；
  3. 为 main 开启 PR + CI 保护；
  4. 引入 feature flag，替代「功能没做完不能合」的长期分支；
  5. 保留 release/* 仅用于需要冻结的大版本，日常发布直接从 main 出。

不要一次性删掉所有分支，也不要同时改模型和发布流程——一次只动一个变量。

常见坑 ​

  1. 照搬大厂模型：对方有专职平台团队和秒级 CI，你没有。
  2. Git Flow 的 hotfix 忘记回灌 develop：下次发布会把 bug 带回来。
  3. GitHub Flow 下长期挂着未完成分支：本质退化成 Git Flow，却没有冻结与集成机制。
  4. Trunk-Based 却没有 feature flag：半成品直接暴露给用户。
  5. 只写文档不配保护规则：模型靠自觉执行，等于没有。
  6. 同时维护两套模型：团队认知分裂，合并路径混乱。

小结 ​

  • Git Flow 优化「多版本 + 冻结发布」，GitHub Flow 优化「单主干 + 持续交付」，Trunk-Based 优化「高频集成」。
  • 选型看三个约束：维护版本数、发布成本、CI 可信度。
  • 模型必须配套分支保护与 CI 门禁，否则只是命名约定。
  • 迁移一次只改一个变量，先建能力再换流程。
  • 冲突治理的上限由分支模型决定：分支越短、集成越频繁，冲突越小越早。
