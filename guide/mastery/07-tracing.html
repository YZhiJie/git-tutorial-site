37 Git 追踪调试：GIT_TRACE2 与性能剖析 ​

当 git fetch 卡住、git status 变慢、hook 行为诡异时，猜是没用的。Git 内置了一套分层追踪：从命令分派、协议协商到 HTTP 细节，都能打开开关看到真实发生了什么。

学习目标 ​

  • 区分 GIT_TRACE、GIT_TRACE_PACKET、GIT_TRACE2 等开关的观测层次。
  • 用 trace2 的 JSON 事件定位 fetch / status 的耗时区间。
  • 在 hook、别名、子进程中排查环境变量与命令分派问题。
  • 知道 trace 日志的安全边界，避免把凭据写进 issue。

追踪开关一览 ​

开关观测什么典型用途
GIT_TRACE=1Git 调用了哪些子命令、参数别名、hook、包装脚本分派
GIT_TRACE_SETUP=1仓库发现过程、.git 位置在错误目录执行命令
GIT_TRACE_PACKET=1fetch/push 的协议行ref 协商、对象计数
GIT_TRACE_CURL=1HTTP 请求/响应细节代理、证书、鉴权
GIT_TRACE_PERFORMANCE=1各阶段耗时粗粒度性能定位
GIT_TRACE2=1trace2 文本事件统一追踪
GIT_TRACE2_EVENT=/tmp/t.jsonJSON 事件流机器分析、CI 诊断
GIT_TRACE2_PERF=/tmp/p.log带计时区的性能事件定位慢在哪个 region

实战一：fetch 很慢 ​

bash
# 先看阶段耗时
GIT_TRACE_PERFORMANCE=1 git fetch origin

# 再看协议协商：对方给了哪些 ref、协商了多少对象
GIT_TRACE_PACKET=1 git fetch origin 2>&1 | head -40

# 最后看 HTTP 层：状态码、重定向、代理、鉴权
GIT_TRACE_CURL=1 git fetch origin 2>&1 | head -60

# 结构化事件，适合脚本统计
GIT_TRACE2_EVENT=/tmp/fetch-trace.json git fetch origin

trace2 的 JSON 事件大致是：

json
{"event":"cmd_name","name":"fetch"}
{"event":"region_enter","category":"fetch","label":"negotiate"}
{"event":"region_leave","category":"fetch","label":"negotiate","time":"0.842"}
{"event":"exit","code":0}

先找 region_leave 里耗时最大的类别，再回到对应层开更细的开关。

实战二：status 变慢 ​

bash
GIT_TRACE2_PERF=1 git status 2>&1 | grep -E 'region|status'

重点看：

  • index::read：索引本身多大、是否需要 split index。
  • status::worktree：工作区扫描耗时。
  • fsmonitor：是否启用、是否真的命中。
  • untracked cache 是否生效：git config --get core.untrackedCache。

常见组合：大仓库 + 未启用 fsmonitor + 未启用 untracked cache，status 每次都在全量扫描工作区。

实战三：hook 与子进程 ​

bash
GIT_TRACE=1 git commit -m "test"
GIT_TRACE2_EVENT=/tmp/hook.json git commit --allow-empty -m "test"

GIT_TRACE 会显示 Git 如何调用 hook 脚本、传了哪些参数；TRACE2_EVENT 里的 child_start / child_exit 能看出子进程是否真的启动、退出码是多少。如果 hook 里读不到环境变量，优先检查：

  • hook 是否以非交互 shell 运行；
  • 变量是否只在当前 shell 会话导出；
  • CI 的 job 级 env 是否传到了 hook 子进程。

诊断工具 ​

bash
git version --build-options     # 编译选项、依赖版本
git --exec-path                 # 实际使用的 Git 程序目录
git diagnose                    # 生成仓库诊断包（Git 2.36+）
git bugreport                   # 生成可提交的 issue 模板

git diagnose 会收集仓库状态、配置、pack 信息等，适合让同事离线分析。提交 issue 前先检查压缩包里是否含路径、remote URL 等敏感信息。

常见坑 ​

坑表现正确做法
trace 日志含凭据URL 里带 token、Authorization 头分享前脱敏；注意 GIT_TRACE_REDACT 的默认行为
生产环境常开 GIT_TRACE2_EVENT日志暴涨、IO 放大只在复现时短暂打开
只看总耗时不看 region知道慢，但不知道哪慢用 TRACE2_PERF 找最大 region
hook 里环境变量没透传本地正常、CI 失败用 GIT_TRACE 看 child_start 与环境
混用 GIT_TRACE 与 GIT_TRACE2输出格式混乱先确定观测层，再只开一个
把 trace 文件直接贴进 issue泄露内部地址/凭据脱敏、裁剪、只保留相关片段

小结 ​

  • Git 的追踪是分层的：命令分派、协议、网络、性能各有开关。
  • 排障顺序从粗到细：PERFORMANCE → TRACE2_PERF → PACKET / CURL。
  • 慢不一定在网络；大仓库里 index、worktree 扫描、pack 解压都可能成为瓶颈。
  • trace 日志本身可能含敏感信息，分享前必须脱敏。
