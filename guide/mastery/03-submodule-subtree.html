22 submodule vs subtree ​

当多个项目要复用同一份代码——共享组件库、设计系统、协议定义、第三方 SDK——你必须在「复制粘贴」「包管理器」「Git 仓库嵌套」之间做选择。包管理器解决的是发布版本的复用；submodule（子模块）与 subtree（子树）解决的是仓库源码的复用，两者都能把另一个仓库嵌进当前仓库，但代价完全不同。

学习目标 ​

  • 说清 submodule 与 subtree 在存储模型上的差异，以及它带来的克隆、更新、CI 影响。
  • 熟练使用 submodule 的 add / update --init --recursive / sync / foreach。
  • 熟练使用 git subtree add|pull|push --prefix，理解 --squash 的取舍。
  • 能按「共享组件库 / 只读第三方代码 / 需要双向提交」做出选型。

两种嵌套模型 ​

text
submodule：主仓库只存一个「指针」

shop-web/
|-- src/
|-- .gitmodules          # 记录子模块 URL、path、branch
`-- packages/ui-kit/     # 目录里是另一个独立仓库
    `-- .git             # 子模块有完整对象库
主仓库中 ui-kit 表现为 gitlink（特殊模式 160000），只记录一个 commit 哈希

subtree：主仓库直接存子仓库的文件快照

shop-web/
|-- src/
`-- libs/ui-kit/         # 普通目录，提交历史被合并进主仓库
    |-- src/
    `-- package.json
没有 .git，子仓库历史以额外父提交的形式存在

关键结论：

  • submodule 是引用，克隆主仓库不会自动拿到子模块内容，必须显式初始化。
  • subtree 是拷贝，克隆即完整可用，但主仓库体积和历史会永久变大。

对比表 ​

维度submodulesubtree
主仓库体积小，只存 gitlink大，包含子仓库全部文件与历史
克隆体验需 --recurse-submodules 或事后 update --initgit clone 即可用
更新方式git submodule update --remote，指针变更需单独提交git subtree pull，合并成一个普通提交
提交回子仓库在子模块内直接提交、推送，再更新主仓库指针git subtree push --prefix 拆出提交，冲突时较麻烦
权限管理天然分离，子仓库可独立授权与保护继承主仓库权限，无法单独控制
历史清晰度主仓库历史只看到「更新子模块指针」子仓库历史被合并进来，可用 --squash 缓解
CI 复杂度高：需初始化、缓存子模块、处理凭证低：普通构建
部分检出支持 submodule deinit，按需拉取不支持，全量存在
适合场景独立演进的共享组件、需要独立 CI/发布只读第三方代码、希望零学习成本的团队

submodule 常用操作 ​

bash
# 添加子模块，并跟踪远端 main 分支
git submodule add -b main https://github.com/acme/ui-kit.git packages/ui-kit
git commit -m "chore: 引入 ui-kit 子模块"

# 查看状态：左侧 - 表示未初始化，+ 表示指针与记录不一致
git submodule status --recursive

生成的 .gitmodules 需要一并提交：

ini
[submodule "packages/ui-kit"]
	path = packages/ui-kit
	url = https://github.com/acme/ui-kit.git
	branch = main

克隆与初始化：

bash
# 推荐：克隆时递归拉取
git clone --recurse-submodules https://github.com/acme/shop-web.git

# 已经克隆但忘了加参数
git submodule update --init --recursive

# 只初始化某一个，减少等待
git submodule update --init packages/ui-kit

# 让子模块指向远端分支最新提交（会改动工作区）
git submodule update --remote --merge packages/ui-kit
git add packages/ui-kit && git commit -m "chore: 升级 ui-kit 到最新"

--remote 默认使用 .gitmodules 里的 branch，没有配置则用远端的 HEAD。--merge / --rebase 决定本地子模块有改动时如何整合，不加则在分离头指针上直接检出目标提交。

批量操作与 URL 变更：

bash
# 对所有子模块执行命令（进入各自目录）
git submodule foreach --recursive 'git switch main && git pull --ff-only'

# 远端 URL 改了（如从 GitHub 迁移到内网 GitLab）
git submodule sync --recursive
git submodule update --init --recursive

# 暂时移除某个子模块的工作区（保留 .gitmodules 记录）
git submodule deinit -f packages/ui-kit

子模块里的分离头指针

git submodule update 默认把子模块切到某个提交，而不是分支，因此进入子模块会看到 detached HEAD。直接在里面提交会落在分离头指针上，必须先 git switch -c 建分支、推送到远端，再回主仓库 git add packages/ui-kit 更新指针。

subtree 常用操作 ​

bash
# 首次引入：把远端 main 合入 libs/ui-kit
git subtree add --prefix=libs/ui-kit https://github.com/acme/ui-kit.git main --squash

# 以后拉取上游更新
git subtree pull --prefix=libs/ui-kit https://github.com/acme/ui-kit.git main --squash

# 把本地对该目录的修改推回子仓库
git subtree push --prefix=libs/ui-kit https://github.com/acme/ui-kit.git feature/fix-button

--squash 把子仓库的一次更新压成一个提交合入主仓库，避免把上游全部历史搬进来。代价是主仓库无法再用 subtree 追溯子仓库的逐条历史，执行 git subtree push 时也需要重新计算拆分。若团队需要完整历史且能接受仓库变大，可以去掉 --squash。

subtree 的 merge 冲突发生在主仓库里，解决方式与普通冲突一致；如果长期不使用 --squash，每次 pull 都可能产生大量历史合并。

把远端地址记成别名

bash
git remote add ui-kit https://github.com/acme/ui-kit.git
git subtree pull --prefix=libs/ui-kit ui-kit main --squash

subtree 不保存远端地址配置，只在合并提交的 message 里记录 git-subtree-dir / git-subtree-split 元数据；地址只存在于命令和文档中，团队应在 README 或脚本里固化这些命令，否则新人不知道如何更新。

企业选型建议 ​

场景推荐理由
共享组件库，独立发版、独立 CI、多项目复用submodule版本边界清晰，主仓库只锁定指针，权限与流水线可分离
引入只读第三方代码，几乎不改subtree克隆即用，CI 零配置，不要求全员理解子模块
需要频繁把改动推回上游submodule直接在上游仓库提 PR，流程自然
团队规模小、希望降低认知成本subtree一条 clone 就能开工
仓库要求可离线构建、制品必须自包含subtree不依赖额外拉取步骤与网络凭证
子仓库含机密或需精细授权submodule主仓库权限不会自动扩散到子仓库
移动端/前端单体仓库，追求工具链统一subtree 或包管理器子模块会让 Metro/Vite 的解析与监听变复杂
只用某个版本、从不跟进上游包管理器 / vendor 目录两种 Git 嵌套都属过度设计
什么时候两者都不该用

如果子仓库有规范的版本发布（npm、Maven、Go module），优先用包管理器锁定版本。submodule 与 subtree 适合「必须改源码」「上游不发布制品」「需要与主仓库同一构建」的场景。把它们当包管理器用，只会增加 CI 与协作成本。

常见坑 ​

坑现象处理
克隆后子模块目录为空构建报找不到包git submodule update --init --recursive
改了子模块但主仓库没提交指针同事拉取后仍是旧版本git add packages/ui-kit && git commit
子模块停在 detached HEAD 就提交提交不在任何分支上，推送丢失先 git switch -c 建分支再提交
子模块 URL 变更后拉取失败仍访问旧地址git submodule sync --recursive
CI 没有子模块凭证Permission denied (publickey)配置 deploy key 或改用 HTTPS + token
subtree 未用 --squash主仓库历史爆炸、合并冲突频繁统一加 --squash，并写进团队脚本
subtree push 冲突拆分出的提交与上游分叉先 subtree pull 同步，再 push
误把子模块目录当普通目录提交出现 gitlink 变更但无文件 diff用 git diff --submodule=log 确认指针变化
bash
# 排查子模块指针到底变了什么
git diff --submodule=log
git ls-tree HEAD packages/ui-kit      # 160000 commit <hash> 即 gitlink

小结 ​

  • submodule 存指针，体积小、权限清晰，但克隆与 CI 需要额外初始化步骤。
  • subtree 存文件快照，克隆即用、CI 简单，但仓库变大且回推上游更麻烦。
  • 共享组件库、需要独立发布与权限隔离选 submodule；只读第三方代码、追求低认知成本选 subtree。
  • 有正规版本发布机制的依赖，优先用包管理器，不要用 Git 嵌套硬扛。

钩子可以把「子模块初始化」「提交规范校验」这类团队约定自动化，见 hooks：团队规范自动化。
