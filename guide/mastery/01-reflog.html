20 reflog：误操作的后悔药 ​

reset --hard 之后发现提交没了、branch -D 删错了分支、rebase 把历史改乱了——这些场景里，只要本地仓库还在，引用日志（reflog，reference log）几乎总能把你捞回来。

先记住一个判断标准：reflog 救的是「引用移动」造成的丢失，不是文件内容的丢失。 从未 add 过的工作区改动、被 git clean -fdx 删掉的未跟踪文件，reflog 无能为力。

学习目标 ​

  • 说清 reflog 记录的对象、存储位置和默认保留期。
  • 用 git reflog 与 git reflog show <branch> 定位误操作前的提交。
  • 独立完成三类救援：误删分支、误 reset --hard、误 rebase / commit --amend。
  • 知道 reflog 何时失效，以及为什么它不能替代远端备份和标签。

reflog 记录了什么 ​

Git 里每个「引用（ref）」的每次移动，都会追加一条日志。最常见的引用是 HEAD 和本地分支，例如 refs/heads/main。日志文件位于：

bash
.git/logs/HEAD            # HEAD 的移动历史（切换分支、reset、commit 都会写）
.git/logs/refs/heads/main # main 分支指针的移动历史

每行格式为：旧哈希 新哈希 操作者 <邮箱> 时间戳 +0800 操作描述。用 git reflog 读的是 HEAD 的日志，等价于 git reflog show HEAD：

bash
git reflog                      # 默认显示 HEAD 最近 90 天的移动记录
git reflog -n 20                # 只看最近 20 条
git reflog --date=iso           # 时间显示为 2026-10-22 10:31:02 +0800
git reflog show main            # 只看 main 分支自身的指针移动
git reflog show main -n 5       # 分支视角通常比 HEAD 更干净

输出左侧的 HEAD@{n} 是相对位置，不是提交哈希：

text
a1b2c3d HEAD@{0}: reset: moving to HEAD~2
9f8e7d6 HEAD@{1}: commit: feat: 增加订单导出
4c5b3a2 HEAD@{2}: commit: fix: 修正金额精度

HEAD@{1} 表示「HEAD 上一次所在的位置」，会随着新操作不断漂移。脚本或文档里引用它时，最好同时记下当时的绝对哈希。

HEAD 与分支的日志是两套

git reflog 跟的是 HEAD，切换分支后看到的是「你走过的路」；git reflog show <branch> 跟的是分支指针。恢复误删分支时用后者更直接，因为分支被删后，它的日志文件可能已被清理，但删除前的哈希仍出现在 HEAD 日志里。

场景一：恢复误删的本地分支 ​

bash
# 错误操作：以为 feature/payment 已经合并，直接强删
git branch -D feature/payment
# Deleted branch feature/payment (was 7d3e2f1).

# 第一步：找到删除前分支指向的提交
git reflog --date=iso | head -30
# 7d3e2f1 HEAD@{3}: checkout: moving from feature/payment to main
# 说明 HEAD@{3} 的旧位置就是该分支最后一次被检出的提交

# 第二步：用哈希重建分支（不要用 HEAD@{3} 之外的猜测）
git branch recover/payment 7d3e2f1
git switch recover/payment
git log --oneline -5           # 确认内容无误

# 第三步：确认无误后再改回原分支名
git branch -m recover/payment feature/payment

分支被删除时，它自己的日志文件通常一并删除，所以只能从 HEAD 日志里找删除前的检出记录；如果记录也已过期，就用 git fsck --lost-found 找悬空提交（dangling commit）。

恢复出来的是「提交链」，不是「分支配置」

重建分支只恢复了指针，上游跟踪关系（upstream）、分支保护和 PR 关联都不会回来。恢复后需要补一条 git branch -u origin/feature/payment。

场景二：恢复误 reset --hard ​

text
A --- B --- C --- D --- E  (main)
                  ^
              reset --hard 到 C，D、E 从分支上消失
bash
git reset --hard HEAD~2        # 危险：D、E 不再被 main 引用
git log --oneline              # 只剩 A B C

git reflog
# e5d4c3b HEAD@{0}: reset: moving to HEAD~2
# 9a8b7c6 HEAD@{1}: commit: feat: 补充导出字段   <- E
# 1f2e3d4 HEAD@{2}: commit: feat: 导出订单       <- D

# 方式一：整体回到 reset 之前
git reset --hard HEAD@{1}

# 方式二：只把丢掉的两个提交捡回来，当前工作保留
git cherry-pick 1f2e3d4^..9a8b7c6

第二种方式更稳：先 git branch backup/pre-reset 9a8b7c6 打个本地备份分支，再决定怎么处理。恢复过程中再次 reset --hard 会把 reflog 继续往前推，HEAD@{1} 的含义随之改变，所以务必先记录绝对哈希。

不要在救援过程中执行 git gc --prune=now

悬空提交在 gc 之前一直存在。救援期间跑一次带 --prune=now 的垃圾回收，可能把你要找的提交彻底删掉，reflog 里只剩一条指向不存在对象的记录。

场景三：恢复误 rebase 或误 amend ​

rebase 和 commit --amend 的本质都是「新建提交、移动分支指针」，旧提交并没有被立刻删除，只是变成了不可达对象。因此两者都能用同一套方法回退。

bash
git rebase -i HEAD~5           # 操作失误，历史被改写
git reflog
# 3c2b1a0 HEAD@{0}: rebase (finish): returning to refs/heads/main
# 0f9e8d7 HEAD@{1}: rebase (pick): feat: 新增发票
# ...
# 7a6b5c4 HEAD@{8}: rebase (start): checkout HEAD~5   <- 起点之前的位置

# rebase 开始前的原始 HEAD 也保存在 ORIG_HEAD
git reset --hard ORIG_HEAD

# amend 之后想找回旧版本
git reflog
# b2c3d4e HEAD@{0}: commit (amend): fix: 修正文案
# a1b2c3d HEAD@{1}: commit: fix: 修正文案   <- amend 前的提交
git reset --hard a1b2c3d

ORIG_HEAD 只在部分危险操作后写入（merge、rebase、reset、pull），且只有一份，会被下一次操作覆盖。reflog 才是完整历史，优先用 reflog。

恢复被改写的提交后，如果原分支已经推送过，不要直接强推。先比对远端，必要时用 git revert 生成反向提交，具体决策见 revert vs reset。

reflog 的边界：过期、gc 与本地性 ​

reflog 默认不是永久的，受两条配置控制：

bash
# 可达引用的日志保留 90 天
git config --get gc.reflogExpire              # 默认 90 days
# 不可达（已删分支/悬空提交）的日志保留 30 天
git config --get gc.reflogExpireUnreachable   # 默认 30 days

# 查看当前所有 reflog 条目及过期时间
git reflog expire --dry-run --all --verbose

# 危险：立即清空全部 reflog（不可恢复）
git reflog expire --expire=now --all
git gc --prune=now

三条硬边界：

  1. reflog 是本地的。 git clone 不会复制 reflog，git push 也不会上传。换一台机器、重新克隆，历史就没了。
  2. 只记录引用移动。 未提交的工作区改动、stash 之外的临时文件、被 clean 删除的文件都不在保护范围内。
  3. 有保留期。 超过 90/30 天的记录会被 gc 清理，长期归档要靠 tag、远端分支或发布分支。
找不到时，试试悬空对象
bash
git fsck --lost-found --no-reflogs
# dangling commit 9a8b7c6...
git show --stat 9a8b7c6        # 逐个确认内容
git branch rescue 9a8b7c6

--no-reflogs 表示连 reflog 都不参考，直接扫对象库，适合 reflog 已过期但对象还没被 prune 的情况。对象一旦被 gc 删除，任何工具都救不回来。

常见坑 ​

坑表现正确做法
把 HEAD@{1} 当固定哈希多执行几次命令后指向了别的提交记下绝对哈希，再操作
在错误的分支上执行恢复git reflog 显示的是 HEAD 轨迹，夹杂 checkout 记录用 git reflog show <branch> 或按操作描述筛选
恢复后立即强推覆盖同事已拉取的提交先 git fetch，再决定 revert 或 --force-with-lease
以为 reflog 能救未跟踪文件clean -fdx 后无记录用 IDE 本地历史或备份；重要产物及时提交
恢复完不建备份第二次误操作把救援点也弄丢救援前 git branch backup/xxx <hash>
在共享/CI 机器上依赖 reflog每次都是全新 clone用 tag 或远端分支固化关键提交

小结 ​

  • reflog 记录 HEAD 与分支引用的每次移动，是本地误操作的兜底网，默认 90 天 / 不可达 30 天。
  • 三类高频救援：git branch <name> <hash> 救分支，git reset --hard <hash> 救 reset/rebase/amend，git cherry-pick 选择性捡回提交。
  • 救援第一步永远是确认绝对哈希并建备份分支，最后一步才是决定是否推送。
  • 它不是备份：不跨机器、不覆盖工作区、会过期。关键节点用 tag 和远端分支固化。
