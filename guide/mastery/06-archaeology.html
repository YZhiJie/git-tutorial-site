36 提交考古：pickaxe、blame 与 range-diff ​

代码里有一行看不懂，或者一个 bug 不知道哪次改动引入的，git log 的默认输出帮不上忙。考古要回答的是三个不同的问题：

  • 这段内容是什么时候进来的？ → pickaxe（-S / -G）
  • 这一行是谁、在哪次提交改的？ → blame
  • 这两版补丁到底差在哪？ → range-diff

三个工具解决不同层次的问题，混用会得到错误的结论。

学习目标 ​

  • 用 -S 与 -G 精确找到内容引入/删除的提交，理解两者差别。
  • 用 blame 定位行级归属，并用 --ignore-rev 跳过格式化提交。
  • 用 log -L 追踪一个函数或一段范围的演变。
  • 用 range-diff 比较 rebase 前后两版提交序列。
  • 避免「blame 显示的是最后一次格式化提交」这类误判。

pickaxe：按内容变化找提交 ​

git log -S 会遍历历史，找出某字符串出现次数发生变化的提交：

bash
# 哪个提交第一次引入 FEATURE_FLAG_V2
git log -S "FEATURE_FLAG_V2" --oneline

# 哪个提交删掉了它
git log -S "FEATURE_FLAG_V2" --oneline --reverse

# 配合路径，缩小范围
git log -S "FEATURE_FLAG_V2" -- src/config/

# 查看具体改动
git log -S "FEATURE_FLAG_V2" -p -- src/config/flags.ts

-S 的判定是出现次数变化，不是「diff 里包含这个字符串」。这意味着：

  • 一次提交把一个字符串从文件 A 移到文件 B，次数不变，-S 不会报出来。
  • 一次提交只是重新格式化，次数不变，也不会报出来。

-G 改用正则匹配 diff 的增删行，只要新增或删除的行匹配就命中：

bash
# 找出所有改动过 fetch( 调用的提交
git log -G 'fetch\(' --oneline -- src/api/

# 找形如 TODO(name) 的行被增删
git log -G 'TODO\([a-z]+\)' -p
选项匹配对象适合
-S <string>字符串出现次数变化「某常量/函数名何时引入」
-S <string> --pickaxe-regex正则的出现次数变化同上，但需要正则
-G <regex>diff 增删行是否匹配「哪些提交动过这类代码」

性能

pickaxe 要读每个提交的 diff，大仓库上很慢。先用 -- path 缩小范围，再加 --since 限制时间：

bash
git log -S "API_BASE" --since="2025-01-01" -- src/

blame：行级归属 ​

bash
# 整个文件
git blame src/checkout.ts

# 指定行范围
git blame -L 40,70 src/checkout.ts

# 忽略空白改动
git blame -w src/checkout.ts

# 检测跨文件移动/复制（更慢但更准）
git blame -C -C -C src/checkout.ts

# 在指定提交时点的文件状态
git blame v1.2.0 -- src/checkout.ts

默认输出每行前的哈希是「最后一次改动这一行的提交」。这正是 blame 最容易误导人的地方：如果一次全仓格式化，所有行都归到格式化提交，真正的作者信息全被覆盖。

跳过格式化提交 ​

先找出格式化提交（通常是 Prettier/ESLint 批量提交），写进一个忽略文件：

text
# .git-blame-ignore-revs
# 2025-03 全仓 prettier
9f1c2a3d4e5f60718293a4b5c6d7e8f901234567
# 2025-07 切换 eslint 规则
b4c5d6e7f8091a2b3c4d5e6f7a8b9c0d1e2f3a4b
bash
# 本次使用
git blame --ignore-revs-file .git-blame-ignore-revs src/checkout.ts

# 设为默认
git config --global blame.ignoreRevsFile .git-blame-ignore-revs

# 临时忽略某一个提交
git blame --ignore-rev 9f1c2a3d src/checkout.ts

GitHub 会读取仓库根目录的 .git-blame-ignore-revs（需要在仓库设置里开启），所以这个文件提交进仓库后，网页上的 blame 也会跳过噪声提交。

log -L：追踪一段代码的演变 ​

-L 直接围绕「行范围」或「函数」列出演进：

bash
# 追踪 checkStock 函数的每次改动
git log -L :checkStock:src/inventory.ts

# 追踪第 40-70 行
git log -L 40,70:src/inventory.ts -p

# 追踪某个函数在旧版本中的形态
git log -L :checkStock:src/inventory.ts v1.2.0..HEAD

-L 的好处是输出只包含这段代码的历史，不会被同文件其他改动干扰。代价是它需要解析 diff 并跟踪行号偏移，比 -S 更慢，且函数识别依赖语言支持（默认的 funcname 正则对 JS/TS 未必准确，可用 --function-context 或自定义 diff driver 改善）。

range-diff：比较两版补丁 ​

rebase 之后，旧提交全换了哈希，git diff old..new 只会显示两边内容差异，看不出「哪些提交被改写了」。range-diff 比较的是提交序列的语义差异：

bash
# rebase 前记下范围
git rev-parse HEAD~3..HEAD        # 旧范围

# rebase 后
git range-diff main old-tip new-tip

# 更常见的写法：分支 rebase 前后
git range-diff origin/main...old-feature origin/main...new-feature

输出形如：

text
1:  3f2a1c9 ! 1:  7d4c2b1 feat: 登录接口
    @@
    - const timeout = 3000
    + const timeout = 5000
2:  8b1e0d4 = 2:  4e8a9c3 feat: 登录失败提示
3:  2a9c7f1 < -:  --------- feat: 调试日志
  • = 表示两个提交内容等价，只是哈希变了。
  • ! 表示内容有改动，下面给出 diff。
  • < / > 表示提交被删除或新增。

这正是 code review 里最需要的视图：reviewer 关心的是「你 rebase 之后改了什么」，而不是「整个分支的最终 diff」。

组合使用：一次真实的排查 ​

线上订单偶尔重复扣款。已知代码在 src/payment/，想定位引入时间：

bash
# 1. 先找关键字：哪个提交引入了 retry 逻辑
git log -S "retryPayment" --oneline -- src/payment/

# 2. 看该提交的完整改动
git show <sha> -- src/payment/

# 3. 追踪这个函数的后续演变
git log -L :retryPayment:src/payment/client.ts --oneline

# 4. 对可疑行做 blame，并跳过格式化提交
git blame -L 88,110 --ignore-revs-file .git-blame-ignore-revs src/payment/client.ts

四步从「面」到「点」：pickaxe 找范围，log -L 看演变，blame 定位到行，show 看上下文。

常见坑 ​

坑后果正确做法
用 -S 找「移动后的代码」找不到，因为次数没变用 -G，或按路径 log --follow
blame 结果直接当成作者归到了格式化提交配置 --ignore-revs-file
忽略文件写短哈希不生效用完整 40 位哈希
log -L 用在超大文件极慢缩小行范围，或先用 -S 定位
range-diff 用它比较两个无关分支输出无意义只比较同一补丁序列的两版
大仓库直接全量 pickaxe几分钟无结果加 -- path、--since
忽略 revs 文件没提交同事/网页 blame 仍被污染提交到仓库根目录

小结 ​

  • -S 看字符串出现次数变化，适合找「引入/删除」；-G 看 diff 行匹配，适合找「所有碰过」。
  • blame 默认归到最近一次改动，格式化提交会污染结果，用 .git-blame-ignore-revs 穿透。
  • log -L 围绕函数或行范围追踪演变，比全文件 diff 更聚焦。
  • range-diff 比较两版提交序列，是 rebase 后 review 的标准视图。
  • 排查路径：pickaxe 缩小范围 → log -L 看演变 → blame 定位到行 → show 看上下文。
