21 bisect：二分定位坏提交 ​

线上报错、构建变慢、某个功能在某次发布后失效，但你面对的是几百上千个提交，git log 一个个翻等于大海捞针。二分定位（bisect）把「逐个试」变成「每次砍一半」：1000 个提交最多约 10 次验证就能锁定第一个坏提交。

学习目标 ​

  • 理解 bisect 的适用前提：历史线性可验证、坏状态单调出现。
  • 掌握手动流程 start / bad / good / reset 与中途查看状态。
  • 用 git bisect run 自动执行测试脚本，并正确使用 0 / 1 / 125 退出码。
  • 能把性能回归这类「非布尔」问题改写成可二分的判定脚本。
  • 分清 bisect 与 git log -S（pickaxe）各自解决什么问题。

原理：为什么是 O(log n) ​

bisect 维护一个区间 [good, bad]，每次检出区间中点让验证者判定，然后保留「坏的那一半」。每轮区间减半，1000 个提交约 10 次、10000 个约 14 次验证，复杂度为 O(log₂ n)。

text
good . . . . . . . . . . bad
          ^ 取中点

good . . . mid . . . . . bad
       ^ 好 -> 保留右半；坏 -> 保留左半

good . mid . . . . . . . bad
       ^ 最终锁定第一个坏提交

前提只有一条：存在一个单调的判定。好提交之前全是好的，坏提交之后全是坏的。如果 bug 时有时无、只在特定机器复现，或者中间某个提交根本编译不过，二分结果就不可信——后者可以用 skip 跳过，前者要先把判定稳定下来。

bisect 会切换工作区

它通过 checkout 不同提交来验证，过程会产生分离头指针（detached HEAD）。开始前必须清理工作区，否则 git bisect start 会直接报错；过程中不要提交、不要切分支。

手动流程 ​

bash
# 0. 确认工作区干净，基于当前分支开始
git bisect start

# 1. 标记当前版本是坏的，再标记一个已知正常的版本
git bisect bad
git bisect good v2.3.0
# Git 检出中点：Bisecting: 4 revisions left to test (roughly 2 steps)

# 2. 在当前检出的版本上验证，然后回答
npm test
git bisect good        # 测试通过
git bisect bad         # 测试失败
git bisect skip        # 编译失败/依赖缺失，无法判定

# 3. 得到 first bad commit，查看后结束
git show --stat HEAD
git bisect reset

过程中随时可以查看进度和已做的判定：

bash
git bisect log                 # 完整判定记录，可保存为文件
git bisect visualize           # 用 gitk 展示剩余区间

git bisect reset 默认回到 git bisect start 时的分支；加 git bisect reset <branch> 可回到指定分支。忘记 reset 会一直停在某个历史提交上，这是新手最常见的「我的代码怎么回退了」的原因。

保存与重放判定

bash
git bisect log > /tmp/bisect.log
git bisect replay /tmp/bisect.log

同事复现同一个问题时，重放日志可以跳过重复的标记步骤。日志里记录的是每个提交的判定，换机器后需要仓库中有对应对象。

自动化：git bisect run ​

手动流程适合验证成本高、需要人眼判断的场景。只要能写成一个脚本，就交给 git bisect run：

bash
git bisect start
git bisect bad HEAD
git bisect good v2.3.0
git bisect run ./scripts/check.sh

脚本退出码约定是硬性契约：

退出码含义bisect 行为
0当前提交正常标记 good
1～124当前提交有问题标记 bad
125无法判定标记 skip，继续二分
126 / 127脚本不可执行 / 命令不存在中止，避免误判
其他（如 130、信号）异常终止中止整个流程

最小可用脚本：

bash
#!/usr/bin/env bash
# scripts/check.sh：仓库根目录下执行，返回 0 表示正常
command -v node >/dev/null 2>&1 || exit 125

# 构建失败说明该提交本身不可验证，跳过而不是判坏
if ! npm ci --silent >/dev/null 2>&1; then
  exit 125
fi

# 用超时防止个别提交卡死
if timeout 120 npm test -- --runInBand >/tmp/bisect-test.log 2>&1; then
  exit 0
else
  exit 1
fi
bash
chmod +x scripts/check.sh      # 没有执行权限会得到 126
git bisect run ./scripts/check.sh

脚本里的 npm ci 会改动 node_modules，但不会改动被跟踪文件，因此不会打断 bisect。不要在脚本里执行 git checkout、git commit 或修改被跟踪的源码。

真实案例：定位性能回归 ​

某接口 P95 延迟从 180ms 涨到 420ms，版本之间相隔 300 多个提交，且没有报错——这不是「测试红绿」问题，需要把性能阈值改写成布尔判定。

bash
#!/usr/bin/env bash
# scripts/perf-check.sh：低于 250ms 视为正常
set -u
npm ci --silent >/dev/null 2>&1 || exit 125

# 跑 5 轮取中位数，降低机器抖动带来的误判
node scripts/bench-api.js --rounds 5 --out /tmp/bench.json >/dev/null 2>&1 || exit 125
p95=$(node -e 'const r=require("/tmp/bench.json");console.log(r.p95)')

# 注意：用 awk 做浮点比较，bash 不支持小数运算
if awk "BEGIN{exit !($p95 < 250)}"; then
  echo "p95=${p95}ms -> good"
  exit 0
else
  echo "p95=${p95}ms -> bad"
  exit 1
fi
bash
git bisect start
git bisect bad HEAD
git bisect good v4.8.0
git bisect run ./scripts/perf-check.sh
git bisect reset

得到的提交如果只是「引入了一个慢查询」，修复仍然要单独评估。bisect 只负责定位，不负责解释；确认后看 git show <hash> 的 diff，再决定修复或 revert。若该提交已在线上，回滚方式见 revert vs reset。

性能脚本要稳定：每轮先 warmup，取多轮中位数而非单次值，阈值留 20% 以上余量，并在固定容器/机型上跑，避免负载波动把好提交误判为坏。

与 git log -S 的区别 ​

维度git bisectgit log -S（pickaxe）
回答的问题哪个提交让行为变坏哪个提交增删了某段文本
判定依据运行测试/脚本提交 diff 中的字符串出现次数变化
适用场景运行时 bug、性能回归、构建失败某个函数/常量/配置项何时被引入或删除
成本需要多次 checkout 与验证一次历史遍历，秒级
结果精度第一个坏提交所有涉及该字符串的提交
bash
# 想知道某段可疑代码是什么时候进来的：先用 pickaxe
git log -S "cache.set(" --oneline -- src/
git log -G "cache\.set\(" -p -- src/     # -G 支持正则

# 知道「坏了」但不知道和哪段代码有关：用 bisect
git bisect start && git bisect bad && git bisect good v4.8.0

经验顺序：能定位到可疑代码就先 log -S，只能描述现象就用 bisect。 两者也可以组合：pickaxe 找到几个候选提交，再用 bisect 在其中确认。

常见坑 ​

坑现象处理
工作区不干净error: Your local changes would be overwritten先 stash 或提交，再开始
忘记 git bisect reset停在 detached HEAD，以为代码丢了git bisect reset，或 git switch - 回原分支
测试脚本不稳定结果来回跳，锁定到无关提交增加重试与多轮采样，或对 flaky 用例 skip
中间提交编译不过run 直接判 bad，定位偏移脚本里构建失败返回 125
good 选得太近区间外的真正坏提交被漏掉good 必须是一个确认可用的版本
合并提交干扰手动验证时逻辑分叉，难以判断用 git bisect skip，或只对 first-parent 历史二分

不要在 bisect 过程中强推或改写历史

bisect 期间 HEAD 在历史提交之间移动，此时执行 rebase、commit --amend、push --force 会污染判定区间甚至改动共享分支。救援和清理都放到 git bisect reset 之后。

小结 ​

  • bisect 用二分把定位成本从 O(n) 降到 O(log n)，前提是判定单调、环境稳定。
  • 手动流程四步：start → bad → good → reset；验证不了的提交用 skip。
  • git bisect run 的退出码是契约：0 好、1 坏、125 跳过，其他值会中止。
  • 性能类问题要把指标写成带阈值的脚本并多轮采样；定位用 bisect，找代码用 git log -S，两者互补。
