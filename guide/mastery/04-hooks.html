23 hooks：团队规范自动化 ​

钩子（hook）是 Git 在特定事件前后自动执行的脚本。团队里「提交前要跑 lint」「提交信息必须符合规范」「推送前不允许有调试代码」这类约定，靠人自觉一定会漏；写进钩子，才能变成每次操作都会执行的强制流程。

学习目标 ​

  • 分清客户端钩子与服务端钩子，知道每个常用钩子能拦截什么、不能拦截什么。
  • 掌握钩子的执行条件：位置、可执行权限、退出码、工作目录与参数。
  • 用 husky + lint-staged 搭建提交前检查，用 commit-msg 校验 Conventional Commits。
  • 理解钩子默认不随 clone 分发，能设计出团队可落地的分发方案。
  • 明确 --no-verify 的合法使用边界。

钩子分类 ​

侧钩子触发时机典型用途
客户端pre-commit执行 git commit 时、生成提交信息前lint、格式化、禁止提交密钥/大文件
客户端commit-msg编辑完提交信息、真正落库前校验 Conventional Commits、禁止空信息
客户端pre-pushpush 传输对象前跑单测、类型检查、阻止推 main
服务端pre-receive收到推送、更新引用前全局策略校验，可拒绝整次推送
服务端update每个被更新的分支各触发一次按分支做权限与保护规则
服务端post-receive引用更新后触发 CI、部署、通知

客户端钩子可以被绕过（--no-verify、直接改本地配置），服务端钩子才是不可绕过的最终防线。企业里通常两边都做：客户端负责快速反馈，服务端负责兜底。

钩子不进入版本库

.git/hooks/ 本身不受版本控制，git clone 不会带走任何钩子。仓库里能提交的只有「安装钩子的脚本」和「钩子脚本源文件」，新成员必须执行一次安装步骤。

执行机制 ​

Git 在 .git/hooks/ 下按文件名查找钩子，文件名必须精确匹配，且必须有可执行权限：

bash
# .sample 后缀不会执行；去掉后缀并加执行权限
cp .git/hooks/pre-commit.sample .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit

约定：

  • 退出码为 0 表示通过；非 0 会中止当前操作（post-* 钩子除外，它们执行失败也不回滚）。
  • 钩子从仓库根目录执行，脚本内使用相对路径要小心；参数由 Git 传入，例如 commit-msg 收到提交信息文件路径，pre-push 从 stdin 收到待推送的引用列表。
  • 钩子继承当前环境变量，但不继承你的 shell 配置。nvm、pyenv 管理的运行时在 GUI 客户端或 IDE 里经常找不到，脚本中应显式初始化或使用绝对路径。
  • 可以用 core.hooksPath 改变查找目录，让钩子脚本随仓库分发：
bash
# 把钩子统一放在仓库的 .githooks/ 目录（该目录可提交）
git config core.hooksPath .githooks
chmod +x .githooks/*

core.hooksPath 是本地配置，仍需每人执行一次，或由安装脚本写入。

典型用途与实现 ​

pre-commit：只检查即将提交的内容 ​

bash
#!/usr/bin/env bash
# .githooks/pre-commit
set -euo pipefail

# 禁止提交私钥、.env 等敏感文件
if git diff --cached --name-only | grep -E '\.(pem|key)$|(^|/)\.env$'; then
  echo "检测到敏感文件，已阻止提交。请移出暂存区：git restore --staged <file>"
  exit 1
fi

注意 git diff --cached：只检查已暂存的内容，不能用工作区状态代替，否则会把未暂存的半成品也判为问题。

commit-msg：校验提交信息规范 ​

Conventional Commits 的格式为 type(scope): subject，例如 feat(order): 支持批量导出。用纯 shell 校验，不依赖 Node：

bash
#!/usr/bin/env bash
# .githooks/commit-msg
set -euo pipefail

msg_file="$1"
# 取第一行非注释内容作为标题
subject=$(grep -v '^#' "$msg_file" | sed '/^[[:space:]]*$/d' | head -n 1)

# 放行自动生成的提交
case "$subject" in
  Merge\ *|Revert\ *|fixup!\ *|squash!\ *) exit 0 ;;
esac

pattern='^(feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert)(\([a-z0-9._/-]+\))?!?: .{1,72}$'
if ! printf '%s\n' "$subject" | grep -Eq "$pattern"; then
  cat >&2 <<'EOF'
提交信息不符合 Conventional Commits：
  <type>(<scope>): <subject>
  type: feat|fix|docs|style|refactor|perf|test|build|ci|chore|revert
示例：feat(order): 支持批量导出
EOF
  exit 1
fi

commit-msg 拿到的参数是临时文件路径，不要修改它（除非你就是要做自动补全，例如追加 issue 号）。

pre-push：推送前跑重检查 ​

bash
#!/usr/bin/env bash
# .githooks/pre-push
set -euo pipefail
protected="refs/heads/main refs/heads/release/*"

while read -r local_ref local_sha remote_ref remote_sha; do
  # 删除远端分支时 local_sha 为全 0，放行
  [ "$local_sha" = "0000000000000000000000000000000000000000" ] && continue
  for p in $protected; do
    case "$remote_ref" in
      $p) echo "禁止直接推送 $remote_ref，请走 Pull Request。" >&2; exit 1 ;;
    esac
  done
done

npm run typecheck && npm test -- --runInBand

pre-push 每次都跑全量测试会让推送变得很慢，通常只跑受影响的测试或类型检查，把全量测试留给 CI。

钩子要快

pre-commit 超过 2～3 秒，开发者就会开始习惯性使用 --no-verify，规范形同虚设。把耗时任务拆到 pre-push 或 CI，pre-commit 只做增量 lint 与格式化。

husky + lint-staged 落地 ​

husky 负责安装钩子并让 .husky/ 目录随仓库分发；lint-staged 只对暂存文件执行命令，保证速度。

package.json：

json
{
  "scripts": {
    "prepare": "husky"
  },
  "lint-staged": {
    "*.{js,jsx,ts,tsx,vue}": ["eslint --fix --max-warnings=0", "prettier --write"],
    "*.{css,scss,md,json,yml,yaml}": ["prettier --write"]
  },
  "devDependencies": {
    "husky": "^9.1.7",
    "lint-staged": "^15.2.10"
  }
}
bash
npm install --save-dev husky lint-staged
npm run prepare                      # 生成 .husky/_ 并设置 core.hooksPath
printf 'npx lint-staged\n' > .husky/pre-commit

.husky/pre-commit（husky v9 不需要 shebang，保留一行命令即可）：

bash
npx lint-staged

.husky/commit-msg（复用上面提交到仓库的 shell 校验脚本）：

bash
sh .githooks/commit-msg "$1"

prepare 生命周期在 npm install 后自动执行，新成员拉代码后装依赖即完成安装。CI 中使用 npm ci 时也会执行 prepare，若不希望 CI 安装钩子，可设置 HUSKY=0：

bash
HUSKY=0 npm ci

常见坑 ​

坑现象处理
钩子没有执行权限完全没反应，也不报错chmod +x .githooks/*，用 git config core.hooksPath 指向目录
以为钩子会随 clone 下发新人本地无任何检查用 husky prepare 或安装脚本
脚本里用相对路径IDE/GUI 下找不到文件基于 git rev-parse --show-toplevel 定位仓库根
找不到 nvm 的 node本地命令行正常，IDE 提交失败脚本中加载 nvm 或写死解释器路径
pre-commit 检查了工作区未暂存的错误也阻止提交用 git diff --cached / lint-staged
服务端钩子缺失本地 --no-verify 即可绕过关键规则放到 CI 或 pre-receive

--no-verify 的边界

git commit --no-verify / git push --no-verify 会跳过客户端钩子，但不会跳过服务端钩子，也不会跳过 CI。允许使用的场景仅限：紧急 hotfix 且已人工复核、钩子本身故障需要临时绕过、生成机器提交（如 release 脚本）。禁止把它当成日常习惯，更不要在脚本、alias 里默认加上。跳过检查造成的规范问题，最终仍会在评审或流水线里暴露。

小结 ​

  • 客户端钩子负责快速反馈，服务端钩子与 CI 才是不可绕过的兜底。
  • 钩子靠文件名、可执行权限和退出码生效；core.hooksPath 能让脚本随仓库分发。
  • pre-commit 只检查暂存内容并保持快速，commit-msg 校验格式，pre-push 承担更重的检查。
  • husky 的 prepare + lint-staged 是前端团队最低成本的落地方案；--no-verify 是应急通道，不是常规路径。

提交信息规范之外，文件级别的换行与合并行为也需要在仓库里固化，见 .gitattributes 与合并策略。
