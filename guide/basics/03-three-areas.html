03 三区模型：工作区、暂存区、版本库 ​

学习目标 ​

  • 能画出工作区、暂存区、本地版本库、远程仓库四层结构及数据流向。
  • 能说出文件从 untracked 到 committed、再到 modified 的完整状态生命周期。
  • 能读懂 git status -s 输出中 XY 两列各自的含义。
  • 能用 git add、git commit 精确控制哪些内容进入下一次提交。
  • 能编写 .gitignore 规则，并处理已被跟踪但需要忽略的文件。

四层结构 ​

Git 把代码的流转拆成四个位置。理解它们，绝大多数「为什么提交里多了/少了文件」的问题都能自行定位。

text
工作区（working tree）      暂存区（index）        本地版本库（repository）      远程仓库（remote）
   README.md        --add-->   待提交快照    --commit-->    commit 对象      --push-->   origin/main
       ^                         |                            |                              |
       |<------ restore ---------|                            |                              |
       |<------------------ restore --staged -----------------|                              |
       |<------------------------ reset ----------------------|                              |
       |                                                                                     |
       |<-------------------------------- fetch / pull -------------------------------------|
  • 工作区：磁盘上能直接编辑的文件。
  • 暂存区（staging area / index）：一个二进制文件 .git/index，记录「下一次提交要包含什么」。
  • 本地版本库：.git/objects 中不可变的提交、目录树、文件对象。
  • 远程仓库：团队共享的另一个完整仓库，通过 origin 等远程名引用。

暂存区是 Git 区别于许多旧式版本控制的关键设计。它让一次提交可以只包含部分修改，而不是「工作区现在是什么就提交什么」。

文件状态生命周期 ​

Git 中的文件始终处于以下四种状态之一：

text
untracked ──git add──> staged ──git commit──> committed
                          ^                       |
                          |                       | 修改文件
                          └────── git add ────────┘
                                  modified
状态含义git status 提示
untracked新文件，从未被 Git 记录Untracked files
staged修改已写入暂存区，等待提交Changes to be committed
committed已写入本地版本库nothing to commit, working tree clean
modified已跟踪文件在工作区被改动，尚未暂存Changes not staged for commit

注意：modified 是相对「暂存区中的版本」而言。一个文件可以同时有已暂存和未暂存的修改，此时它在 git status -s 中会显示为 MM。

读懂 git status 短格式 ​

bash
git status
# On branch main
# Changes to be committed:
#         modified:   src/app.ts
# Changes not staged for commit:
#         modified:   README.md
# Untracked files:
#         docs/notes.md

git status -s
# M  src/app.ts
#  M README.md
# ?? docs/notes.md

短格式的两个字符 XY：

  • X：暂存区相对 HEAD 的差异（已暂存的变化）。
  • Y：工作区相对暂存区的差异（未暂存的变化）。
  • ??：未跟踪文件；!!：被忽略的文件（需 --ignored 才显示）。
输出含义
??新文件，未跟踪
A 新文件已暂存
M已跟踪文件被修改，未暂存
M 修改已暂存
MM暂存后又改了一次，两部分都存在
D工作区删除了文件，未暂存
D 删除操作已暂存
R 重命名已暂存
UU合并冲突，双方都修改了同一区域

记忆方法：左列看「提交会带上什么」，右列看「还有什么没放进暂存区」。

状态如何被命令改变 ​

操作起点终点命令
暂存新文件/修改工作区暂存区git add <path>
暂存已跟踪文件的删除工作区暂存区git add -u 或 git rm <path>
生成提交暂存区本地版本库git commit -m "..."
撤销暂存暂存区工作区保持git restore --staged <path>
丢弃工作区修改暂存区工作区git restore <path>
发布提交本地版本库远程仓库git push
bash
echo "hello" > demo.txt
git status -s
# ?? demo.txt

git add demo.txt
git status -s
# A  demo.txt

git commit -m "docs: 添加演示文件"
# [main 8b1e0d4] docs: 添加演示文件
#  1 file changed, 1 insertion(+)
git status -s
# （无输出，工作区干净）

echo "world" >> demo.txt
git status -s
#  M demo.txt

git commit 只读取暂存区。提交后再改文件，改动留在工作区，必须再次 git add 才会进入下一次提交。

.gitignore ​

.gitignore 放在仓库任意目录，规则作用于该目录及其子目录。常见写法：

text
# 依赖与构建产物
node_modules/
dist/
build/

# 环境变量与密钥
.env
.env.*
!.env.example

# 日志与临时文件
*.log
*.tmp
.DS_Store

# 只忽略根目录下的 docs 缓存，不影响子目录
/docs/.cache/

语法要点：

写法含义
dist/忽略任意层级的 dist 目录
/dist/只忽略仓库根目录下的 dist
*.log忽略任意层级的日志文件
!important.log取消忽略，需放在能覆盖前规则的顺序之后
docs/**/*.tmp** 匹配任意层级目录

已跟踪文件不受 .gitignore 影响 ​

.gitignore 只控制未跟踪文件。一个文件如果曾经被提交，即使后来写进 .gitignore，Git 仍会继续跟踪它的修改。

bash
# 从索引中移除，但保留磁盘文件
git rm --cached .env
git commit -m "chore: 停止跟踪本地环境变量文件"

# 确认状态
git status -s
# D  .env        ← 暂存区记录为删除

如果 .env 已经推送过，历史中仍然存在敏感信息。此时必须轮换密钥，再视情况用历史改写工具清理；仅删除当前文件并不能让泄露的凭据失效。

空目录不会被跟踪

Git 只跟踪文件。一个目录下的文件全部被忽略时，该目录不会出现在提交中。需要保留结构时，放一个 .gitkeep 并显式 git add。

常见坑 ​

git add . 可能把密钥一起提交

. 会递归暂存当前目录下所有未忽略文件，包括 .env、本地数据库、调试配置。养成先 git status -s 再 git add <具体路径> 的习惯；至少确认 .gitignore 已覆盖敏感文件。

.gitignore 对已暂存文件无效

文件已经进入暂存区后，再加入 .gitignore 不会自动取消暂存。必须 git restore --staged <file> 或 git rm --cached <file>。

删除文件用 git rm

直接 rm file 后，git status 会显示 D，仍需 git add -u 才把删除写入暂存区。git rm file 一步完成删除与暂存；只想取消跟踪、保留磁盘文件时用 --cached。

小结 ​

  • 四层结构是工作区、暂存区、本地版本库、远程仓库，add、commit、push 依次推进。
  • 文件状态按 untracked → staged → committed → modified 循环，暂存区是提交内容的唯一来源。
  • git status -s 的 X 列表示已暂存变化，Y 列表示未暂存变化。
  • .gitignore 只影响未跟踪文件，已跟踪文件需要 git rm --cached 才能停止跟踪。
  • 提交前先看状态，再精确暂存，能避免绝大多数误提交。
