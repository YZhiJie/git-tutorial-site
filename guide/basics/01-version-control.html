01 版本控制与 Git 的定位 ​

学习目标 ​

  • 能说明版本控制在「可追溯、可回滚、可协作」三个维度上解决的问题。
  • 能对比集中式（Centralized VCS）与分布式（Distributed VCS）在存储与离线能力上的差异。
  • 能用自己的话解释 Git 的「快照（snapshot）而非差异（diff）」模型。
  • 能识别工作目录与 .git 目录的职责边界，并用 git init、git clone 创建仓库。
  • 能判断 Git 在需求、开发、测试、发布链路中的位置。

为什么需要版本控制 ​

没有版本控制时，团队通常靠文件名区分版本：需求_v1.docx、需求_v2_最终版.docx、需求_v2_最终版_改.docx。这套做法的问题不是「乱」，而是无法回答几个关键问题：

  • 某一行代码是谁、在什么时候、为什么改的？
  • 上周五还能跑的功能，是哪一个改动弄坏的？
  • 两个人同时改同一个文件，如何合并而不是互相覆盖？
  • 线上出故障时，如何精确回到上一个可用版本？

版本控制系统（Version Control System，VCS）把这些问题收敛为三个能力：

能力具体表现
可追溯每次变更都有作者、时间、说明和完整内容
可回滚任意历史版本都能检出，且不影响其他版本
可协作多人在各自副本上开发，再通过明确机制合并

对开发者而言，Git 不只是「备份工具」，它是代码变更的事实来源（source of truth）。代码评审、持续集成（CI）、发布、故障定位都建立在提交历史之上。

集中式与分布式 ​

集中式版本控制的代表是 SVN。仓库只有一份，放在中央服务器；开发者检出（checkout）工作副本，提交时直接写服务器，因此提交必须联网。分支通常通过目录拷贝实现，成本高，团队往往不敢频繁开分支。

分布式版本控制的代表是 Git。每次 git clone 得到的不只是最新文件，而是包含全部历史的完整仓库。提交先写本地数据库，只有 git push 才需要网络。分支只是一个指针，创建和切换几乎零成本。

维度集中式（SVN）分布式（Git）
仓库位置仅中央服务器每个克隆都是完整仓库
提交直接写服务器，需联网先本地提交，推送时才联网
历史依赖服务器本地拥有完整历史
分支目录拷贝，成本高指针移动，成本极低
离线工作基本不可用可提交、查历史、切分支
版本标识全局递增版本号内容哈希（commit SHA）

需要强调：分布式不等于不需要远程仓库。团队仍然会用 GitHub、GitLab 作为共享中心，但它只是「多个完整仓库中的一个」，而不是唯一数据源。

快照而非差异 ​

传统版本控制倾向于保存「文件相对上一版的差异」，读取某个版本时需要从头叠加补丁。Git 的做法不同：每次提交（commit）保存的是当时整个项目的一份快照（snapshot）。

为了不把未修改的文件重复存一遍，Git 用内容寻址（content-addressed）的方式存储对象：文件内容计算出哈希值作为对象 ID，内容相同的文件只存一份。快照中的目录树（tree）引用这些对象，提交对象（commit）再引用目录树和父提交。

text
commit 3f2a1c9
  └── tree（项目根目录快照）
        ├── blob a1b2c3  README.md
        └── tree 4d5e6f  src/
              └── blob 7a8b9c  main.ts   ← 与上一提交内容相同，复用同一对象

commit 8b1e0d4  ← 父提交，同样指向一棵 tree

因此：

  • 查看历史版本是「取出某棵 tree」，不需要重放补丁。
  • 比较两个版本时才临时计算差异，git diff 是结果而非存储形式。
  • 任何内容一旦写入对象库就不可变，修改文件只会产生新对象。

这也解释了为什么提交哈希能作为版本唯一标识：它由内容、父提交、作者和时间共同决定，篡改历史必然改变哈希。

工作目录与 .git 目录 ​

一个 Git 仓库由两部分组成：

  • 工作目录（working tree）：你实际编辑的文件，普通目录结构。
  • .git 目录：仓库数据库与配置，包含对象、引用、索引、钩子等。
bash
ls -a
# .  ..  .git  README.md  src

ls .git
# HEAD  config  description  hooks  index  info  logs  objects  refs

几个关键条目：

路径作用
.git/objects所有文件内容、目录树、提交对象
.git/refs/heads本地分支指针，每个文件内容是一个提交哈希
.git/HEAD当前所在分支的引用
.git/index暂存区（staging area）的二进制记录
.git/config当前仓库的本地配置
.git/logsreflog，记录 HEAD 与分支的移动历史

删除 .git 等于删除全部历史，工作目录会退化成一个普通文件夹。反过来，拷贝项目时带上 .git，就把完整历史一起带走了。

快速判断当前目录是否在仓库内

git rev-parse --is-inside-work-tree 输出 true 表示在工作目录内；输出 fatal: not a git repository 表示不在任何仓库中。

最小演示：init 与 clone ​

从零创建一个仓库：

bash
mkdir git-demo && cd git-demo
git init
# Initialized empty Git repository in /Users/you/git-demo/.git/

git status
# On branch main
# No commits yet
# nothing to commit (create/copy files and use "git add" to track)

如果初始化提示 On branch master，说明 init.defaultBranch 仍是旧默认值，可在下一篇配置为 main。

创建第一个提交：

bash
echo "# Git Demo" > README.md
git add README.md
git commit -m "chore: 初始化仓库"
# [main (root-commit) 3f2a1c9] chore: 初始化仓库
#  1 file changed, 1 insertion(+)

git log --oneline
# 3f2a1c9 chore: 初始化仓库

从远程获取一个已有仓库：

bash
git clone https://github.com/octocat/Hello-World.git
cd Hello-World
git log --oneline -3
# 7fd1a60 Merge pull request #6 from ...

git clone 等价于：初始化本地仓库、登记远程地址（origin）、拉取全部对象、创建工作分支并检出。默认会取完整历史；--depth 1 可做浅克隆，只取最近一次提交，适合 CI，但不适合需要查历史或做合并的场景。

Git 在研发链路中的位置 ​

一个典型的企业研发链路中，Git 承担「代码变更的记录与流转」：

  1. 需求拆分为任务，从主干拉出功能分支。
  2. 开发者在本地以小提交推进，每个提交可独立解释。
  3. 推送分支，发起合并请求（Pull Request / Merge Request）。
  4. CI 在提交上运行测试与静态检查，评审在差异上进行。
  5. 合并回主干，按发布节奏打标签（tag）。
  6. 线上问题通过回滚提交或热修复分支处理。

Git 不负责需求管理、构建产物和部署状态，但它为这些系统提供稳定的版本坐标：CI 跑在哪个提交、镜像由哪个提交构建、线上运行的是哪个 tag，都应能追溯到唯一的 commit 哈希。

常见坑 ​

不要把 .git 当普通目录操作

手动删除 .git/refs、编辑 .git/HEAD、用文件管理器覆盖 .git，都可能让仓库无法识别。需要修改引用时使用 git branch、git switch、git update-ref 等命令，让 Git 自己维护一致性。

克隆下来的仓库不是「只读副本」

本地克隆拥有完整历史，可以随意提交、重置、变基。这些操作在推送前只影响本地；一旦推送，就会影响所有协作者。权限控制应放在远程仓库，而不是指望本地副本「不会改」。

用网盘同步工作目录会损坏仓库

把包含 .git 的目录放进 iCloud、OneDrive、Dropbox 实时同步，可能在写入对象时产生冲突文件，导致索引或对象损坏。需要备份时使用 git push 或 git bundle。

小结 ​

  • 版本控制解决的是可追溯、可回滚、可协作，Git 是代码变更的事实来源。
  • 分布式意味着每个克隆都有完整历史，提交在本地完成，推送才需要网络。
  • Git 保存提交时刻的完整快照，通过内容哈希去重复用对象，差异是临时计算出来的。
  • 工作目录是可见文件，.git 是仓库数据库；删除 .git 就删除了历史。
  • git init 从零建库，git clone 复制完整仓库并建立远程关联。
