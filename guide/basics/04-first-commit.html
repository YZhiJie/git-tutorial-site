04 提交四件套：status / add / commit / log ​

学习目标 ​

  • 能用 git status 和 git diff 判断改动处于工作区、暂存区还是提交中。
  • 能用 git add -p 把一次修改拆成多个逻辑提交。
  • 能说清 git commit -m、git commit -a 的行为边界。
  • 能写出符合 Conventional Commits 的提交信息。
  • 能用 git log --oneline --graph --decorate 与 git commit --amend 检查和修正历史。

四件套的分工 ​

日常节奏是：先看状态与差异，再精确暂存，然后提交，最后用日志确认。跳过前两步，容易把无关改动或敏感文件带进提交。

git status：先看清局面 ​

bash
git status -s
#  M src/login.ts
# ?? src/utils/crypto.ts

git status -sb
# ## feature/login...origin/feature/login [ahead 1]

-s 输出短格式，-b 额外显示分支与上游跟踪关系。ahead 1 表示本地比远程多一个提交，behind 2 表示远程多两个提交。

git diff：三个比较视角 ​

同名命令在不同参数下比较的对象完全不同：

命令比较对象典型用途
git diff工作区 vs 暂存区看还有哪些改动没暂存
git diff --staged暂存区 vs HEAD看这次提交将包含什么
git diff HEAD工作区 vs HEAD看全部未提交改动
git diff main...feature两分支分叉点 vs feature看分支实际引入了什么
bash
git diff
# diff --git a/src/login.ts b/src/login.ts
# --- a/src/login.ts
# +++ b/src/login.ts
# @@ -12,6 +12,9 @@ export function login() {
# +  retry(3)

git diff --staged
# 暂存区与 HEAD 的差异

只看文件名用 git diff --name-only，统计用 git diff --stat。

提交前必看的两个命令

git status -s 确认文件清单，git diff --staged 确认内容。两者都通过再执行 git commit，能拦住大部分误提交。

git add：选择进入提交的内容 ​

bash
git add src/login.ts          # 暂存单个文件
git add src/                  # 暂存目录下所有变化
git add -u                    # 只暂存已跟踪文件的修改与删除
git add -A                    # 暂存所有变化，包括新增文件

git add . 等价于对当前目录执行 -A，会递归包含新增文件。路径越具体，提交越可控。

分块暂存：git add -p ​

一个文件里混着两件事（修 bug 和改格式）时，用 -p（patch）逐块选择：

bash
git add -p src/login.ts
# @@ -12,6 +12,9 @@ export function login() {
# +  // 增加超时重试
# +  retry(3)
# Stage this hunk [y,n,q,a,d,s,e,?]?

常用按键：

按键含义
y暂存这一块
n跳过这一块
s把当前块拆成更小的块
e手动编辑要暂存的行
q退出，不再处理后续块
?显示帮助

分块暂存后，可以第一次提交只包含 bug 修复，第二次提交只包含格式调整。历史更清晰，回滚和评审也更容易。

暂存的是内容，不是文件

git add 记录的是此刻的文件内容快照。暂存后继续修改文件，新改动不会自动进入暂存区，git status 会显示 MM。提交前再跑一次 git add。

git commit：生成提交 ​

bash
git add src/login.ts
git commit -m "feat: 登录接口增加超时重试"
# [feature/login 3f2a1c9] feat: 登录接口增加超时重试
#  1 file changed, 3 insertions(+)

# 需要补充说明时使用多个 -m
git commit -m "fix: 修复登录超时" -m "超时阈值从 3s 调整为 10s，并补充重试上限。"

不写 -m 会打开 core.editor 配置的编辑器，按以下结构填写：

text
fix: 修复登录超时

超时阈值从 3s 调整为 10s，避免弱网环境下误判失败。
补充重试上限，最多 3 次。

Closes #128

git commit -a 的边界 ​

bash
git commit -a -m "chore: 同步格式化结果"

-a 会自动暂存已跟踪文件的修改与删除，然后提交。它不会包含：

  • 未跟踪的新文件；
  • 已暂存内容之外、提交前又改动的部分（-a 会一并暂存，但不含未跟踪文件）。

因此 -a 适合「全是已跟踪文件的小改动」，不适合新增文件的场景。

提交信息规范 ​

团队协作中推荐 Conventional Commits，格式为：

text
<type>(<scope>): <subject>

<body>

<footer>
type用途示例
feat新功能feat(auth): 支持手机号验证码登录
fix修复缺陷fix(order): 修复金额为 0 时无法提交
chore构建、依赖、脚手架chore: 升级 Vite 到 5.4

subject 用祈使句、不超过 50 个字符、结尾不加句号。破坏性变更在 footer 写 BREAKING CHANGE: ...，或在 type 后加 !，如 feat(api)!: 移除 v1 接口。只写 update、fix bug 这类信息无法生成变更日志，也无法在排查时提供线索。

git log：回看历史 ​

bash
git log --oneline --graph --decorate --all
# * 3f2a1c9 (HEAD -> main, origin/main) feat: 登录接口增加超时重试
# * 8b1e0d4 fix: 修复超时
# * 2a9c7f1 chore: 初始化项目

常用筛选：

bash
git log -5                          # 最近 5 条
git log -p                          # 每条提交的具体差异
git log --author="Zhang San"        # 按作者
git log -S "retry(3)"               # 搜索引入/删除该字符串的提交

--oneline --graph --decorate --all 是排查分支结构最常用的组合：一行一个提交，画出分叉与合并，显示分支与标签指向。

git commit --amend：修正最后一次提交 ​

漏了一个文件，或提交信息写错，且尚未推送时：

bash
git add src/utils/crypto.ts
git commit --amend --no-edit
# [feature/login 9c4d2e1] feat: 登录接口增加超时重试
#  2 files changed, 20 insertions(+)

--amend 不是「修改原提交」，而是用当前暂存区创建一个新提交替换它：

  • 提交哈希会变化；
  • 原提交仍在 reflog 中，短时间内可找回；
  • 只影响最后一次提交，更早的提交需要交互式变基。

已推送的公共提交不要 amend

改写提交会让本地与远程历史分叉，其他人拉取后会产生重复提交或冲突。需要更新远程时必须使用 git push --force-with-lease，且只允许在自己的功能分支上操作。主干分支（main/develop）通常受保护，禁止强推。

常见坑 ​

提交信息只写「update」

历史一旦积累，git log 无法回答「这次改了什么、为什么改」。至少写清 type 和一句话主题，复杂改动在正文补充背景与影响范围。

小结 ​

  • 提交前用 git status -s 看清单，用 git diff --staged 看内容。
  • git add -p 能把一次修改拆成多个逻辑独立的提交。
  • git commit -a 只覆盖已跟踪文件，不包含未跟踪的新文件。
  • Conventional Commits 让历史可读、可生成变更日志，type 与 subject 必须准确。
  • --amend 会生成新哈希，仅用于未推送的个人提交。
